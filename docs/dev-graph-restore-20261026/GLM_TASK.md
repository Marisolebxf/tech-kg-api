# 给 GLM 的执行提示词

你现在直接执行下面的任务，在你当前工作的开发分支新增代码与文档，不要只交付分析或计划。用户要求依据原 `dev` 的 SQL 快照，在**另一个新图空间 `dev_restore_20261026`** 恢复数据、准备测试数据和验证九大业务展示。**原 `dev` 只能作为只读参考，禁止向它写入、覆盖、清空、删除数据或修改 Schema/索引。** 保持已有未提交修改，按仓库指令执行测试。

## 必须遵守的图空间隔离

- 默认目标固定为 `dev_restore_20261026`。如果同名空间存在，只有确认它属于本次恢复后才可幂等续跑；否则另选带唯一后缀的新空间，并将实际空间名统一传递给后续步骤，不清空已有空间。
- 恢复、建 Schema/索引、测试数据装载、重试、清理、核验及索引重建都必须显式接收并使用同一个目标空间。写入入口在连接/写入前校验目标非空且不等于 `dev`，不满足就立即退出；不得通过隐藏开关绕过。
- 同时核对客户端空间配置、HTTP `X-Graph-Space`、nGQL `USE` 与脚本参数，禁止任一层回退到现有默认 `dev`。复用客户端时须显式绑定新空间，不复用指向 `dev` 的写客户端。
- 前端与 API 验收使用独立测试实例、请求级空间选择或独立配置，全部指向实际新空间。不得为此修改现有业务服务的全局默认图空间、覆盖公共 `.env` 或把现有 dev 入口切换到恢复数据；配套搜索/向量索引、缓存等也需按新空间隔离。
- 报告每一步实际使用的图空间。保护目标的入口测试必须覆盖传入 `dev`、空值或配置不一致时拒绝写入；这些测试使用 mock，不向原 dev 发送任何测试写请求。

## 目标

1. 使用 `docs/dev-graph-restore-20261026/data/dev_graph_restore_20261026.sql.gz`，新增脚本，在新图空间 `dev_restore_20261026` 恢复与原 `dev` 大体相似的图。允许 VID/EID 改变，实体属性、关系连接、多条关系实例和业务用途必须正确；不向原 dev 写入。
2. 准备能覆盖九大业务、方便前端丰富展示的测试数据。优先利用恢复数据，缺少的场景使用明确标记的可重复生成测试数据补齐。
3. 实际验证九个页面；把测试数据和证据单独记录在当前分支的 `docs/dev-graph-restore-20261026/NINE_BUSINESS_TEST_DATA.md`。

阅读本目录 README、`data/schema.sql`、`data/manifest.json`、测试数据文档，再查当前分支 `README.md`、`CLAUDE.md`、前后端路由、业务服务、DAO、图客户端与 DDL。不要仅依据旧文档猜规则。

九大业务以前端路由和 `frontend/src/views/business-service/service-modules.ts`、`actual-service-rules.ts`（以当前分支实际路径为准）为准，不直接把后端 catalog 的 12 个子服务当作 12 个业务。

## A. 新增 SQL → 独立新图空间恢复脚本

新增独立恢复入口，不直接调用那些依赖旧 `dwd_*` 来源表的历史全量 ETL 来冒充恢复。可以复用现有图客户端、DDL/转义/批写工具和当前平台契约。建议提供恢复入口、测试数据入口和核验入口，名称可以遵循当前仓库风格，例如：

- `backend/script/restore_dev_from_sql.py`
- `backend/script/seed_nine_business_restore.py`
- `backend/script/verify_dev_restore.py`

实现要求：

1. 导入或读取 SQL 恢复库，先核对 54 张表、15 个输入视图。识别 15 种实体、37 种关系，以及两张辅助表。
2. 先在实际新图空间创建所需图 Schema/索引并装载节点，再装载关系；遵循当前仓库实际客户端及平台约定。先 DESCRIBE/核对属性类型，不向严格 Schema 写未知列；需要调整 DDL 时使用显式绑定新空间的 schema 管理能力，不修改原 dev 的 Schema/索引。
3. SQL 的 `id` 是新来源键。统一实现并持久化“来源节点键 → 新 VID”映射，关系两端从同一映射解析。不要为实体和关系各生成一套不一致的 ID，也不要随机生成后不保存映射。保留原业务属性与原业务标识，核对 API resolver、搜索、详情及传参兼容性。
4. 367,011 个节点有实际属性，127,397 个端点缺少属性；全量新节点键为 494,408。`v_input_*` 已提供带 `_is_placeholder` 的输入，Person 166,940 行、Organization 11,206 行。明确保留并标记占位，不把未知人物伪装成已补全，不静默丢关系。若目标 Schema 必填字段阻碍占位写入，要使用可追溯的兼容策略并报告影响范围。
5. `organization_base` 是共挂标签：恢复同一节点的标签身份，不重复新建节点。SQL 原始属性对象在 `_properties`，可用于核验；辅助表和辅助字段不是额外业务类型。
6. 恢复全部 528,537 条已提供关系，合著关系 156,140 条。`from_schema/to_schema` 不是属性名装饰，要保留不同端点组合。不同来源关系行可能同类型、同两端：为它们使用稳定的新 rank/关系身份，不能全部按 `@0` 覆盖，也不能错误地去重成一条。
7. 使用分批、限并发、重试、断点续跑与幂等写入；输出逐类型扫描/成功/失败/跳过/隔离数量及失败明细。清理操作仅限实际新图空间内、本任务生成的 fixture 命名空间/批次；禁止清理原 dev，也不通过删除整个恢复空间来绕过幂等问题。
8. 六类大关系导出可能缺原图并行 rank，本 SQL 不能承诺逐字节还原原图。以本 SQL 实际行与业务相似性为基准，如实写出无法恢复的范围。
9. 检查前端/API 的 MySQL enrichment、实体解析、Milvus/搜索索引、缓存等依赖。恢复的是图投影库，并没有自动恢复所有 `dwd_*` 表；不能继续依赖不存在的数据源让页面空白。需要的兼容查询、同步或索引构建应接到同一批可追溯数据。

## C. 验证、文档与完成条件

1. 校验 SQL 源行数、图中分类型节点/边数量、属性样本/指纹、端点可达、占位数量。把源实际节点、占位、新增 fixture、共挂标签分别统计；有额外融合/过滤时给出逐项差异，不把它们算成“丢数据后仍通过”。
2. 重跑恢复和 fixture 入口，核对重复执行不会无限增节点或丢失并行边。记录执行命令、环境指向、耗时、批次和失败清单。
3. 按仓库要求运行有关测试；有必要的脚本逻辑测试与真实环境检查都要完成。前端验证应通过明确指向实际新图空间的测试入口打开九个页面，操作主要交互，检查非空业务结果、节点/关系和详情可见、控制台/API 无相关错误。可以用 Playwright 或现有可见浏览器工具，留下图空间配置、截图及请求/响应证据，不能误用现有 dev 页面的结果。
4. HTTP 200、空数组、只有占位、只展示固定假页面、旧校验日志，都不能算成功。环境阻碍实际验证时写清未验证项，不冒称通过。
5. 在当前分支维护 `docs/dev-graph-restore-20261026/NINE_BUSINESS_TEST_DATA.md`，每个场景记录：实际新图空间（默认 `dev_restore_20261026`）、隔离测试入口、来源/fixture 标记、SQL 主键和新 VID 对照、查询参数、时间范围、触发步骤、预期非空结果、实际数量、截图/日志路径、状态与问题。新增独立恢复执行记录，给出从空环境重现的命令，并记录原 dev 未被本任务写入、覆盖或清理的核查依据。
6. 提交当前分支新增脚本、必要兼容修复、测试和文档；不混入凭据、本机环境文件或其他人的未提交修改。最终回复提交号、代码/文档路径、九大业务逐项结果和仍存在的限制。

交付目标是“能够重跑的恢复过程 + 真实可用的九大业务展示 + 可复测的数据文档”，不能止步于导入 SQL 或仅写方案。
