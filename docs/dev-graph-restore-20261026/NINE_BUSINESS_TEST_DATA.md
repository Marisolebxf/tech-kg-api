# 九大业务测试数据登记与验收交接

本文是 SQL 重建任务的测试数据交接文档。**目前只登记已核对的数据基线、代码入口和待执行场景；尚未在 GLM 的运行环境重建图谱或验收九大业务，下面所有执行状态均为“待执行”。** GLM 完成实现后，应直接在其当前分支更新本文，填写实际 ID、请求、响应、截图和执行结论。

**目标为独立新图空间 `dev_restore_20261026`，原 `dev` 只读，禁止向其写入、覆盖、清空、删除或修改 Schema/索引。** 恢复、测试数据、清理及前端/API 验收均显式使用实际新空间，测试入口和索引/缓存保持隔离，不修改现有业务服务的默认空间。若新空间重名且不属于本次任务，另取带后缀的新名称并登记，不覆盖它。

SQL 文件位置、校验方式及还原说明见同目录的 [README.md](README.md)。本文不包含数据库密码或特定机器的连接信息。

## 1. 数据基线及使用边界

以下是本次 SQL 的已知基线，不代表 GLM 环境的图谱已经达到这些数量：

| 项目 | SQL 基线 |
|---|---:|
| 业务实体表 | 15 张 |
| 业务关系表 | 37 张 |
| 有实际导出属性的节点 | 367,011 个 |
| 缺少节点属性的关系端点 | 127,397 个 |
| 含缺属性端点的统一节点键 | 494,408 个 |
| 包内实际恢复的关系 | 528,537 条 |
| 合著关系 `COAUTHOR_WITH` | 156,140 条 |

- `kg_node_index`、`kg_missing_node` 是辅助表，不再各建一批独立业务实体。
- `organization_base` 是共挂基础标签；其记录与业务节点重复，不应据此重复建人、论文等节点。
- `v_input_person` 的 166,940 行包括 40,139 个有属性人物及 126,801 个缺属性端点；`v_input_organization` 的 11,206 行包括 10,610 个有属性机构及 596 个缺属性端点。不能把占位行当作资料完整的演示人物或企业。
- 新 VID 可以不同。每个测试场景必须记录 SQL 关联键、运行时新 VID 和对应关系；不可直接复用旧文档中的 `person_*` 参数并宣称有效。
- 本 SQL 恢复的是导出包实际保留的记录。六个大关系类型只有按端点折叠的普通导出，不能宣称其全部并行 rank 已从原图完整恢复。
- SQL 基线数据与新造的测试数据必须分开统计。新增 fixture 应使用独立批次/来源标记和可定位的 ID 范围，重复运行应保持幂等；清理只针对该批次。
- 不得为原有真实人物或企业编造履历、任职、财务或风险事实。缺数据的展示场景应使用明确标识的虚构测试实体，或如实标记尚不支持。

### 当前规则中特别容易遗漏的点

1. **改 VID 后仍要能查到实体。** 检查接口是否按 `person_`、`node_` 前缀或原业务 ID 重建 VID；必要时通过来源键查询或 ID 映射适配，测试参数从当前重建图实际读取。
2. **时间条件不能靠空时间字段凑通过。** 使用当前表单和后端共同接受的格式，记录请求原文。旧文档可能混用 `YYYY-MM` 与 `YYYY-MM-DD`，须以当前代码和实际响应验证。
3. **直接合作不等于共同成果。** B03/B06 要选同一成果节点真实连接两位专家的样例。只有合著计数边时，不足以证明共同论文、项目、专利列表正常。
4. **论文合作的团队与被引需要完整邻域。** 共同作者、引用方论文、引用方作者、期刊和关键词节点都要实际存在；不能单凭节点上的累计数替代所有邻域展示。
5. **当前全景第四层为事件/资讯。** 本分支 `industry_chain_panorama.py` 中 `flagship_achievement` 的标题是“产业动态事件”，实际接受 `Event`/`News`，不是旧文档中的论文/专利/项目层。四层不得有一层因套用旧资料而始终为空。
6. **企业子模块可能仍依赖 MySQL/LLM。** 图重建不自动等于企业背景、财务等纯 MySQL 读取链路已恢复。需要使用的辅助功能应核实当前数据来源，补测试适配或如实登记缺口，不能伪造后端响应。
7. **页面应使用实际接口结果。** 摘要、列表、实体/关系详情、画布、图例和溯源应来自重建图或明确测试 fixture。已有前端示例 JSON、历史截图及旧 smoke 报告均不能作为新环境通过证据。
8. **占位节点与 fixture 区分。** 占位节点只是源包缺属性的端点；fixture 是新建的明确测试数据。二者都不能混称为“已恢复的完整人物资料”。
