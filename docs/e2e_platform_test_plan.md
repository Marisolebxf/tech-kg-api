## 0. 环境与通用约定

- **被测栈**：`docker-compose.dev2.yml`（已在运行）— web `http://localhost:8089`，api `http://localhost:8002`，temporal-worker / temporal / temporal-mysql 配套。
- **认证**：容器内 `AUTH_ENABLED=false`，所有页面与 API 免登录直达；admin 路由守卫直通。
- **默认图空间**：`dev2`（当前已索引 1115 实体）；可用空间：`algo_test` / `dev` / `dev2` / `e2e_verify_space` / `entity_binding_demo` 等。
- **测试数据源库**：`temporal-mysql-dev2` 上的 `techkg_e2e` 库（`widgets` 表含正常行 + 毒行，是既有 e2e 数据，凭据取自根目录 `dev2_extract_e2e.py`）。
- **造数/清数命名**：一律 `e2e_` 前缀，测试后统一回收（删 schema / 删配置 / 删任务走 UI 删除，本身即覆盖删除功能）。
- **断言三层**：① 界面可见反馈（文案/角标/表格行）② API 复核（curl 8002 对应端点）③ 图库复核（graph-console 执行 `DESCRIBE TAG` / `MATCH ... RETURN count(v)`）。
- **原生 confirm 弹窗**：配置删除、任务删除用 `window.confirm`，Playwright 以 `page.on('dialog')` 接受。
- **用例落点**：`frontend/e2e/platform/*.spec.ts` + 新增 `frontend/playwright.platform.config.ts`（baseURL `http://localhost:8089`，chromium）。宿主机执行。
- **已知环境噪音**（非回归，不记 bug）：`review-full-integration.spec.ts` 需独占环境，不在本方案执行。
- **已知缺陷（待修复，非噪音）**：embedding 服务故障（如 key 过期 401）时索引构建**静默降级**——`index.degraded` 只写入执行结果 JSON（`temporal_workflows.py`），前端零渲染、任务仍显示成功。用户已判定不可接受：服务出错必须显式提醒，验收用例 F6。

## B. 图谱查询（/overview 的「query」Tab）

### B1 参数模式查询
- **前置**：先经 nGQL 或实体列表取 dev2 空间一个真实实体名（如某个 Paper 名称）。
- **步骤**：切到 query Tab（参数模式）→ 填实体名称 → 图谱范围选「科研成果图谱」→ 点「查询图谱」。
- **输入**：真实实体名；范围=科研成果图谱。
- **预期输出**：「综合图谱展示」渲染画布并显示「N 个节点 / N 条关系」统计；下方详情面板出现 摘要|实体|关系|溯源 四个 Tab；图谱范围留空/非法时「查询图谱」不可用或有校验提示。
- **实体颜色图例**（与九大业务对齐）：画布旁「实体类型图例」**跟随本次返回的图数据动态变化**——图例项=结果中实际出现的实体类型集合，颜色与画布节点一致；换一个结果更收敛的实体名重查，图例随之收敛；空结果时图例不渲染。
- **最终状态**：节点数 ≥1，详情 Tab 均可切换；图例与画布实体类型一一对应。

### B2 nGQL 模式执行
- **步骤**：切「nGQL 模式」→ 图空间选 `dev2` → 输入语句 → 点「执行 nGQL」（也验证 Ctrl+Enter）。
- **输入**：`MATCH (v:Paper) RETURN id(v) AS vid, v.Paper.name AS name LIMIT 5`；再执行 `MATCH (v:Paper) WHERE v.Paper.name == "__none__" RETURN v`。
- **预期输出**：第一条出「nGQL 执行结果 · 5 行记录」表格；第二条显示「语句执行成功，无返回记录」空态文案。
- **最终状态**：两种结果态均可见，无报错。

### B3 溯源三点与构建详情跳转 ★
- **步骤**：B1 结果中选中一个**实体节点**打开「溯源」Tab；再选一条**关系**看其溯源。
- **溯源三要素断言（与九大业务统一）**：Tab 同步展示三点——**【源数据表】**（MySQL 源表名）、**【英文字段名】**（MySQL 英文字段名）、**【图空间 VID】**（图空间里的 vid）；实体与关系均要有；关系选中时两端端点也各带三要素。值与图库复核一致：`MATCH (v) WHERE id(v)=="<VID>" RETURN v` 的 `source_table` 等溯源属性 = 页面展示的源数据表；VID 与画布节点 vid 一致。
- **预期输出**：三要素字段齐全非空（经平台抽取入库的实体必有三点；nGQL 手工造的裸节点可为空，记为条件分支并标注来源差异）。
- **构建详情跳转**：若实体有构建来源，点「查看构建详情 →」跳转到对应流程实例详情页，落地页为 ProcessInstanceDetailView 且无 JS 错误（无来源数据时该按钮不出现，记为条件分支）。

### C10 删除：引用拦截 + 假删模式 + 二次确认 ★（假删为需求驱动）
- **引用拦截（已实现）**：先尝试删除仍被 `E2E_RELATES` 引用的 `E2EWidget` 实体 → 被拦，提示「该实体 Schema 仍被关系引用，请先删除关系: E2E_RELATES」（后端 `referenced_relation_names` 守卫）——实体删除之前必须先删除关系。
- **删除顺序**：先删关系 `E2E_RELATES`、再删实体 `E2EWidget`，两者均出现**二次确认弹窗**（文案说明后果），确认后列表行消失。
- **假删模式（delete flag，需求驱动）**：实体和关系删除应采用**假删**——置删除标记而非物理删行，**读取路径统一用该 flag 过滤**。
  - 预期：删除后 `GET /schemas` 不再包含两条目（读取过滤生效）；控制库中两行仍存在且 `is_deleted=true`（DB 复核）；图库 TAG/EDGE **不 DROP**（`DESCRIBE TAG E2EWidget` 仍成功——目录假删不破坏图库存量数据）。
  - **现状（2026-09-03）**：schema 级删除是**硬删**（`_dao.delete` 物理删行 + S3 脚本清理，图库本就不 DROP——原用例断言"图库已 DROP"与实现不符，一并纠正）。按需求改为 flag 假删 + 读取过滤后验收；属性级仍保持硬删除（ae31551 产品决策，不随之回退）。

### C12 权限：标准实体/关系只读（管理员可改，普通用户不可）（条件分支）
- **要求**：标准（系统）实体/关系对普通用户**只读**——无编辑入口/接口拒绝；平台管理员可修改。
- **实现现状**：后端已 gating（`assert_mutable`：is_system 需平台管理员或 `SCHEMA_ADMIN_USER_IDS`；非系统需 owner 或管理员），修改/删除共用。
- **验证方式**：dev2 容器 `AUTH_ENABLED=false` 时 admin 校验直通，UI 无法区分角色 → 本用例需 `AUTH_ENABLED=true` + 一个普通账号 + 一个管理员账号（超出本方案"不含认证"范围，单列条件分支）：普通用户打开 `/schema`，标准实体/关系行无「属性管理」「上传脚本」「删除」等编辑入口；API 直调返回 403；管理员全量可操作。
- **兜底**：角色判定由后端集成测试覆盖（`tests/integration/test_schema_*` 权限分支），本用例仅在具备双账号环境时执行。

## N. 一对一脚本全量管道：新图空间完整验证 ★（N1/N3 需求驱动）

> 目标（用户 2026-09-03 确认）：全部 **49 个一对一抽取脚本（15 实体 + 34 关系）**经**前端界面**驱动——上传脚本、启动任务——从各自绑定的数据源表读数、走完 activity steps、脚本只输出 JSON，由平台负责消歧/对齐/入库；全程在一个**新图空间**（非 dev2）验证，不污染现网。主测**单脚本任务**（实体抽取）与**多脚本任务**（关系抽取——关系脚本依赖实体先行），并覆盖任务的**两种触发方式：触发一次与周期触发**。
> 前置：现网数据源可连（D4 验证）；49 个 schema 均已有脚本+来源绑定（`script/register_platform_extraction.py` 注册产物）。

### N0 新图空间准备
- **步骤**：`POST /api/v1/graph-spaces` 创建 `e2e_full_<ts>`（真实 CREATE SPACE；传播延迟后 nGQL `SHOW SPACES` 可见）。
- **预期输出**：任务中心/查询页/实体列表的空间下拉均出现该空间。
- **最终状态**：新空间全平台可选。

### N1 新空间 Schema 创建 + 脚本上传（前端全流程，依赖 M1/M2）★
- **方式（用户 2026-09-03 确认）**：不做任务侧自动建 DDL——在新空间按**脚本定义的实体描述**，走前端页面把 schema 全部建好，再上传脚本，再跑任务：
  1. `/schema` 页图空间切到 `e2e_full_<ts>`（M1）→ 按 15 个实体脚本的 SOURCES 元数据（实体名/属性/描述）**逐个前端创建实体 schema**（M2：DDL 在新空间执行 `CREATE TAG IF NOT EXISTS`）。
  2. 再按 34 个关系脚本的描述创建关系 schema（起点/终点选新空间已建实体——M3 联动；顺序保证端点存在）。
  3. 对全部 49 个 schema 走前端「上传脚本」传对应 transform 脚本（C3 通道全量验证）。
  4. 逐个「来源表」绑定数据源/库/表（C4 通道；SOURCES 元数据提供表名，query_sql 复杂源按注册器探测结果填）。

- **前置依赖**：M1/M2/M3（schema 页空间选择与按空间创建）未实现时本步无法走前端——这是 N 组的先决需求，优先级排在 M 组之后。
- **效率说明**：49 个表单可由 Playwright 循环驱动（SOURCES 元数据即造数清单）；若表单体量过大，允许退化 5~8 个走 UI 表单、其余经同端点 API 创建（记录退化比例）。

- **要求**：关系脚本依赖实体就位——多脚本串行任务需支持 **schema 抽取步**（每步=一个 schemaId 抽取），实体步在前、关系步在后，一步失败即停并可定位。**现状**：chain 只串上传 python 脚本定义（`create_chain_definition` 强制 `sourceKind=python`），不能串 schema 抽取 → 需求驱动改造。

### N5 触发方式②：周期触发（真实调度）★

- **清理**：删除任务；`e2e_full_<ts>` 空间与数据保留策略执行后决定（DROP SPACE 或留作 N 组回归环境，记录在案）。
