# 双 VID 查询兼容

当实体属性保存在 MySQL 裸 ID 节点，而关系端点使用带前缀 VID 时，读取两端并在响应中合并。无需环境变量或图空间开关。原图库不做属性迁移或关系重写。

例如 IC0007 保存“集成电路”的属性，chain_IC0007 保存 HAS_NODE 边：查询任一 ID 均补齐实体属性，沿两种 ID 查询关系。存在同类型带前缀节点时，响应使用带前缀 ID；普通单套 VID 数据保持原节点 ID。仅按已知实体类型处理前缀，不拆分 ID 内部下划线。裸 ID 同时对应多个配置实体类型时返回冲突，调用方需使用完整带前缀 ID。

入口统一经过 infra/graph_db/vid_alias.py，覆盖节点单查、批查、列表及属性查找、邻域、子图扩展、最短路径。显式类型路径搜索先遍历真实关系、再使用合并后的实体属性做年份等过滤；按逻辑端点、关系类型和 rank 去重，再分页。兼容路径最多读取/保留 20000 条边或中间路径，超出返回错误，不静默截断成完整结果。列表 total 仍表示图库物理计数，不把整个图库全量扫描做逻辑实体计数。

实体有效属性优先取裸 ID，同类型带前缀节点补齐空缺，保留 0 和 false；不借用其他实体类型的属性。保留既有置信度回写功能，但回写地址定位到真实保存属性的节点，避免把属性继续写到空端点。

已知前缀见 PREFIXES，采用现有抽取约定（person_、org_、paper_、patent_、project_、keyword_、chain_、node_ 等）。关系类型及方向仍遵守原业务 Schema；此兼容不将任意不同名称的关系类型自动视为同义关系。
