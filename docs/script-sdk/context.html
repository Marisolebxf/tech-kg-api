模块：backend/sdk/kg_sdk.py —— 五类客户端的懒构造、降级约定与跨运行水位。

  • 注入机制：KG_SCRIPT_CTX

被 Temporal activity 以子进程方式加载的脚本，不自己读配置文件、不自己建连接 —— 一切连接参数由 activity 在子进程外解析好后序列化注入。kg_sdk.Context 就是这层注入的载体：

# activity 子进程内的注入链路
activity（解析数据源选择器 → 连接参数 dict）
  └─ env KG_SCRIPT_CTX = {"mysql": {...}, "graph": {...}, "watermark": ...}
      └─ 脚本进程 Context(raw) → ctx.mysql / ctx.graph / ctx.llm ...（懒构造）

两种脚本入口

两参形式：step_fn(payload, ctx)

activity 已经替你包装好 Context，直接用第二个参数：

def my_step(payload: dict, ctx: "Context") -> dict:
    if ctx.mysql is None:                 # 未选择 MySQL 数据源 → 降级
        return {"status": "skipped"}
    ...

单参形式：workflow(payload)

与内置抽取脚本的 Temporal 入口同形态。Context 从环境变量自行构造：

from kg_sdk import current_context

def workflow(payload: dict) -> dict:
    ctx = current_context()          # 未配置（本地 dev / legacy）时返回 None
    if ctx is None:
        ...                           # 自行降级：读环境变量直连，或直接报错
约定

current_context() 在一次进程内是缓存的（reset_current_context() 供测试重置）。 JSON 解析失败时静默返回 None 而不是抛错 —— 脚本必须对 None 做降级判断。

五类客户端与降级约定

五个属性全部懒构造：第一次访问才建连接。某个选择器没配置时对应属性返回 None （与 infra.llm.get_llm_client 的降级约定一致），脚本统一用 if ctx.xxx: 判空：

属性类型说明
ctx.mysql infra.mysql.MySQLClient | None SQLAlchemy 引擎封装；参数键：host / port / database / username / password
ctx.graph infra.graph_db.TRSGraphClient | None 构造后自动 connect()；参数键：base_url / space / api_key / timeout
ctx.milvus pymilvus.MilvusClient | None 参数键：uri / db_name / token / timeout；token 缺省不发
ctx.llm infra.llm.LLMClient | None 无 api_key 即 None；参数键：api_key / base_url / model
ctx.embedding infra.llm.EmbeddingClient | None 同上，多一个 dimensions 
def workflow(payload: dict) -> dict:
    ctx = current_context()

    rows = [...]                       # ① 读 MySQL
    if ctx and ctx.mysql:
        from sqlalchemy import text
        with ctx.mysql.engine.connect() as conn:
            rows = [dict(r) for r in
                    conn.execute(text("SELECT ...")).mappings()]

    summary = ""                        # ② LLM 合成，失败降级
    if ctx and ctx.llm:
        summary = ctx.llm.synthesize(...) or ""

    return {"rows": len(rows), "summary": summary}

水位与检查点：ScriptConfig

跨运行增量状态由 activity 在 step 成功后写回，脚本通过只读的 ctx.config 读取：

@dataclass(frozen=True) class ScriptConfig: watermark: str | None = None # ISO 时间戳水位 checkpoint: dict | None = None # 任意 JSON 检查点（如已处理到的偏移）
def workflow(payload: dict) -> dict:
    ctx = current_context()
    since = payload.get("since")
    if ctx and ctx.config.watermark:
        since = since or ctx.config.watermark   # 显式 payload 优先，其次上次水位

    from script.entity_extractors_one_entity.common import apply_since, iter_rows
    sql = apply_since("SELECT * FROM t ORDER BY id", since)
    ...

水位读写与 etl_watermark.py（独立 CLI）共享同一套约定；框架侧的自动写回发生在 Temporal activity 的输出后处理阶段（_write_watermark），脚本本身只负责消费水位并在输出里 报告本次处理到的最大更新时间（供框架写回）。

运行元信息

Context 同时暴露本次执行的调度元信息，可用于日志打标或幂等键：

属性类型含义
ctx.step_idstr | None当前 step 标识
ctx.attemptint | None重试次数（第几次尝试）
ctx.prev_outputsdict上游 step 的输出（管道串联用）
ctx.execution_idstr | None流程实例 ID
ctx.task_idstr | None任务 ID
ctx.definition_idstr | None流程定义 ID
ctx.to_dict()dict原始注入 dict（调试用）

注入机制：KG_SCRIPT_CTX

  • activity 把「已解析的连接参数」（不是活对象）JSON 序列化进 KG_SCRIPT_CTX 环境变量； 两参 step 脚本同时合并进 ctx dict。
  • 本地调试可以自己伪造：
# 本地手工构造 Context 跑用户脚本（不依赖 Temporal）
KG_SCRIPT_CTX='{"mysql": {"host": "127.0.0.1", "port": 3306,
  "database": "gkx_element", "username": "root", "password": "..."},
  "graph": {"base_url": "http://localhost:8090", "space": "dev",
  "api_key": "..."}}' \
  uv run python user_script.py
安全边界

脚本进程持有明文密码与完整环境变量，这是观测，不是管控 —— 脚本可以绕开 ctx.mysql 直连任意地址。表级 ACL 需要网络层方案（子进程只允许访问代理端口），另行立项。 平台侧「脚本实际访问了哪些表」的观测方案见 docs/脚本数据访问溯源设计方案.md。
