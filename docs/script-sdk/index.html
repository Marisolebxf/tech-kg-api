为什么需要这套工具

写一个「从 MySQL 抽数据、写入 NebulaGraph」的脚本，听起来只是拼 SQL + 调接口。但生产级抽取脚本要面对的问题远不止这些：

问题SDK 提供的答案
表有几百万行，一把梭 SELECT 会把内存打爆 iter_rows() 分页迭代（OFFSET / keyset 游标双模式）
每次全量重跑太浪费 apply_since() 增量条件注入 + watermark 水位
重跑一次就多一批重复点/边 确定性 VID / 稳定键 / 边 rank，同一源记录重跑得到同一身份，覆盖更新而非重复插入
源数据脏：空串、"-"、"1,200万"、超长文本、NaN 值语义转换族（text_or_none、to_float_or_none、截断与降级）
一条坏行让整个任务失败 行级容错：mapper 异常计 invalid 并继续，最后汇总统计
数据从哪来的说不清 provenance() 溯源属性（源表 / 源记录 / 批次 / 置信度）随点边一起落图
边写了，端点却不存在（悬空边） existing_vids() 批量端点验存，缺失跳过并计数
同一个脚本要在命令行调试、也要被 Temporal 调度 双入口约定：CLI（argparse）与 workflow(payload) 共享同一份 build_sources()

能力地图：三个层次

整个工具集自下而上分三层：

┌─────────────────────────────────────────────────────────────────┐
│  编排层   run_entity_extractor / run_relation_extractor        │
│          逐源 → 分页 → 行级容错 → 批量写图 → 统计汇总            │
├─────────────────────────────────────────────────────────────────┤
│  写入层   EntityRecord / EdgeRecord                             │
│          merge 保护 · 端点验存 · ensure_edge_schema · 双写通道   │
├─────────────────────────────────────────────────────────────────┤
│  原语层   iter_rows · apply_since · 值语义 · VID · 溯源 · 置信度 │
├─────────────────────────────────────────────────────────────────┤
│  运行时   kg_sdk.Context（mysql / graph / milvus / llm / embed） │
└─────────────────────────────────────────────────────────────────┘
  • 运行时：Context 提供五类客户端的懒构造与降级约定 —— 被 Temporal activity 子进程加载的脚本通过它拿连接。
  • 原语层：纯函数工具，与写入无关，单独可用。读取 · 值语义 · 标识 · 溯源。
  • 写入与编排层：记录类型 + 主流程函数。新脚本通常只需要写 SQL + mapper 函数，其余全部交给框架。实体 · 关系 · 主流程。

快速上手：最小的实体抽取脚本

一个实体脚本 = 源 SQL + mapper 函数 + 双入口。mapper 收到一行源数据，返回 0..n 条 EntityRecord：

"""One-entity extractor: Demo（示例）."""

from typing import Any
from script.entity_extractors_one_entity.common import (
    EntityRecord, build_parser, common_args_from_payload,
    configure_logging, extra_json, print_json,
    provenance, run_entity_extractor, text_or_empty,
)

SQL = "SELECT * FROM dwd_demo_table ORDER BY id"

def demo_entity(table: str, row: dict[str, Any], batch: str) -> list[EntityRecord]:
    demo_id = row.get("id")
    if not demo_id:
        return []                       # 缺主键：跳过这一行
    vid = f"demo_{demo_id}"
    props = {
        "name": text_or_empty(row.get("name")),
        "extra_json": extra_json(row),   # 整行源数据快照
        **provenance(table=table, record_id=str(demo_id), ingest_batch=batch),
    }
    return [EntityRecord("Demo", vid, props)]

def build_sources(payload: dict[str, Any]):
    return [("dwd_demo_table", SQL, demo_entity)], None

def main() -> None:
    parser = build_parser(__doc__ or "")
    args = parser.parse_args()
    configure_logging(args.log_level)
    sources, dedupe = build_sources(vars(args))
    print_json(run_entity_extractor(
        database=args.database, batch_size=args.batch_size,
        limit=args.limit, dry_run=args.dry_run,
        ingest_batch=args.ingest_batch, since=args.since,
        dedupe=dedupe, sources=sources,
    ))

def workflow(payload: dict[str, Any]) -> dict[str, Any]:
    # Temporal 入口；payload 与 vars(args) 同形态
    common = common_args_from_payload(payload)
    configure_logging(common["log_level"])
    sources, dedupe = build_sources(payload)
    return run_entity_extractor(
        database=common["database"], batch_size=common["batch_size"],
        limit=common["limit"], dry_run=common["dry_run"],
        ingest_batch=common["ingest_batch"], since=common["since"],
        dedupe=dedupe, sources=sources,
    )

if __name__ == "__main__":
    main()

跑起来：

# 先空跑验证映射（不写图）
$ cd backend
$ uv run python -m script.entity_extractors_one_entity.demo_entity --dry-run --limit 10

# 真跑
$ uv run python -m script.entity_extractors_one_entity.demo_entity --limit 500

# 增量：只抽 updated_time 更新的行
$ uv run python -m script.entity_extractors_one_entity.demo_entity --since 2026-08-01T00:00:00

最小的关系抽取脚本

关系脚本结构完全相同，mapper 返回 EdgeRecord。注意两条铁律：关系脚本一律不建顶点（端点缺失跳过并计数），边的两端 VID 必须用与实体脚本同一套公式（见 标识）：

from script.relation_extractors_one_relation.common import (
    EdgeRecord, edge_provenance, run_relation_extractor,
)

def demo_owns(table: str, row: dict, batch: str) -> list[EdgeRecord]:
    src, dst = row.get("owner_id"), row.get("thing_id")
    if not src or not dst:
        return []
    return [EdgeRecord(
        "OWNS",
        f"demo_{src}",            # 必须与实体侧 VID 公式一致
        f"thing_{dst}",
        {**edge_provenance(source_table=table,
                           source_record_id=f"{src}|{dst}",
                           ingest_batch=batch)},
        source_tag="Demo", target_tag="Thing",  # 端点验存
    )]
完整可运行示例 真实脚本的完整剖析（含 --source 多源选择、rank 模式、matcher 预加载） 见 完整脚本剖析。

设计原则

  • 一实体一脚本 / 一关系一脚本：每个 graph Tag（或边类型）一个入口脚本，脚本是可独立运行的单元，不是配置文件。
  • 幂等可重跑：写入一律走 upsert 语义（merge_node / 带确定性 rank 的 INSERT EDGE / merge_edge），同一批数据跑 N 遍结果一致。
  • 行级容错：单行映射失败只计 invalid，不中断整批；每行 mapper 异常都带 exc_info 落日志。
  • 口径显式化：历史脚本存在两套值语义（机构域「空白→NULL」与论文/专利域「value or ""」），工具集把两套口径都保留并命名清楚，不做隐式统一。
  • 溯源内置：每个点/边自带 source_table / source_record_id / ingest_batch / ingest_time / confidence。
  • 全量行快照：映射不到一等属性的字段进 extra_json，源数据零丢弃。

代码在哪里

模块内容
backend/sdk/kg_sdk.py运行时 Context：五类客户端、watermark、双入口约定
backend/script/entity_extractors_one_entity/common.py实体侧工具集（运行时 + 原语 + 实体写入 + 主流程）
backend/script/relation_extractors_one_relation/common.py关系侧工具集（边写入双通道 + 主流程）
backend/script/relation_extractors_one_relation/resolvers.py端点解析：机构名精确匹配、keyword/paper VID、实体列表解析
backend/script/entity_extractors_one_entity/org_catalog.py机构域源表目录（表名 / 实体类型 / 复合稳定键）
backend/script/entity_extractors_one_entity/mappers.py机构域各实体类型的字段映射函数库
连接方式的差异（重要）

script/*_one_*/common.py 里的 mysql_engine() / graph_client() 读 MYSQL_* / TRS_GRAPH_* 环境变量，适合本机 CLI 与既有调度； 而 kg_sdk.Context 由 Temporal activity 注入连接参数（ctx.mysql / ctx.graph）。 用户上传脚本应优先走 Context；原语层函数（分页 / 值语义 / VID / 溯源）不依赖连接来源，两边通用 —— 写入层需要把 engine/client 作为参数传入而不是自己构造。详见 运行上下文。

路线图（规划中，未实施）

  • ctx 注入版 ETL utils（sdk/etl_utils.py）：把原语层 + 写入层以 ctx.mysql / ctx.graph 为依赖注入的形式暴露给用户上传脚本。
  • 双入口骨架框架（run_dual_mode()）：用一份参数声明同时生成 argparse 与 payload 提取，替代手工镜像的 main()/workflow()。
  • 共享底层模块（script/etl_kit.py）：消除实体包 / 关系包 common.py 之间逐字复制的运行时原语。
  • 观测式访问溯源：SDK 客户端挂钩记录脚本实际访问的表 / tag / collection，随 step 结果回传（见 docs/脚本数据访问溯源设计方案.md，已评审）。
