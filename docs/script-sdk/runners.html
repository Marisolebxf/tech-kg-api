抽取主流程与双入口

run_entity_extractor / run_relation_extractor —— 你只写 SQL 和 mapper，循环、容错、统计全部内置。

主流程函数

run_entity_extractor(*, database, batch_size, limit, dry_run, ingest_batch, sources: list[tuple[table, sql, mapper]], since=None, global_limit=False, dedupe=None, cursor_column=None, extra_params=None) -> dict
run_relation_extractor(*, database, batch_size, limit, dry_run, ingest_batch, sources, since=None, dedupe=None, cursor_column=None, extra_params=None) -> dict

内置的完整循环（两个函数结构对称）：

for table, sql, mapper in sources:            # ① 逐源
    sql = apply_since(sql, since)                # ② 增量注入
    for row in iter_rows(engine, sql, ...):     # ③ 分页
        try:
            mapped = mapper(table, row, batch_id) # ④ 行级容错
        except Exception:
            stats["invalid"] += 1; log.warning(exc_info=True)
            continue
        ...dedupe / 攒批...                       # ⑤ batch_size 攒批写入
# ⑥ engine.dispose()（finally）；返回 summary dict
参数语义
since 对每个源 SQL 注入 updated_time > :since（自动处理 ORDER BY 位置），绑定值自动传
limit 单源行数上限（关系版）；实体版默认也是单源，见 global_limit
global_limit （仅实体）True 时 limit 跨所有源全局生效（旧项目脚本口径：先跑满一个源再跑下一个）
dedupe="first" 实体：同一 VID 首条胜出（旧产业链 setdefault 口径，如 paper-author 的同名作者）；关系：同一 (type, src, dst) 首条胜出
cursor_column keyset 游标分页列（旧专利脚本口径，如 "id"）
extra_params 附加 SQL 绑定参数（如 :table_suffix），随 :since 一起传给 iter_rows
ingest_batch 缺省自动生成 ENTITY_/RELATION_ + UTC 时间戳

sources 声明

sources 是 (表名, SQL, mapper) 三元组列表。表名会同时用作溯源的 source_table 与 summary 的 key —— 用真实表名，不要用别名：

sources = [
    ("dwd_zh_author", "SELECT * FROM dwd_zh_author ORDER BY paper_id, author_id", authored_by),
    ("dwd_en_author", "SELECT * FROM dwd_en_author ORDER BY paper_id, author_id", authored_by),
]

机构域多表共享一个 mapper 时可表驱动生成（表目录在 org_catalog.py）：

sources = [(t, f"SELECT * FROM {t} ORDER BY 1", mapper) for t in PERSON_TABLES]

summary 统计口径

{
  "ingest_batch": "RELATION_20260828T093000Z",
  "sources": {
    "dwd_zh_author": {
      "scanned": 12000,        # 读到的源行数
      "valid": 11800,          # mapper 产出的记录数（含缺主键跳过）
      "written": 11500,        # 实际写图（rank 通道含 merge 更新）
      "updated": 0,            # 实体 merge 保护命中的更新数（关系版无此键）
      "invalid": 12,           # mapper 抛异常的行数
      "missing_source": 280,   # 关系版：端点验存起点缺失
      "missing_target": 8      # 关系版：端点验存终点缺失
    },
    ...
  }
}
invalid 与 missing 的区别

invalid = mapper 抛异常（代码 bug 或极端脏数据，看 warning 日志定位）； missing_* = 记录合法但端点不在图里（多半是实体脚本没先跑，属于编排问题）。 两者都不中断运行 —— 任务结束看 summary 决定是否补跑。

双入口模式：CLI + Temporal

每个脚本同时是（1）可独立调试的 CLI（2）被 Temporal activity 子进程加载的 workflow 函数。 约定用 build_sources(payload) 把「参数 → sources」的决策收成一份，两个入口共享：

def build_sources(payload: dict):
    # payload 既来自 vars(args)（CLI），也来自 Temporal 注入 —— 同形态
    table_choice = payload.get("table", "all")
    tables = TABLES if table_choice == "all" else (table_choice,)
    return [(t, f"SELECT * FROM {t} ORDER BY id", my_mapper) for t in tables]

def main() -> None:                       # CLI 入口
    parser = build_parser(__doc__ or "")   # 通用 7 参数 + 脚本专属参数
    parser.add_argument("--table", choices=("all", *TABLES), default="all")
    args = parser.parse_args()
    configure_logging(args.log_level)
    sources = build_sources(vars(args))          # vars(args) 就是 payload
    print_json(run_relation_extractor(..., sources=sources))

def workflow(payload: dict) -> dict:       # Temporal 入口
    common = common_args_from_payload(payload)   # argparse 的 dict 化镜像
    configure_logging(common["log_level"])
    sources = build_sources(payload)
    return run_relation_extractor(..., sources=sources)

payload 的约定：key 用 snake_case，与 argparse 转换后的 vars(args) 同形态 （--dry-run → dry_run）。这样 build_sources 一份代码两条路径复用。

镜像漂移是当前最大的坑

build_parser 与 common_args_from_payload 是手工互为镜像 —— 新增通用参数要同步改 两个包的两个函数，漏改不会报错，只是 workflow 路径下参数静默失效。规划中的 run_dual_mode() 框架会用一份参数声明生成两条路径（见 路线图）。

预加载编排（matcher 类脚本）

匹配型关系脚本（FUNDED_BY / HAS_OUTPUT / LEADS / HAS_PARTICIPANT）在主流程前有一段 固定编排：收候选 → 加载 matcher → 补 schema → 建报告：

def _prepare(database, tables, batch_size, limit, since, dry_run, batch):
    # ① 连 MySQL 收集候选键（try/finally dispose）
    engine = mysql_engine(database)
    try:
        candidates = collect_organization_candidates(
            engine, tables, batch_size=batch_size, limit=limit, since=since)
    finally:
        engine.dispose()

    # ② 连图加载 matcher；顺带幂等补边 schema（try/finally close）
    graph = graph_client()
    try:
        matcher = ProjectEntityMatcher.from_graph(
            graph, {**EMPTY_CANDIDATES, "organization": candidates})
        if not dry_run:
            ensure_edge_schema(graph, "FUNDED_BY", EDGE_SCHEMA)
    finally:
        graph.close()

    # ③ 复核报告：ambiguous / not_found 进目录供人工复核
    return matcher, ProjectIngestReport(report_dir, ingest_batch=batch,
                                       dry_run=dry_run)

# ④ 主流程结束后：summary 附上报告路径与计数
summary["report_dir"] = str(report.report_dir)
summary["report"] = report.write()
  • 注意 matcher 的连接是预加载阶段独立建/关的 —— 主流程写图时另建连接，两条 try/finally 各管各的。
  • dry_run 下 matcher 照常加载（只读不写），但跳过 ensure_edge_schema。
  • 报告中 matched / ambiguous / not_found / cross_domain 是匹配质量的核心观测指标。

CLI 参数参考

build_parser(description) 提供全部内置脚本的通用 7 参数：

参数默认说明
--log-levelINFO日志级别（httpx 自动压到 WARNING）
--databasegkx_elementMySQL 库名
--batch-size500分页页大小 = 写图攒批阈值
--limit无行数上限（试跑）
--since无增量水位：只抽 updated_time > since 的行
--dry-run关只读源与映射，不写图
--ingest-batch自动显式批次号（幂等重跑/对账）

脚本专属参数（--source、--table、--report-dir 等）在通用参数之后追加， 对应 payload key 直接用参数名（--report-dir → payload["report_dir"]）。
