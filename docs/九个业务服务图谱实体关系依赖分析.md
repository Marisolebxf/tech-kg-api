# 九个业务服务图谱实体关系依赖分析

本文按前端 `frontend/src/views/business-service/service-modules.ts` 中的九个业务服务口径整理。重点说明每个服务要正常工作时需要哪些图谱实体和关系，以及这些实体/关系是从 MySQL 直接抽取，还是在抽取过程中依赖其他实体、关系、索引或对齐结果生成。

## 总体口径

业务服务运行时不直接查 MySQL，而是通过后端业务接口调用图谱查询接口读取 `dev` 图空间。因此这里的“需要”指图数据库中必须已经存在的 Tag/Edge 及其关键属性。

实体抽取有两类：

- 直接抽取实体：从 MySQL 要素库表直接读取并写入图的顶点，例如 `dwd_scholar -> Person`、项目表 -> `Project`、专利表 -> `Patent`、机构表 -> `Organization/Event/News/Product`、产业链表 -> `IndustryChain/IndustryNode`。
- 依赖式抽取关系：关系脚本通常不创建两端实体，只在两端实体已存在、可唯一匹配或高置信对齐后写边。例如项目 `LEADS` 依赖 `Project` 和 `Person` 已存在，专利 `APPLIED_BY` 依赖 `Patent` 与 `Organization/Person` 的匹配结果，产业链 `BELONGS_TO_NODE` 依赖产业链节点和企业实体已存在。

## 公共实体与关系来源

### MySQL 直接抽取的主要实体

| 图实体 | 主要来源表/脚本 | 说明 |
| --- | --- | --- |
| `Person` | `dwd_scholar`，脚本 `load_scholar_entities.py` | 专家/学者节点，合并 `dwd_scholar_talent_flag`、`dwd_scholar_research_direction` 为属性；VID 为 `person_{scholar_id}`。机构 ETL 也会为高管、法定代表人、受益人等生成角色型 Person，但不做全局学者消歧。 |
| `Organization` | 国内外机构要素库，脚本 `organization_entity_etl.py` 等 | 企业、机构、研究院、高校等；VID 通常为 `org_{源机构ID}`，多源属性可能合并到 `extra_json`。 |
| `Project` | `dwd_zh_project`、`dwd_en_project`，脚本 `load_project_graph.py` | 项目节点，VID 为 `project_{id}`，包含项目标题、经费、周期、批准时间、成果计数等。 |
| `Paper` | 中文/外文论文要素库及论文期刊 ETL | 论文节点，供署名、合作成果、论文合作服务使用。 |
| `Patent` | 全球专利要素库，脚本 `load_patent_graph.py` | 专利节点，并生成关键词/专利族等相关实体属性或节点。 |
| `Report` | 中文/外文报告要素库 | 报告节点，主要作为项目成果或全景成果展示。 |
| `Keyword` | 项目/专利/论文等 ETL | 关键词节点，项目 ETL 可按规范化文本创建。 |
| `Event` | 机构风险、财务、融资、招聘、工商变更、招投标、司法等表 | 机构事件节点，VID 通常为 `event_{source_table}_{source_record_id}`。 |
| `News` | `dwd_org_important_news_info`、产业资讯等表 | 资讯节点，VID 通常为 `news_{source_table}_{source_record_id}`。 |
| `Product` | 机构产品表 | 产品节点，用于企业技术方向、经营范围、背景展示。 |
| `IndustryChain` / `IndustryNode` | 产业链要素库，脚本 `load_industry_chain_graph.py` | 产业链及链节点，支撑产业链全景和 TOP-N 事件服务。 |

### 依赖其他实体/关系抽取的主要关系

| 图关系 | 方向 | 抽取来源与依赖 |
| --- | --- | --- |
| `AFFILIATED_WITH` | `Person -> Organization` | 学者关系脚本从 `dwd_scholar` 抽取任职机构，依赖 `Person` 已存在；机构端优先用 `scholar_org_id`，否则按机构名生成桩节点，后续依赖 Milvus/机构对齐认领到真实 `Organization`。 |
| `COAUTHOR_WITH` | `Person <-> Person` | 从 `dwd_scholar_coauthor` 抽取，依赖两端 `Person` 已存在，属性含 `co_paper_count`、置信度和溯源。 |
| `AUTHORED_BY` | `Paper -> Person` | 论文领域或学者关系兜底从 `dwd_scholar_paper_relation` 等抽取，依赖 `Paper`、`Person` 已存在。 |
| `INVENTED_BY` | `Patent -> Person` | 专利关系脚本从专利发明人字段抽取，依赖 `Patent` 与可匹配的 `Person`，不确定候选进入复核。 |
| `APPLIED_BY` / `OWNED_BY` | `Patent -> Organization/Person` | 专利申请人/权利人抽取，依赖 `Patent` 与申请人/权利人实体匹配；可使用向量对齐，低置信进入复核。 |
| `CITES` | `Patent -> Patent` | 专利引用抽取，依赖引用目标专利能匹配到图中 `Patent`。 |
| `OUTPUT_OF` | `Patent/Paper/Report -> Project` 或相关成果链路 | 专利/成果与项目关联，依赖成果与项目实体匹配。 |
| `FUNDED_BY` | `Project -> Organization` | 项目 ETL 从 `funded_institution` 抽取，依赖已存在 `Project` 和唯一匹配的 `Organization`。 |
| `LEADS` | `Project -> Person` | 项目 ETL 从 `project_host` 抽取，依赖 `Project` 与唯一匹配的 `Person`。 |
| `HAS_PARTICIPANT` | `Project -> Person` | 项目 ETL 展开 `participants`，依赖 `Project` 与唯一匹配的 `Person`。 |
| `HAS_KEYWORD` | `Project -> Keyword` | 项目 ETL 展开关键词，允许创建 `Keyword`。 |
| `HAS_OUTPUT` | `Project -> Paper/Patent/Report` | 项目 output JSON 解析成果，依赖成果实体按 DOI、标题、专利号等唯一匹配。 |
| `LEGAL_REP_OF` / `EXECUTIVE_OF` / `SHAREHOLDER_OF` / `BENEFICIAL_OWNER_OF` / `ACTUAL_CONTROLLER_OF` | `Person/Organization -> Organization` | 机构关系 ETL 从法定代表人、高管、股东、受益人、实控人表抽取；依赖机构实体存在或高置信对齐，人员端按角色和来源字段生成稳定 VID。 |
| `INVESTS_IN` / `ACQUIRES` / `SUBSIDIARY_OF` | `Organization -> Organization` | 机构关系 ETL 从投资、并购、子公司表抽取；依赖两端 Organization 已存在或可高置信对齐。 |
| `INVOLVED_IN` | `Organization -> Event` | 机构关系 ETL 从财务、风险、融资、工商、司法、招投标等事件表抽取；依赖 `Organization` 与 `Event` 已存在。 |
| `HAS_NEWS` | `Organization -> News` | 机构关系 ETL 或产业链 ETL 连接机构和资讯；依赖 `Organization` 与 `News` 已存在。 |
| `PRODUCES` | `Organization -> Product` | 机构产品关系，依赖 `Organization` 与 `Product` 已存在。 |
| `HAS_NODE` / `CHILD_OF` / `DOWNSTREAM_OF` / `COVERS_CHAIN` | `IndustryChain/IndustryNode` 之间 | 产业链 ETL 从产业链要素库抽取链、节点、层级和上下游关系。 |
| `BELONGS_TO_NODE` | `Organization -> IndustryNode` | 产业链 ETL 抽取企业与产业链节点关联，依赖 `Organization` 和 `IndustryNode`，常带 `chain_score`。 |

## 1. 科技专家/人才直接关系

### 正常工作所需实体和关系

- 必需实体：`Person`。
- 必需关系：`COAUTHOR_WITH`。
- 关键属性：`Person.name_zh/name_en/scholar_org/research_fields`，`COAUTHOR_WITH.co_paper_count/relation_time/confidence/match_evidence`。
- 可增强实体/关系：`Paper` + `AUTHORED_BY`、`Patent` + `INVENTED_BY`、`Project` + `LEADS/HAS_PARTICIPANT`、`Organization` + `AFFILIATED_WITH`。当前直接关系服务主查询使用 `COAUTHOR_WITH`，增强信息主要用于解释“共论文/共项目/共专利/同机构”等摘要。

### 抽取方式

- `Person` 由 `dwd_scholar` 直接抽取。
- `COAUTHOR_WITH` 由 `dwd_scholar_coauthor` 抽取，依赖双方 `Person` 已写入图。
- 任职机构信息由 `AFFILIATED_WITH` 补充，来自 `dwd_scholar`，依赖 `Person` 与 `Organization` 或机构桩节点；真实机构对齐依赖 Milvus/机构索引。

## 2. 科技单节点间接关系

### 正常工作所需实体和关系

- 必需实体：作为核心节点的 `Person`，以及多跳路径上可达的 `Person/Organization/Project/Paper/Patent/Event/IndustryNode` 等。
- 必需关系：至少需要一批可遍历的直接关系边，如 `COAUTHOR_WITH`、`AFFILIATED_WITH`、`AUTHORED_BY`、`INVENTED_BY`、`LEADS`、`HAS_PARTICIPANT`、`FUNDED_BY`、`APPLIED_BY`、`INVOLVED_IN`、`BELONGS_TO_NODE`。
- 关键属性：边类型、边置信度、节点标签、路径深度、业务侧配置的关系类型过滤条件。

### 抽取方式

- 本服务不产生新实体或新边，只依赖已入图的直接关系做 2 至 3 跳路径分析。
- 学术关联主要依赖 `COAUTHOR_WITH/AUTHORED_BY`。
- 机构关联主要依赖 `AFFILIATED_WITH` 及机构层级边 `SUBSIDIARY_OF/PART_OF/BELONGS_TO`。
- 项目关联主要依赖 `Project` 及 `LEADS/HAS_PARTICIPANT/FUNDED_BY/HAS_OUTPUT`。

## 3. 科技两点合作成果

### 正常工作所需实体和关系

- 必需实体：两个 `Person`。
- 成果实体：`Paper`、`Patent`、`Project`，奖项目前更多来自项目 output 计数或成果字段，不是独立强依赖。
- 必需关系：`AUTHORED_BY`、`INVENTED_BY`、`LEADS`、`HAS_PARTICIPANT`。
- 关键属性：成果标题、时间字段、领域字段、引用/产出计数字段，以及连接边的溯源和置信度。

### 抽取方式

- `Person` 从 `dwd_scholar` 直接抽取。
- `Paper` 从论文要素库直接抽取，`AUTHORED_BY` 依赖 `Paper` 与 `Person` 已存在后由论文/学者关系脚本写入。
- `Patent` 从全球专利要素库直接抽取，`INVENTED_BY` 依赖专利发明人与图中 `Person` 的匹配。
- `Project` 从中外项目表直接抽取，`LEADS/HAS_PARTICIPANT` 依赖项目负责人、参与人名称与已有 `Person` 唯一匹配。
- 服务运行时分别取两位专家邻接成果，再求交集或共同项目关系。

## 4. 科技专家同事关系

### 正常工作所需实体和关系

- 必需实体：`Person`、`Organization`。
- 必需关系：`AFFILIATED_WITH`。
- 增强关系：`COAUTHOR_WITH`、机构层级边 `SUBSIDIARY_OF/PARENT_OF/PART_OF/BELONGS_TO`、成果边 `AUTHORED_BY/INVENTED_BY/LEADS/HAS_PARTICIPANT`。
- 关键属性：`AFFILIATED_WITH.work_experience_date/work_experience_department_zh/work_experience_position_zh/organization_base/organization_id/confidence`。

### 抽取方式

- `Person` 从 `dwd_scholar` 直接抽取。
- `Organization` 从机构要素库直接抽取；没有稳定机构 ID 的学者任职关系先连到机构名桩节点。
- `AFFILIATED_WITH` 从 `dwd_scholar` 的机构、部门、职位、任职时间字段抽取，依赖 `Person` 和机构端点。
- 机构层级边从机构关系 ETL 抽取，依赖两端 `Organization` 已存在或高置信对齐。
- 服务通过共同机构、共同部门、任职时间重叠判断同事关系，并用共同论文/项目/专利作为证据增强。

## 5. 科技专家校友关系

### 正常工作所需实体和关系

- 必需实体：`Person`。
- 必需属性：`Person.education_background_date`、`education_background_institution_zh/en`、`education_background_degree_zh/en`。
- 增强关系：`COAUTHOR_WITH`、`AUTHORED_BY`、`INVENTED_BY`、`LEADS`、`HAS_PARTICIPANT`，用于生成互动摘要。
- 可选实体：若后续将学校建成 `Organization`，可用 `AFFILIATED_WITH` 或教育类关系增强；当前服务主要读取 `Person` 属性。

### 抽取方式

- 教育经历不是单独关系，随 `Person` 从 `dwd_scholar` 直接抽取为属性。
- 校友关系由服务实时推理，不写入图。判断依据包括同校、同学历、同期或时间区间重叠。
- 互动摘要依赖已存在的共同论文、专利、项目和合作者关系。

## 6. 科技专家论文合作关系

### 正常工作所需实体和关系

- 必需实体：`Person`、`Paper`。
- 必需关系：`AUTHORED_BY`；可用 `COAUTHOR_WITH` 做快速统计或兜底。
- 关键属性：论文标题、发表时间、期刊/会议、主题/关键词、引用数，作者关系的引用数、署名等属性。
- 增强实体/关系：`Journal` 或期刊属性、`Keyword`、论文引用关系、机构关系 `AFFILIATED_WITH`。

### 抽取方式

- `Person` 从 `dwd_scholar` 直接抽取。
- `Paper` 从中文/外文论文要素库直接抽取。
- `AUTHORED_BY` 从论文作者表或 `dwd_scholar_paper_relation` 抽取，依赖 `Paper` 与 `Person` 已存在。
- `COAUTHOR_WITH` 从 `dwd_scholar_coauthor` 抽取，可作为论文合作边的聚合视图；真实论文级证据仍依赖 `Paper - AUTHORED_BY - Person` 链路。

## 7. 重点关注科技企业关系

### 正常工作所需实体和关系

- 必需实体：`Person`、`Organization`。
- 项目/专利合作实体：`Project`、`Patent`。
- 治理类关系：`EXECUTIVE_OF`、`LEGAL_REP_OF`、`ACTUAL_CONTROLLER_OF`、`BENEFICIAL_OWNER_OF`、`SHAREHOLDER_OF`、`AFFILIATED_WITH`。
- 项目合作关系：`HAS_PARTICIPANT`、`LEADS`、`FUNDED_BY`，以及部分路径可能使用 `PARTICIPATES_IN`。
- 专利合作关系：`INVENTED_BY`、`APPLIED_BY`。
- 风险背景关系：`INVOLVED_IN`，用于首要企业风险提示。
- 关键属性：企业名称、上市状态/股票代码、行业、注册资本、成立年、主营产品、边上的职位/角色/时间，很多企业背景字段需要从 `Organization.extra_json` 摊平读取。

### 抽取方式

- `Organization` 由机构实体 ETL 从机构要素库直接抽取，多源字段合并。
- 治理关系由机构关系 ETL 从法定代表人、高管、股东、受益人、实控人等表抽取，依赖企业端 `Organization` 已存在；人员端可能是机构领域生成的角色型 `Person`，也可能与专家 `Person` 通过稳定 ID 或名称匹配产生可达路径。
- 项目合作依赖 `Project` 直接抽取后，再由 `LEADS/HAS_PARTICIPANT/FUNDED_BY` 连接专家、项目和企业。
- 专利合作依赖 `Patent` 直接抽取后，再由 `INVENTED_BY/APPLIED_BY` 连接专家、专利和企业。
- 风险提示依赖机构事件 `Event` 与 `INVOLVED_IN`，事件实体来自机构事件表，关系依赖企业与事件实体都已存在。

## 8. 科技产业链点 TOP-N 事件关系

### 正常工作所需实体和关系

- 必需实体：`IndustryNode`、`IndustryChain`、`Organization`、`Event`、`News`。
- 必需关系：`BELONGS_TO_NODE`、`HAS_NODE`、`INVOLVED_IN`、`HAS_NEWS`。
- 专家增强关系：`EXECUTIVE_OF`，用于从 TOP 事件企业补查关联专家。
- 关键属性：`BELONGS_TO_NODE.chain_score`，事件类型、发生时间、金额、事件标题/描述，企业名称，新闻时间和标题。

### 抽取方式

- `IndustryChain/IndustryNode` 从产业链要素库直接抽取。
- `BELONGS_TO_NODE` 由产业链 ETL 抽取企业与链节点关系，依赖 `Organization` 和 `IndustryNode` 已存在，关系属性带链上强度。
- `Event/News` 从机构事件、机构资讯、产业资讯等表直接抽取。
- `INVOLVED_IN/HAS_NEWS` 由机构关系 ETL 或产业链 ETL 连接企业与事件/资讯，依赖两端实体已存在。
- `EXECUTIVE_OF` 由机构关系 ETL 从高管表抽取，依赖专家/人员节点和企业节点。

## 9. 科技产业链全景图

### 正常工作所需实体和关系

- 必需实体：`IndustryChain`、`IndustryNode`。
- 四层展示实体：核心技术可由 `Keyword/IndustryNode/Product/Patent` 表达，领军企业为 `Organization`，领军专家为 `Person`，代表成果为 `Paper/Patent/Project/Report`。
- 必需关系：`HAS_NODE`、`CHILD_OF`、`DOWNSTREAM_OF`、`COVERS_CHAIN`、`BELONGS_TO_NODE`。
- 跨域增强关系：企业与事件 `INVOLVED_IN/HAS_NEWS`，专家与成果 `AUTHORED_BY/INVENTED_BY/LEADS/HAS_PARTICIPANT`，企业与专利/项目 `APPLIED_BY/FUNDED_BY/PARTICIPATES_IN`，企业产品 `PRODUCES`。
- 关键属性：产业链节点名称、层级、上下游方向、企业 `chain_score`、专家论文/引用/h-index、成果时间和影响力指标。

### 抽取方式

- 产业链和链节点由产业链 ETL 直接从产业链要素库抽取。
- 链内结构边 `HAS_NODE/CHILD_OF/DOWNSTREAM_OF/COVERS_CHAIN` 由产业链 ETL 直接生成，依赖链和节点实体。
- 企业挂链 `BELONGS_TO_NODE` 依赖企业实体和链节点实体。
- 领军专家、代表成果、核心技术不是一个单独抽取结果，而是全景服务基于已有跨域实体和关系按标签、关键词、影响力指标、子图邻接实时筛选排序。

## 按服务汇总依赖矩阵

| 服务 | 最小可用实体 | 最小可用关系 | 增强依赖 |
| --- | --- | --- | --- |
| 科技专家/人才直接关系 | `Person` | `COAUTHOR_WITH` | `Paper/Patent/Project/Organization` 与成果、任职边 |
| 科技单节点间接关系 | `Person` 及路径邻居 | 任意可遍历业务边 | 多域实体越完整，间接路径越丰富 |
| 科技两点合作成果 | `Person`、`Paper/Patent/Project` | `AUTHORED_BY/INVENTED_BY/LEADS/HAS_PARTICIPANT` | `HAS_OUTPUT`、成果影响力字段 |
| 科技专家同事关系 | `Person`、`Organization` | `AFFILIATED_WITH` | `COAUTHOR_WITH`、成果边、机构层级边 |
| 科技专家校友关系 | `Person` | 无硬性图边，依赖教育经历属性 | `COAUTHOR_WITH`、成果边 |
| 科技专家论文合作关系 | `Person`、`Paper` | `AUTHORED_BY` 或 `COAUTHOR_WITH` | 期刊、关键词、引用、机构 |
| 重点关注科技企业关系 | `Person`、`Organization` | 治理边、项目边、专利边之一 | `INVOLVED_IN`、企业 `extra_json` 背景字段 |
| 科技产业链点 TOP-N 事件关系 | `IndustryNode`、`Organization`、`Event/News` | `BELONGS_TO_NODE/INVOLVED_IN/HAS_NEWS` | `HAS_NODE`、`EXECUTIVE_OF` |
| 科技产业链全景图 | `IndustryChain`、`IndustryNode` | `HAS_NODE/CHILD_OF/DOWNSTREAM_OF/BELONGS_TO_NODE` | 企业、专家、成果、事件全域关系 |

## 建议的入图先后顺序

1. 机构域实体：先建立 `Organization/Event/News/Product` 等基础节点。
2. 学者域实体：写入 `Person`。
3. 论文、专利、项目、报告等成果实体。
4. 学者关系：`AFFILIATED_WITH/COAUTHOR_WITH/AUTHORED_BY`。
5. 机构关系：治理、投资、层级、事件、资讯、产品关系。
6. 专利关系：`INVENTED_BY/APPLIED_BY/OWNED_BY/CITES/OUTPUT_OF`。
7. 项目关系：`FUNDED_BY/LEADS/HAS_PARTICIPANT/HAS_KEYWORD/HAS_OUTPUT`。
8. 机构对齐、学者消歧、向量索引等依赖型修正任务。
9. 产业链实体和关系：`IndustryChain/IndustryNode`、链内结构和企业挂链关系。

如果只为了九个业务服务可用，最关键的验收点是：`Person`、`Organization`、`Paper`、`Patent`、`Project`、`IndustryNode`、`Event/News` 七类实体必须有数据；`COAUTHOR_WITH`、`AFFILIATED_WITH`、`AUTHORED_BY`、`INVENTED_BY`、`LEADS/HAS_PARTICIPANT/FUNDED_BY`、治理类企业边、`BELONGS_TO_NODE`、`INVOLVED_IN/HAS_NEWS` 必须能被图查询接口查到。
