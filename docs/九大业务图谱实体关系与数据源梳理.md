# 九大业务图谱实体关系与数据源梳理

> 基于代码调研(2026-09),所有结论均标注 `file:line`,可按行号核对。

##〇、数据流总架构

```
gkx_element (要素库,只读) ──┐
gkx_local (业务库,只读)  ──┤  离线 ETL 脚本(backend/script/load_*.py)
默认库 (MYSQL_DATABASE,    │      │
        默认 gkx_element) ─┘      ▼
                        NebulaGraph dev 空间
                        (经 trs-graph-service REST 访问)
                               │  TRSGraphClient / graph-search API
                               ▼
                    九大业务(运行时大多只查图,不直连 MySQL)
                               + LLM 合成(企业背景/关系挖掘)
```

- **图空间**:业务几乎全部跑在 **dev** 空间(`TRS_GRAPH_SPACE` 默认 dev);techkg 空间只有旧版 `script/load_graph.py` 在用。
- **运行时 vs 离线**:九大业务中 7 个**纯查图**;例外是企业关系子系统——`expert_enterprise_relation`/`expert_enterprise_mining` 图缺节点时从 **gkx_local** 补点,`enterprise_background_analysis` 完全不查图(纯 MySQL+LLM)。
- **溯源三要素**(sourceTable/sourceField/graphVid)是每个响应的标准字段,来源要么是图节点自身的 `source_table` 属性,要么是硬编码常量。
- **三个 MySQL 源库**:
  - `gkx_element`(要素库):几乎所有 ETL 的主源,图的血缘所在(`infra/gkx_element.py`)。
  - `gkx_local`(业务库):运行时业务查询用,仅企业关系子系统直查(`infra/gkx.py`)。
  - 默认库(`MYSQL_DATABASE`,默认 gkx_element):`load_graph.py`/`load_project_graph.py` 等经 `get_mysql_client()` 使用。
  - ⚠️ `dwd_scholar`、`dwd_org_base_info` 等同名表在 gkx_element 与 gkx_local 中**都存在**。

## 二、分业务详述

### 1. 科技专家/人才直接关系(`service/expert_direct_relation.py`)

- **图用法**:`search_nodes(label="Person")` 按 name_zh/name_en 定位专家(VID 约定 `person_{scholar_id}`)→ `get_node_edges(a, edge_type="COAUTHOR_WITH", limit=100)` → 按 `co_paper_count` 降序去重 → 机构(节点属性子串)/时间(边属性 `relation_time`)过滤。
- **业务输出**:单专家 = 合作关系列表(`relationStrength = min(99, 60+log1p(共文数)×10)`);双专家 = 验证二人是否有直接合著边。
- **数据源**:`Person` ← `gkx_element.dwd_scholar`(`script/load_scholar_entities.py`);`COAUTHOR_WITH` ← `gkx_element.dwd_scholar_coauthor`(`script/load_scholar_relations.py`)。
- ⚠️ 可核实差异:代码读边属性 `relation_time`(`expert_direct_relation.py:392`),但学者域 schema(`script/init_scholar_schema.py:116-120`)的 `COAUTHOR_WITH` 并无此属性,时间筛选实际基本退化(无法解析即排除)。

### 2. 科技单节点间接关系(`service/expert_indirect_relation_api.py`)

- **图用法**:`get_subgraph(core, depth=2~3, limit=200, 双向)` 一次性拉全类型子图,之后**纯 Python 做路径推理**:
  - DFS 枚举节点不重复的简单路径(候选 ≤1000、结果 ≤50,`MAX_CANDIDATE_PATHS`/`MAX_RESULT_PATHS`);
  - 边强度:边属性 confidence/score → `co_paper_count` 对数归一(`0.6 + log1p(x)/log1p(200)*0.35`,封顶 0.95)→ 默认权重表兜底 0.75;
  - 路径强度 = 边强度几何平均 × `0.92^(跳数-1)`;
  - 默认权重表 `DEFAULT_EDGE_WEIGHTS`:`COAUTHOR_WITH:0.84, AFFILIATED_WITH:0.88, EMPLOYED_BY:0.9, PARTICIPATES_IN/HAS_PARTICIPANT:0.86, INVENTED_BY:0.88, AUTHORED_BY:0.86, PUBLISHED_IN:0.8, CITES/CITED_BY:0.72`。
- **关系分组**(用于路径归类,`RELATION_GROUPS`):
  - 学术:`COAUTHOR_WITH/AUTHORED_BY/CITES/CITED_BY/PUBLISHED_IN/HAS_KEYWORD/RELATED_TO`
  - 机构:`AFFILIATED_WITH/EMPLOYED_BY/EXECUTIVE_OF/LEADS/MEMBER_OF_FAMILY`
  - 项目:`PARTICIPATES_IN/HAS_PARTICIPANT/FUNDED_BY/OUTPUT_OF/HAS_OUTPUT`
  - 专利:`INVENTED_BY/APPLIED_BY/BELONGS_TO_NODE`
  - 产业:`INVESTS_IN/SHAREHOLDER_OF/SUBSIDIARY_OF/ACQUIRES/ACTUAL_CONTROLLER_OF/BENEFICIAL_OWNER_OF/PRODUCES`
- **数据源**:即图中全部域,见第三节映射总表。

### 3. 科技两点合作成果(`service/expert_cooperation_achievement.py`)

- **图用法**:两名专家各拉 500 条双向边(`get_node_edges(direction="both", limit=500)`,不带 edge_type,Python 侧按 `edge.type` 分拣)→ **同类邻居集合求交 = 共同成果**(`AUTHORED_BY`→论文、`INVENTED_BY`→专利、`LEADS/HAS_PARTICIPANT`→项目)→ 每类取前 `limitPerType`,`get_node` 组装标题/时间/领域(优先 `HAS_KEYWORD`→`Keyword` 节点)/奖项。
- **业务输出**:汇总 + `coreContribution`(共同专利/项目/论文 Top2)+ `cooperationMode` 规则分类(时间跨度≥3 年且总量≥3 → 长期稳定型;单类型;多类型)。
- **数据源**:
  - `Paper`+`AUTHORED_BY` ← `dwd_zh_paper/dwd_en_paper` + `dwd_zh_author/dwd_en_author`;
  - `Patent`+`INVENTED_BY` ← `dwd_patent`;
  - `Project`+`LEADS/HAS_PARTICIPANT` ← `dwd_zh_project/dwd_en_project`;
  - `HAS_KEYWORD` ← 论文分类/专利 keywords/项目 keywords;
  - 奖项读 `Project.output_awards`(JSON,源自 `dwd_*_project_output`)。
  - 均 gkx_element,经 `load_paper_journal_graph.py`/`load_patent_*.py`/`load_project_graph.py`。

### 4. 科技专家同事关系(`service/expert_colleague_relation.py` + `application/expert_colleague_relation.py`)

唯一"写回图"的推理模块。

- **图用法**:
  1. 并行 3 个一跳子图(`AFFILIATED_WITH` out / `COAUTHOR_WITH` both / 全类型上下文);
  2. 任职机构经层级边(`SUBSIDIARY_OF/PARENT_OF/PART_OF/BELONGS_TO`)扩上下级;
  3. 对每个机构反查 `AFFILIATED_WITH` **入边**得候选同事;
  4. 双方任职时间段(边属性 `work_experience_date` 等)按月序号(`year*12+month`)求交集 + 部门归一(`work_experience_department_zh` 等)+ 共享 Team/成果节点。
- **业务输出+写图**:置信度打分(同机构 0.42 + 时长 ≤0.22 + 同部门 0.12 + 合著 ≤0.12 + 团队 0.05 + 成果 ≤0.05,封顶 0.98),然后 **`CREATE EDGE IF NOT EXISTS COLLEAGUE`** 并 upsert 写回图(`application/expert_colleague_relation.py:182-249`,端点 `sorted((a,b))` 规范方向)。
- **数据源**:`AFFILIATED_WITH` ← `gkx_element.dwd_scholar`(scholar_org_id、work_experience_*);`COAUTHOR_WITH` ← `dwd_scholar_coauthor`;`COLLEAGUE` 为本模块推理产物(非 ETL)。

### 5. 科技专家校友关系(`service/expert_alumni_relation.py`,只读)

- **图用法**:
  1. 教育经历从 **Person 节点属性**解析(`education_background_institution_zh/_en`、`education_background_degree_zh/_en`、`education_background_date` + JSON blob);
  2. `STUDIED_AT` 出边找院校节点 → 院校 `STUDIED_AT` **入边**反查同校专家;
  3. 兜底 nGQL:`MATCH (v:Organization) RETURN …`(校名索引,60s TTL)/ `LOOKUP ON Person WHERE Person.education_background_institution_zh == "…"`(专用索引 `person_edu_inst_zh_idx/_en_idx`);
  4. 匹配后用 `COAUTHOR_WITH/AUTHORED_BY/INVENTED_BY/LEADS/HAS_PARTICIPANT` 统计互动。
- **业务输出**:维度 = 同校(必要,NFKC 归一后相等或互含)+ 同学历 + 同期(教育年份交集);互动 = 合著直连 + 共同论文/专利/项目计数。无置信度字段。
- **数据源**:Person 教育属性 + `STUDIED_AT` ← `gkx_element.dwd_scholar`(education_background_*,边上 `source_table="dwd_scholar"`)。

### 6. 科技专家论文合作关系(`service/expert_paper_cooperation_api.py`)

- **图用法**:
  1. **两跳路径 nGQL**(graph-search `paths/search` 编译):`(A)-[:AUTHORED_BY]->(Paper)<-[:AUTHORED_BY]-(B) WHERE publication_year BETWEEN …`(dev 空间;techkg 空间为 `Scholar-[AUTHORED]->Paper` 反向),分页拉 ≤1000 篇共同论文;
  2. 每篇论文并发一跳子图取 `PUBLISHED_IN`(期刊)/`HAS_KEYWORD`(主题)/`CITED_BY`(被引);
  3. 期刊分级 / 主题 Top8 / 被引统计 → `academicImpactScore = min(99.5, 论文数×6.5 + 总被引/max(18,论文数×3) + 已分级数×4)`;
  4. 无时间条件且无路径时回退 `COAUTHOR_WITH` 一/二跳路径(读 `co_paper_count`);
  5. 合作者不足 3 时读 `PAPER_COOPERATED_WITH` 边的 `structured_result` JSON 补核心合作者。
- **数据源**:`Paper` ← `dwd_zh_paper/dwd_en_paper`;`AUTHORED_BY` ← `dwd_zh_author/dwd_en_author`;`PUBLISHED_IN` ← `dwd_zh_journal/dwd_en_journal` + `publication_id`;`CITES/CITED_BY` ← `dwd_*_paper_reference/citation`;`HAS_KEYWORD` ← `dwd_*_paper_classification`。
- 备注:`PAPER_COOPERATED_WITH` 边只在读取处出现,**本仓库无写入代码**(注释称由 MySQL 数据构建);`expert_paper_cooperation.py`(MySQL demo 版,直查 gkx_local 7 张表:`dwd_scholar`、`dwd_scholar_research_direction`、`dwd_scholar_coauthor`、`dwd_scholar_paper_relation`、`dwd_scholar_papers`、`dwd_en_journal`、`dwd_zh_journal`)未挂路由,仅保留。

### 7. 重点关注科技企业关系(4 个协作模块)

**主入口** `tech_enterprise_relation_business.py`(`/kg-service/key-enterprise-relation`,纯查图,经 graph-search `filtered-subgraph` 拉专家子图,按 12 种边归类):

| 类别 | 边类型 | 方向 | 置信度 |
|---|---|---|---|
| 治理 | `EXECUTIVE_OF`/`LEGAL_REP_OF`/`ACTUAL_CONTROLLER_OF`/`BENEFICIAL_OWNER_OF`/`SHAREHOLDER_OF`/`AFFILIATED_WITH` | Person→Organization | 0.9 |
| 项目 | `HAS_PARTICIPANT`/`LEADS`(Person→Project)、`PARTICIPATES_IN`/`FUNDED_BY`(Project→Organization) | — | 0.8 |
| 专利 | `INVENTED_BY`(Patent→Person)、`APPLIED_BY`(Patent→Organization) | — | 0.8 |
| 风险 | `INVOLVED_IN`(Organization→`Event`,命中 11 类风险 event_type:bankruptcy/zhixing/shixin/tax_punish/judicial_case/illegal/equity_freeze/judicial_sale/abnormal/pledge/chattel) | depth=1 | — |

再按角色关键词分 L1/L2/L3、过滤重点科技企业(排除高校/研究院/政府/MOCK)、从 `Organization.extra_json` 摊平企业背景(org ETL 把 base_info/product 等多表数据塞进 extra_json)。

**构建** `expert_enterprise_relation.py`:写 `Scholar`/`Organization` 节点 + `EMPLOYED_BY` 边(rank@0,`relation_type` 英文码 `/` 合并:employment/advisor/rd_cooperation/project_cooperation/tech_cooperation,响应时映射中文);多边合并去重,rank≠0 旧边删除;图缺节点从 **gkx_local** 的 `dwd_scholar`/`dwd_org_base_info`/`dwd_org_stock_base` 补点。

**标注** `relation_detail_annotation.py`:`get_edge` + `update_edge` 补 `EMPLOYED_BY` 的 role/tech_field/start_date/end_date;角色码表 chief_scientist/cto→L1、technical_advisor/rd_lead→L2、engineer→L3。

**背景分析** `enterprise_background_analysis.py`:**不查图**,纯 gkx_local 9 张表 + LLM 合成三维度(行业地位/核心技术/经营财务)结论,LLM 失败降级模板:
`dwd_org_base_info`、`dwd_org_stock_base`、`dwd_org_org_product_info`、`dwd_org_tag_info`、`dwd_org_industry_chain_dtl`、`dwd_org_industry_chain_prod_dtl`、`dwd_org_stock_finance_info`、`dwd_org_annual_financial_info`、`dwd_patent`(CPC 分布)。

**挖掘** `expert_enterprise_mining.py`:LLM 从 `dwd_scholar` 传记抽企业(失败降级正则)→ `SHOW TABLES` 扫 gkx_local 约 31 张含 org_id 的 `dwd_org_*` 表建候选池 → 剥公司后缀 + rapidfuzz(阈值 85)消歧 → 编排依次调 build/annotate/analyze。

### 8. 科技产业链点 TOP-N 事件(`service/industry_node_top_events_business.py`)

- **图用法**:
  1. 产业链节点(`node_{id}`)一跳子图取 `BELONGS_TO_NODE`(带 `chain_score`)的链上企业 + `HAS_NODE` 取链名;
  2. 企业按 `chain_score` 降序,默认取 ≤max_orgs(20),指定 event_type 时扩至 200 家;
  3. 每企业并行拉 `INVOLVED_IN`(→`Event`)/`HAS_NEWS`(→`News`)子图(News 统一记 `event_type="news"`);
  4. 事件按类型精确等值/年月(`occur_date[:7]`)过滤,按 event_id 去重保留 chain_score 高者;
  5. **影响力分** = 事件权重(破产/失信/执行/股权冻结 3.0、融资 2.0、新闻 1.0 等 `EVENT_WEIGHT` 表)× 金额对数 × 新近度 × 链分;
  6. TOP-N + 风险等级(命中 `RISK_EVENT_TYPES`→高;融资/财务→中;否则低)及分级置信度(高 0.9/中 0.75/低 0.6);
  7. TOP 事件企业反查治理边(`EXECUTIVE_OF`/`LEGAL_REP_OF`/`ACTUAL_CONTROLLER_OF` **入边**)关联专家。
- **数据源**:`IndustryChain`/`IndustryNode`/`HAS_NODE`/`CHILD_OF`/`DOWNSTREAM_OF` ← `dwd_industry_chain_info`;`BELONGS_TO_NODE` ← `dwd_org_industry_chain_dtl`;`News` ← `dwd_industry_chain_news_info`/`dwd_org_important_news_info`;`Event`/`INVOLVED_IN` ← 15 张财务/风险/招投标表;治理边 ← `dwd_org_executive_info` 等(均 gkx_element)。

### 9. 科技产业链全景图(`service/industry_chain_panorama.py`)

- **四层实体模型**:

| layer | 标签 | 名称属性 | 指标属性 |
|---|---|---|---|
| 核心技术 | `Keyword`, `IndustryNode` | keyword/node_name/name | citation_nums |
| 领军企业 | `Organization` | name_cn/name_en/name | paper_nums |
| 领军专家 | `Person` | name_zh/name_cn/name_en | h_index |
| 代表成果 | `Paper`, `Patent`, `Project` | title_zh/title_en/title/title_original | citation_nums |

- **图用法流程**:关键词归一(预置"人工智能/集成电路"等别名)→ anchor 解析(anchorId > 预置热点提示 > `IndustryNode`→`IndustryChain`→`Keyword` 通用序,唯一命中才生效)→ 各层 `find_nodes` 属性精确等值(未命中且属可扫描标签 `{IndustryNode, IndustryChain, Keyword}` 时退化为单页 50 条扫描+本地包含匹配)→ 种子选取(偏好序 专家>企业>技术,≤6 个)→ 多种子 `get_subgraph(depth, limit=60)` 合并去重 → `relationTypes` 过滤边并去孤立点 → 边置信度取 `confidence` 或 `chain_score/100`。
- **数据源**:同 8 + 论文/专利/项目/学者各域(见下节)。

## 四、值得注意的点

1. **两库同名表**:`dwd_scholar`、`dwd_org_base_info` 等在 gkx_element(ETL 灌图源)和 gkx_local(运行时企业模块直查)中都存在——图里数据的血缘是 gkx_element,而企业背景分析运行时读的是 gkx_local,口径可能存在差异。
2. **业务不直连源库是设计原则**:直接关系/间接关系/合作成果/同事/校友/论文合作/产业链两模块全部零 dao/MySQL import,溯源字段只是回读图节点 `source_table` 属性或硬编码常量;只有企业关系子系统例外(图+MySQL 混合)。
3. **图上的两类边**:ETL 灌入的事实边(`COAUTHOR_WITH`、`STUDIED_AT`、治理边等)vs 业务写回的推理边(`COLLEAGUE`、`EMPLOYED_BY` 的构建/标注)。
4. **查询全是 REST 封装**,仅三处发 nGQL:论文合作的两跳路径查询(graph-search `paths/search` 编译)、校友兜底 `MATCH`/`LOOKUP`、同事关系的 `CREATE EDGE COLLEAGUE` DDL。
5. **Milvus**(`scholar_person`/`org_domain_*`/`patent`/`project`/`paper`/`journal` 等 collection)只服务于离线 ETL 的实体对齐消歧,九大业务运行时**不用向量检索**。
6. **ETL 幂等与水位**:全部 rank@0 / merge / IF NOT EXISTS;增量水位在 `script/.etl_watermark/<域>.txt`(`etl_watermark.py`)。
