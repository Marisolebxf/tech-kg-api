## 1. 用户确认的业务口径

- A「入库决策」只验收真正的消歧 `T_LINK`：存在本空间、同实体类型的有效同名候选，且真实判定进入灰区，才建案并扣留待入库实体及关联边。
- C「抽取失败重跑」沿用现有失败通道；代码模板名为 `T_EXTRACT_FAIL`，不是新增一个名为 `EXTRACT_FAILED` 的模板。
- 本构建链路不新增 `T_DIRECT`，也不能把无候选记录换个模板或改个文案继续作为消歧灰区案。
- “同名”须与实际名称归一规则一致；仅向量相近、名称不同，不足以满足此次用户要求的同名门控。请核查现有多路召回的影响面，不擅自全局关闭近邻检索或改动无关检索功能。
- 没有候选不等于抽取失败；质量不合格也不等于程序异常。无候选的新实体按正常入库规则处理，质量处理按已有明确规则处理，不能为了测试把二者硬送 A/C。

## 2. 已独立核对的事实

2026-10-20，Codex 通过可见 Chrome 逐案只读检查当前测试空间的 50 个入库决策案，未裁决、未刷新候选：

| 分组 | 案数 | 实际情况 |
|---|---:|---|
| 正常消歧 `disambiguation-gray-v1` | 27 | 均有候选，建案得分 0.8 |
| 脚本挂起 `script-pending-gray-v1` | 23 | 16 案有候选，7 案候选为空；整体 `matchScore` 缺失 |

- 50 案实际模板全为 `T_LINK`，没有发现本批生成 `T_DIRECT`。空候选不能据此称为 T_DIRECT。
- 23 个强制触发案中，空候选的 7 案属于原样本说明里的 1 个新实体场景和 6 个质量/驳回场景；按用户此次规则，它们不应冒充自然消歧灰区验收。
- 本批未发现真实 `matchScore=0`；强制案缺该值，当前页面显示 `—`，不是 0。整体分、候选分、抽取置信度是不同概念。

- 当前公式 `0.6×名称相似度 + 0.4×属性一致率` 在无可比属性时使用中性值 0.5，所以同名得 0.8 符合既有代码，不是算术错误。不得为了让分数多样而伪造属性、分数或更改阈值。
- 同空间另一批 7 条失败重跑案件现显示全部已完成；只读日志显示重跑执行成功、读 7 / 写 7 / 失败 0。本问题不能据此重开为 C 通道普遍失败，也不意味着所有 C 场景已覆盖。

以上为现场汇总，真实记录映射、身份材料及原始响应不放公开分支。当前未做新的数据库或服务器追踪。

## 3. 根因与代码入口

只读依据：`kgetl@884d9bcd`；另参照 PR [#543](https://github.com/Marisolebxf/tech-kg-api/pull/543) 的候选刷新实现。实施前须重新获取最新 kgetl 并核实 #543 合并状态。

1. 专用 `person_entity_step_trigger.py::_transform` 按固定名单把实体从 `entities` 移到 `pendingReview`，不是依靠正常评分进入灰区。
2. `backend/service/temporal_workflows.py::_enqueue_entity_pending_item` 召回、评分后直接 `create_direct_case(... template_id="T_LINK")`；没有用 `decide()` 约束灰区，也没有拒绝空候选建案。函数名称里的 direct 不代表实际模板是 T_DIRECT。
3. 同函数保存候选分数，却未保存整体 `matchScore/margin`；前端仍统一称“灰区人工裁决”，隐藏了强制挂起与自然灰区的区别。
4. `backend/service/entity_disambiguation.py::score_candidate/decide` 的正常判定已有三分支：自动合并、灰区、新实体。高分但前两名分差不足也可进灰区，不要把灰区错误收窄成只有 `[0.65,0.85)`。
5. 基础 `person_entity_step.py` 的作者 mapper 主要输出姓名及原始 JSON，学者 mapper 则输出机构、统计等字段；当前有效评分字段并未对齐。原始真实材料存在，不代表评分器已经读取到身份判别证据。请确认从源行、脚本输出、Schema 过滤到评分输入各层实际保留了什么。

## 4. 建议的最小修复路线

### A. 统一真实判定，不允许脚本强制建灰区案

- 本次测试不再使用固定名单强制送审版，基础转换输出进入正常消歧流程；测试用例标签只放受限清单，不写成业务路由指令。
- 后端对可能产生 T_LINK 的入口统一校验：同空间/同类型/排除自身的有效同名候选存在，且真实 `decide` 结果为 gray，才允许建案。审计候选召回、批内消歧、写前守卫、pendingReview 旁路及可用的候选刷新入口，不只修一个建案调用点。
- 同名资格与候选集合、评分、裁决白名单必须一致。不要用一个同名候选作为门票，却自动合并到另一个仅近邻候选；新规则如何与现有多路召回兼容，请先列清最小影响范围。
- 无候选/低分新实体回到正常实体写入；自动合并走既有属性保留和 per-VID 互斥逻辑；只有灰区记录及其关联边进入扣留与后续裁决链路。无候选分支绝不能仅 `return/continue`，因为旧触发脚本已把记录从 `entities` 移走，那样会丢实体和关联边。
- 若仍保留 pendingReview 接口，必须交付其 merge/gray/new 三条分流与实体、边交接方案，不能把非灰区静默丢弃，也不能让自动合并后的边仍指向旧 VID。
- 区分“成功召回但确实为零”和“召回服务失败/截断/未就绪”。技术失败按既有重试/失败策略处理，不可伪装成无候选正常新建；同样不能伪造灰区。请列出当前召回接口能提供的证据与不足，不要求本次顺带重写整个召回系统。
- 学者与作者阶段需要依赖时，验收先完成学者预抽取再处理作者；生产路径仍须保留写前复查和并发保护，不能把手工分阶段当作消除所有竞态的代码修复。

### B. 对齐评分证据，而不是重造样本结论

- 先交字段映射表：源字段 → 可比较身份特征 → 两侧含义/缺值规则 → 实际评分输入 → Schema/快照保留位置。只选确有来源、含义可比的字段；主键不同不直接证明异人，同机构也不单独证明同人。
- 经核验的机构信息、稳定标识或关联证据能否用于评分，须据现有材料说明；不得凭空补 ORCID、机构、学历，不以作者序号或整段 `extra_json` 相等作身份评分。
- 若需新增 Schema 属性、改变共享评分权重或引入新匹配策略，单列影响和批准项，不夹在修脚本里上线。可先保留当前中性评分政策，但页面必须说明“无可比属性/证据不足”，不能把中性值描述成实际有 50% 属性相同。
- 初版优先校准和复用已有真实同名样本，不预设所有“合并组”必须合并；强证据和辅助证据要区分，最终身份真值另经核验。

### C. 页面、快照与历史兼容

- 新灰区案保存实际 `matchScore`、`margin`（单候选可为 null）、判定原因/规则版本，以及足以解释分数的证据元信息；记录缺少字段时显示未记录，不能用 0 填补。
- 名称相似度、实际属性一致率与“无可比属性时的中性值”分开展示；若详情补读的是当前图证据，明确不是建案时点快照，不能拿当前明细冒充当时计算依据。
- 历史强制挂起案保留历史标识，不能倒填分数、改写为自然灰区；旧空候选案提示历史状态/当前无有效候选，禁止合并。历史案件的人工迁移、重处理另批，不自动入图或删案。
- #543 的刷新候选、CAS、审计和白名单边界保留。刷新后候选全失效时，不自动 create/reject，不自动关闭历史案件，提示人工处理；它不等于允许新建空候选灰区案。
- T_DIRECT 的历史兼容或其他工作流是否仍有用途要先盘点，不因本次仅 A/C 就全仓删除模板或改历史表。

## 5. 新验收样本与通过条件

使用新命名隔离空间，保留既有图、案件、审计和水位；现有来源库先只读复用。需要追加真实数据时，先交来源、字段、数量、精确目标和回滚清单再获批执行，不借本文自动追加数据。

不再要求固定凑满 23 案。请给出足够覆盖的逐案清单，至少包含：

| 场景 | 预期 |
|---|---|
| 确无同名候选且记录有效 | 正常新建，无 A 案；实体及对应边不丢 |
| 同名、真实可比证据支持且满足合并阈值/分差 | 自动合并，无 A 案；旧属性保留、边端点改写正确 |
| 同名、真实得分在灰区 | 产生 T_LINK，至少一个有效同名候选，评分可复算 |
| 同名、多个高分候选且分差不足 | 产生 T_LINK，不擅自择一 |
| 同名、证据不足且无可比属性 | 如仍按现政策送审，说明中性值来源，不冒充已知同人 |
| 同名、实际证据冲突、低于灰区 | 正常新建，不误并，不强制送审 |
| 仅向量相近但不同名 | 不满足本次 A 同名门控；核对实体和边按批准的正常路径处理 |
| 召回异常、候选跨空间/跨类型、自身 VID、候选被删除 | 不产生伪灰区，不越空间裁决、不因技术失败静默新建 |
| 脚本仍返回空候选/高分/低分 pending 项 | 不能绕过门控；三分流不丢数据，异常有可追踪结果 |
| 行级真实抽取异常及故障注入对照 | 仅走 C；恢复基础脚本后按原记录重跑，成功态与实际写入一致 |

回归要求：

- 新建 A 案逐案断言：模板 T_LINK、同名资格、候选非空、真实判定为 gray、分数/分差/原因完整；本构建链路没有新 T_DIRECT。
- 人工 merge/create/reject 各覆盖：状态、目标属性、暂存边端点/rank/属性、审计一致；禁用/拒绝不合法或跨空间合并。
- 所有记录按新建/合并/扣留/按规则过滤/技术失败对账，不能仅数案件；重复执行、候选变化和并发不能重复建案或漏写。候选变化不应成为同一来源事件重复建案的理由。
- 同名样本先入学者、后处理作者，另加来源并发/到达顺序变化回归；有在途历史时保留 Temporal 版本化与重放兼容验证。
- C 的重跑中、成功、再次失败三态、完成态禁重跑继续回归；不以已有 7 案成功声称所有重跑路径均通过。
- 服务单测、前端测试与真实 Chrome/真实图库验收分开报告，失败与未测项如实保留。不得将桩测试通过写成线上验证通过。
