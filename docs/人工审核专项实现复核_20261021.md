### R1 [P1] 技术故障被当作 invalid，可能永久丢点/丢边

**位置：TW:2942-2944、3662-3664、3760 附近。** `_pending_write_descriptor_ok` 捕获控制库/DESCRIBE 的任意异常并返回 False；上层把该组 VID 计入 `invalidEndpointVids`，关系写入过滤这些边后仍可正常结束并推进来源水位。

最小复现：让 `get_session_factory` 抛暂态 RuntimeError，函数返回 False，而非上抛。这违反“确定性业务 invalid 才进无效集合、技术失败必须上抛”的已接受契约。

**修复要求：** 目录确无实体、DESCRIBE 成功但无名称列可判 invalid；连接、查询、超时及响应损坏应上抛，不能转成业务无效。补 activity→workflow 的水位不推进测试。

### R2 [P1] 终态裁决查询发生在重新评分之后，能复活已驳回事件

**位置：TW:3705-3723；主实体流 TW:3450-3483 同类。** priorVerdict 只在本次重新判 gray 后调用 `_open_entity_gray_case_v2` 时查询。如果相同源事件此前已被 reject，本次候选被删除、召回退化或评分变化为 new，代码直接 `_write_pending_vertex`，完全绕过旧裁决；若变化为 merge，则先 deferred，也没有机会读取已成功应用的 create/merge 决定。

最小复现：pending 首次真实 gray→人工 reject→相同输入重放但同名召回为空，结果 `written=1`，被驳回实体再次写入图库。

**修复要求：** 在重新 decide 和任何图写副作用之前，基于稳定事件身份查找既有案件及应用状态；复用 OPEN 的待审处置、成功终态的 priorVerdict，FAILED/UNKNOWN 失败关闭。只对确实未处理的新事件进行正常评分建案。

### R3 [P1] 批内 merge 绕过 B′ 且丢失旧 VID 改写关系

**位置：TW:3382-3385。** v2 的 first-by-name 分支在真实 decide=merge 时仍直接把第二条实体 ID 改成第一条并继续，未触发 `DEFERRED_MERGE_BLOCKED`，也没有向边流传回第二条旧 VID 的映射。`test_batch_same_name_dedupe_keeps_v1_semantics` 还主动把这一例外写成通过标准。

最小复现：同批两个不同 VID、同名且身份属性相同的实体，`autoMergeEnabled=false` 下仍返回两个相同 VID，无错误。后续引用第二 VID 的边无法通过端点终判；若引用边先被挂入案件，裁决补边路径还可绕过终判。

**修复要求：** 按收口 B′ 统一失败关闭，不以“保留 v1”增设未经批准的 merge 例外；测试应断言错误码、无改写副作用和受影响来源水位不推进。

### R4 [P1] ingress 身份取输出 VID 与动态输出摘要，重跑不稳定

**位置：TW:2746-2750、3705-3709。** `source_record_id` 优先取 `record.id`，即使存在真实 `sourceRecordId` 也被忽略；`compute_event_version` 输入是转换后的完整 record，未携带并使用源行事件身份。仓内实体脚本 `backend/script/entity_extractors_one_entity/common.py:618/647` 会生成当前 `ingest_time`，导致同一源行恢复时 HMAC 改变并重复建案。另一方面，多个源行映射同一 VID 时又可能丢失真实来源区别。

最小复现分别证实：给定 `id=v1/sourceRecordId=real-source-row`，材料第二项是 v1；仅改变转换结果 `props.ingest_time`，材料中的事件摘要随之改变。

**修复要求：** reader/transform/pending/resolve/prewrite/S3 两形状全链传递稳定 `sourceBindingId/sourceRecordId/sourceEventVersion`；摘要取 canonical 源业务行，排除运行时生成的摄取元数据，不能以输出对象全量摘要替代。补真实脚本跨重跑、同 VID 多源行、跨 chunk 测试。

### R5 [P1] APPLY_FAILED 被当作正常开放案，应用失败未关闭后续执行

**位置：MRP:320-321、1574、1625-1629。** 两段提交将图写失败案件置 APPLY_FAILED；但该状态不在 TERMINAL_STATUSES，ingress 直接返回普通重复案且没有 priorVerdict，park 也把它放进 open_by_vid 并选为 capture 案。调用方会继续扣留/暂存并成功结束，来源水位可以推进，未按 `applyStatus=FAILED` 抛 `VERDICT_NOT_APPLIED`。

最小复现：创建 v2 案，持久 `applyStatus=FAILED` 且状态 APPLY_FAILED，送入一条新边；未抛错误而是成功 park。

**修复要求：** 既有案路由必须先检查耐久应用标记，明确区分真正待裁决 OPEN/CLAIMED 与应用失败/UNKNOWN/中断；后一组不得走普通开放案吞入路径。补 ingress 和跨执行边两条失败关闭测试。

### R6 [P1] 人工裁决补边绕过另一端的待审/拒绝/不存在状态

**位置：MRP:1645-1651（只挂一端）、1951（直接 create_edge）。** 当边 A→B 的两端都有待审案，v2 park 用 next 只挂到其中一个案件；裁决 A 为 create/merge 后，`_apply_link_verdict` 直接写出 A→B，不检查 B 仍待审、已被 reject 或根本不存在。pipeline 中新增的端点终判对该路径不起作用。

最小复现：A、B 两个 v2 OPEN 案→park A→B→仅裁决 A=create，FakeGraph 已收到 `create_edge(a,b)`，B 仍 OPEN。B 若后续 merge/reject，该边也不会被可靠修正。

**修复要求：** 裁决补边须复用统一的双端点路由与存在性终判；任一端未决继续耐久暂存，任一端 reject 丢弃，两端都达到允许写入状态才 INSERT。关联边从原案件转交/去重需有可恢复事务语义，并发 park/裁决时不得丢边。

### R7 [P1] merge 重放以 application.canonical_vid 代替批准的持久 remap

**位置：MRP:331-332、1603-1604；`gray_gate.prior_verdict_disposition`。** 实现直接从裁决应用行获取 merge 的 canonical_vid 并放行，模型注释明确写“只读本表”；未从方案 A 的持久 remap 取 canonical，也不在 remap 尚未实施时抛 `MERGE_CANONICAL_MISSING`。

第六轮已明确 canonical 只能来自经批准的持久 remap，应用标记用于确认应用状态，不能成为未经批准的替代映射机制。单层案件目标还不足以处理 A→B→C 链式合并，不能因应用行有一个字符串就假定已到 canonical 终点。

**修复要求：** 保持本阶段方案 A 未实施的边界，提供明确的 canonical resolver 接口；remap 不可用时 merge 重放必须失败关闭，禁止回退至应用表或决议目标直接放行。不得为修此项擅自实施 remap 建表/部署。

### R8 [P2] 详情富化覆盖建案证据，评分字段仍混用两个时点

**位置：MRP:1766-1772；前端 LinkCandidate 仍声明 comparedProps 为 string[]。** v2 已保存建案时 `nameSim/propsAgree/propCompared/propMatched/comparedProps`，但打开详情仍调用旧富化函数，用当前图库属性重新评分后 `cand.update(detail)` 覆盖这些字段，而 candidate.score / `_resolution.matchScore` 留在建案时点。评审员看到的总分和明细可能互不相符。

最小复现：建案快照 propsAgree=0.5，当前图库候选属性一致；调用详情富化后返回 propsAgree=1.0。这不是仅并列展示当前图库证据。

**修复要求：** 保持建案证据字段只读；当前图库属性/当前重算结果放入独立、标注时点的字段，前端分别展示并校准 comparedProps 信封类型。覆盖一次“建案后候选属性变化”的测试。

### R2-b [P1] priorVerdict 只前置到 resolve，写前守卫仍能否定已应用的人工 create

**位置：TW:3425-3436、1979-1989；写前终判默认启用。** 主实体流 resolve 已按稳定事件身份识别 `create+APPLIED`，以 `keptAsNew` 返回待写记录；紧接着 `write_records` 仍调用 `_prewrite_recheck`，该函数没有相同的前置裁决逻辑，直接重新评分。若当前候选得分变成 merge，会先抛 `DEFERRED_MERGE_BLOCKED`，已确认的人工 create 再次被自动评分阻断。

**独立复现：** 同一记录已有 create+APPLIED 案，resolve 返回 `keptAsNew=1`；将其 records 交给真实 `_prewrite_recheck`，同名候选属性一致，得到 `stage=prewrite/score=1.0` 的 deferred 异常。

**修复要求：** 把已确认 priorVerdict 的处置贯穿至真正写入前最后一步。写前守卫须从可信的事件身份和耐久应用标记重新确认，而非依据可由脚本伪造的 bypass 标记；已应用 create 应允许幂等写入，FAILED/UNKNOWN 继续失败关闭。测试覆盖 resolve→write_records 的默认守卫开启路径，不能靠关守卫通过。

### R4-b [P1] pending 两次重建 record 均丢弃声明的 sourceEventVersion

**位置：TW:3779-3784、3839-3844。** `_gray_ingress_material` 支持声明 `sourceEventVersion` 为权威，但 pending item 重建 record 时只携带 id/props/sourceTable/sourceRecordId，该声明在前置查询和建案两处都丢失。因此同一来源行的业务版本由 v1 变 v2，仍使用相同的输出 HMAC 命中旧事件，旧 reject 会吞掉本应重新判定的新源事件。

**独立复现：** pending item 声明 `business-version-1`→首次 gray 建案→人工 reject；其他字段保持不变，仅声明业务版本改为 `business-version-2`；第二次返回 grayCases=0，未形成新案，错误沿用了旧 reject。

**修复要求：** 声明事件版本在 pending/主流/前置查案/建案/S3 两形状中完整传递，确保查询与写入同键。不要以扩大 volatile 删除列表代替源事件身份传递；声明版本变化是新事件，单纯摄取时间变化仍应保持同事件。补跨 chunk 与 S3/内联一致测试。

### R6-b [P1] 暂存边仍为无锁快照读改写，并发成功却丢失已确认的边

**位置：MRP:1536、1748-1766。** `_park_edges_v2` 仍读取 candidate_snapshot、在内存追加 `_pendingRelations` 后整体覆盖提交；没有案件行锁、版本 CAS 或独立边唯一账本。两个 worker 同时将不同边 park 到同一案件时会读到同一旧快照，后提交覆盖先提交，两个调用都报告成功。裁决时永远看不到被覆盖的边，来源水位却可以推进。

**独立交错复现：** 第一调用读到空挂起列表，拟追加 a→b；在它提交之前，让第二 session 读取旧快照并成功提交 a→c；第一调用随后提交。最终列表只有 a→b，a→c 丢失，两次 park 均成功。复现使用 SQLite 内存库和提交点注入，验证的是没有任何并发冲突防护时的读改写结果，不冒充真实 MySQL 并发测试。

新增 `_flush_pending_relations` 还有相同边界：读旧案件快照后在另一个 session 整体覆盖摘除，若同时有 park/裁决，也可能覆盖新边或转交到已经完成裁决的案件。

**修复要求：** v2 路由应在同一事务内锁定并重读案件状态/快照，或者使用可靠的版本 CAS 重试/独立唯一边账本；park、转交、摘除和提交裁决需要共用一致的并发约束。可按 VID/case_id 确定锁序避免死锁。并发测试至少覆盖同案双 park、park 与 submit、转交与另一端 submit，并断言成功确认的边总数与去向一致。

SQLite 不实现 MySQL 行锁；若选择 SELECT FOR UPDATE 修复，需要使用支持锁的测试替身或真实隔离测试库证明串行化，不能仅靠当前 SQLite 用例或源码存在 with_for_update 就宣布并发闭环。确定性交错复现可以随正确的锁模型调整测试调度，但不得删除“成功 park 的边不丢”这一断言。
