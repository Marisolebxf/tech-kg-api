1. 只有本空间、同实体类型、排除自身后的**有效归一化同名候选**进入真实判定，且判定结果为 `gray`，才允许新建 `T_LINK`。

3. 同名资格、评分候选集合、分差计算、案件候选快照和人工 merge 白名单必须一致。仅近邻但不同名的候选不得影响 A 类 `decide`，也不得成为 merge 目标。

## 二、对 `00be6d6d` 的阻断复核

### 1. pending 重注入不能只写回 `output.entities`

当前 `execute_transform` 会从脚本输出中 `pop("pendingReview")`；下游按 Schema 的单一 `kind`，并以 `transformed.get("entities") or transformed.get("edges")` 选一路记录。现有 `invented_by_relation.py`、`applied_by_relation.py` 等关系脚本会同时输出边和 pending 实体。

因此，简单把 pending 实体塞回 `output.entities` 存在以下问题：

- 关系 Schema 不会进入 `resolve_entity_batch` 的实体分支；
- `entities or edges` 会让其中一路被遮蔽；
- pending 实体可能被当成关系记录，或原边被忽略；
- 无法证明实体、边在 new/merge/gray 三分流中均不丢失。

请交付独立的实体旁路或明确的双流方案：同一步输出的实体与边分别进入各自解析/写入链路，边在端点 new/merge/gray 结果明确前按可追踪状态处理。不得只证明本次 Person 实体脚本可用而破坏通用 pending 接口。

### 2. 同名集合必须先过滤，再执行 `decide`

不能对“同名精确 ∪ 不同名近邻”全集执行 `decide`，再用“其中存在一个同名候选”作为开案门票。例如不同名近邻 0.84、同名候选 0.60 时，全集判定为 gray，但同名集合真实判定为 new，仍会生成伪灰区。

本专项的判定口径必须等价于：

```text
eligible = candidates where
  same graph_space
  and same entity_type
  and vid != incoming_vid
  and normalize(candidate.name) == normalize(incoming.name)

outcome = decide(score(eligible))
create T_LINK iff eligible is not empty and outcome.decision == "gray"
```

不同名近邻可保留为只读诊断信息，但不得进入 A 类分数、margin、候选快照或 merge 白名单。请说明批内、图库召回、写前守卫和 #543 刷新如何复用同一个 eligibility 函数，避免各入口规则漂移。

### 3. `detect_extract_collisions` 必须显式退出新建 A 案链路

该入口默认启用，发生在写图后；它只按同名碰撞建 `T_LINK`，不评分、不走 `decide`、不扣留记录，也没有 `matchScore/margin`。这与新口径不兼容。

请明确：在消歧 v2 链路中不得再由它创建 `T_LINK`。若保留，只能作为不建案的观测/告警，且不能把已写图记录包装成“待入库灰区”。同时说明 Temporal 在途历史的版本化兼容策略。

### 4. `extra_json` 不能支撑所谓“同源自动合并/低分新建”样本

当前 `score_candidate` 没有把 `extra_json` 排除在业务属性外；批内记录两侧若都有该字段，就会比较整段 JSON。`00be6d6d` 用“同论文重复作者行 extra_json 完全相同→1.0”及“不同论文整段不同→0.6”证明同源样本可达，违反已确认口径。

- 同一作者行若本来就是同一 VID，只是幂等重复写，不是有效的自动合并样本。
- 不同 VID 时整行 JSON 通常包含不同主键/论文信息，不能据其相同或不同证明身份。
- 学者与作者按不同到达顺序时，批内原始 props 与图库经 Schema 过滤后的 props 不同，还会造成评分口径随执行顺序变化。

请修正字段对照和样本计划：现有真实作者材料缺少可比身份字段时，跨源自动合并和真实冲突低分新建应标记为当前不可达；同源场景也不得用整段 `extra_json` 补齐。若建议把 `extra_json` 加入排除集合，需说明对现有评分和回归的影响，但不得在本轮直接实施。

### 5. #543 刷新必须对齐新白名单，但不能改写历史含义

PR #543 当前刷新使用多路召回并把结果写回 merge 白名单。新规则下，新案及采用新 policyVersion 刷新的案件只能保留有效归一化同名候选；不同名近邻不得因刷新重新获得 merge 资格。

请给出版本化方案：保留 #543 的 version CAS、审计、失效候选剔除和终态保护；说明新案、历史自然灰区案、历史强制挂起案分别如何刷新。刷新后候选为空时仍不得自动 create/reject/关闭案件。

### 6. 跨执行 VID remap 新表暂不批准

auto-merge 只改实体记录 VID、关系仍引用旧 VID 的缺口属实，但 `entity_vid_remap(graph_space, from_vid, to_vid)` 尚不足以实施。请先补齐：

- 数据模型、建表/升级、索引和服务初始化文件清单；
- 映射落账时点，如何只在实体写入成功后生效；
- resolve、批内合并、写前终判产生的映射如何组合并保留原 VID；
- 同执行关系、跨执行关系、关系先到、实体先到和并发到达时序；
- 链式映射、环检测、路径压缩、并发 CAS/锁、删除和失败恢复；
- graph_space、entity_type/node_label、来源身份的作用域；
- 是否可复用已有溯源/身份机制，以及不建新表的最小替代方案；
- Temporal 事件历史和 S3/内联两种载荷形状的兼容。

未经单独批准，不得建表、跑 DDL 或把 remap 写入现有业务表。

### 7. 新案必须保存建案时点可复算证据

当前 `_open_entity_gray_case` 把候选压缩为 `vid/name/score`，丢失 `nameSim/propsAgree/comparedProps`；详情页补读的是当前图库证据，不能冒充建案时点证据。

请设计新快照字段，至少包含：

- `matchScore`、`margin`、decision reason、policyVersion；
- 每个 eligible 候选的 `nameSim`、实际 `propsAgree`、`comparedProps`；
- 是否使用“无可比属性中性值 0.5”，并明确它不是 50% 属性相同；
- 同名资格及归一化规则版本；
- 精确召回成功/真零/Schema 无名称列/服务异常/近邻降级的可区分状态；

不得只依靠页面打开时重新计算。
