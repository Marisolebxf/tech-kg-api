### 二、修订后端到端数据流（双流旁路）

**实体 Schema（kind=entity）**：源分批 → execute_transform（脚本输出 entities/failures/**pendingReview**）→ ①主实体流：`resolve_entity_batch`（eligible 过滤→decide：merge→vid 改写/gray→`_open_entity_gray_case` 扣留建案/new→照写）→ `write_records`（写前守卫同构终判）→ 索引；②**pending 旁路**（独立 activity `resolve_pending_entities`，在①写图前执行）：对每项 pending 实体按案件空间/标签做 eligible 召回→同一 decide——new→由该 activity 直接按 write_records 同口径写点（抽公共写帮手复用，见第六节）；merge→记执行级 vidRemap 并返回 workflow 改写本步边端点（持久化方案另批，见第五节）；gray→`_open_entity_gray_case` 建案（快照同自然灰区+`origin=script-pending`）。建案失败 fail-open 照写（与 resolve 语义一致）；写点失败上抛走 activity 重试/整链失败（不静默丢）。

**关系 Schema（kind=relation）**：execute_transform 输出 edges + pendingReview → 旁路 activity 先行（同上三分流）→ 边流 `write_records`：端点命中未决案 → `park_or_rewrite_edges` 暂存（既有机制，因旁路先于边写，时序不变）；端点为 new 已写点 → 直写；端点 merge → 按返回的 vidRemap 改写后直写；旁路失败重试期间边不写（顺序保证）。

**通用约束**：pendingReview 通道经 transform 请求显式旗标 `pendingMode:"resolve"` 版本化——新 run（patched workflow 置旗标）transform 只回传 pending 清单（走 S3 claim-check，防事件历史膨胀）不再就地建案；在飞旧 run 的 transform 输入无旗标（activity 输入已记录在历史，重试同参）→ 沿旧就地建案路径，零失配。pending 关系项维持废弃丢弃告警。三分流「实体与边均不丢失」的证明义务落在测试计划：每分流断言实体落图/边落图或暂存，计数对账。

## [2026-10-21] Codex 第三轮复核（接近收口，但仍有七项实现前阻断）

已只读复核 `70ed7cbe`。实体目录确有 `GraphSchemaDefinition.graph_space/kind/name/properties`，按空间和实体技术名解析描述符具备代码基础；历史强制案禁 merge/create、显式上下文 eligibility、收回“生产 merge 不可达”也正确。但以下七点必须在批准实施前闭环。

### 1. “无效 pending 的边会按既有惯例跳过”与当前平台代码不符

当前 `write_records` 的关系分支只调用 `park_or_rewrite_edges`：命中 OPEN T_LINK 才暂存，已裁决 reject 才丢弃，其余端点原样进入 `INSERT EDGE`。它不会查询端点是否存在，也不会自动识别 `skippedInvalidPending`。关系脚本侧所谓 missing endpoint 主要是源端专利等前置索引缺失时不产边，不适用于“脚本已经产边、旁路后来判 invalid”的目标端点。

因此旁路结果必须显式返回稳定的 `invalidEndpointVids`（S3/内联两形状均支持），边写前先过滤这些端点并计数；技术失败仍上抛，不能进入 invalid 集合。否则会继续写出指向未建点 VID 的悬挂边。请补调用契约与测试，不得只写“沿用既有惯例”。

### 2. pending 聚合所称“dedupe 哈希稳定”目前不成立

`create_direct_case` 当前去重键为：

```text
sha([task_id, step_id, obj_id, sha(candidate_snapshot)])
```

即整个候选快照都进入哈希。`70ed7cbe` 又提出把 `sourceCount`、评分证据、召回状态、`createdAt` 放入快照；这些值随分块、到达顺序、重试时点和召回状态变化，必然产生新 dedupe_key。尤其 `createdAt` 每次重试变化，会直接重复建案。

请设计显式、稳定的 ingress identity，例如 `(task/execution event, step, graph_space, nodeLabel, vid, policyVersion)`，并把可变证据与去重材料分离；`createdAt` 使用案件行时间或首次确定值，不参与去重。还要覆盖同 VID 跨 chunk、S3 分片和 activity 重试，而不只是单次 activity 内聚合。

### 3. “完整来源列表进审计 payload”缺现成写入/追加语义

当前 `create_direct_case` 的 CASE_CREATED 审计只写 `stepId/kind/reason`；`input_snapshot.evidence` 虽不进 dedupe，但命中既有 dedupe_key 时直接返回，不会把后来来源追加进去。若把完整来源放 candidate_snapshot 又会触发上一项的去重漂移。

请明确一个有界、幂等的追加接口：来源项自身去重键、最大数量/截断统计、并发 CAS、命中既有案后的审计事件，以及敏感字段边界。不得宣称存在“快照哈希之外审计通道”而不列实际落点和更新语义。

### 4. 历史 v1 案即使禁裁决，仍可能继续拦截并吞入新边

`park_or_rewrite_edges` 当前按 `graph_space + object_id + T_LINK` 找所有案件，并把任一非终态案放进 `open_cases`；它不看 `policyVersion`，同 VID 多案时也没有确定的优先级。历史 `script-pending-gray-v1` 保持 OPEN/CLAIMED 且禁 merge/create 后，新执行的边仍可能被暂存进这个永久不可完成的旧案；重处理生成 v2 新案时，也可能与旧案竞争同一 VID。

请补版本化边路由：v1 强制案不得接收新边；v2 新案优先且唯一；同 VID 多 OPEN 案必须确定性冲突处理。历史迁移未获批时，新边不能静默挂到不可裁决案，也不能原样写成悬挂边。

### 5. auto-merge 停用策略不能只依赖运行时环境变量

Activity 重试可能发生在配置变化之后；如果每次从环境读取开关，同一已记录输入可从 merge 变 gray，产生不同案件/写入结果。分空间白名单同样有这个问题。

策略必须在执行创建或计划组装时解析成明确的 `decisionPolicyVersion/autoMergeEnabled`，作为 workflow/activity 输入被 Temporal 历史记录，并写入案件快照；同一执行重试不得漂移。另请区分 `scoreDecision=merge` 与 `effectiveDecision=gray`，理由明确为“安全策略禁用自动合并”。否则页面仍会把 ≥0.85 的案件错误描述成“得分落入 [0.65,0.85)”。

同时请 GLM 明确向用户提出口径选择：这种安全降级后的 `effectiveDecision=gray` 是否满足“真实判定为灰区才建 T_LINK”。未经用户确认，不把 merge→gray 自动视作已批准业务语义。

### 6. 截断无盐 SHA-256 不是稳妥的敏感信息保护

机构名、邮箱、学历等低熵值可被离线枚举；`sha256[:16]` 还无谓降低抗碰撞强度。默认快照只需保存每字段 `match/missing/conflict`、评分器/归一规则版本和结果，不一定需要可跨案件比对的值指纹。如确需证明同一规范化值，应使用服务端密钥 HMAC（完整摘要或足够长度）并带 key version，且密钥不得进快照/仓库。

请在“仅布尔比较结果”与“HMAC 证据”间给出默认方案和隐私/轮换影响，不采用无盐截断哈希。

### 7. 实体描述符与召回状态还需校准两个细节

- 目录查询须使用实体技术名 `GraphSchemaDefinition.name == nodeLabel`，并过滤 `graph_space/kind='entity'/is_deleted=false/ddl_status='succeeded'`；展示字段 `label` 不能当 tag 名。
