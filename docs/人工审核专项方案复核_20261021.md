### 二、修订后端到端数据流（双流旁路）

**实体 Schema（kind=entity）**：源分批 → execute_transform（脚本输出 entities/failures/**pendingReview**）→ ①主实体流：`resolve_entity_batch`（eligible 过滤→decide：merge→vid 改写/gray→`_open_entity_gray_case` 扣留建案/new→照写）→ `write_records`（写前守卫同构终判）→ 索引；②**pending 旁路**（独立 activity `resolve_pending_entities`，在①写图前执行）：对每项 pending 实体按案件空间/标签做 eligible 召回→同一 decide——new→由该 activity 直接按 write_records 同口径写点（抽公共写帮手复用，见第六节）；merge→记执行级 vidRemap 并返回 workflow 改写本步边端点（持久化方案另批，见第五节）；gray→`_open_entity_gray_case` 建案（快照同自然灰区+`origin=script-pending`）。建案失败 fail-open 照写（与 resolve 语义一致）；写点失败上抛走 activity 重试/整链失败（不静默丢）。

**关系 Schema（kind=relation）**：execute_transform 输出 edges + pendingReview → 旁路 activity 先行（同上三分流）→ 边流 `write_records`：端点命中未决案 → `park_or_rewrite_edges` 暂存（既有机制，因旁路先于边写，时序不变）；端点为 new 已写点 → 直写；端点 merge → 按返回的 vidRemap 改写后直写；旁路失败重试期间边不写（顺序保证）。

**通用约束**：pendingReview 通道经 transform 请求显式旗标 `pendingMode:"resolve"` 版本化——新 run（patched workflow 置旗标）transform 只回传 pending 清单（走 S3 claim-check，防事件历史膨胀）不再就地建案；在飞旧 run 的 transform 输入无旗标（activity 输入已记录在历史，重试同参）→ 沿旧就地建案路径，零失配。pending 关系项维持废弃丢弃告警。三分流「实体与边均不丢失」的证明义务落在测试计划：每分流断言实体落图/边落图或暂存，计数对账。

逻辑事件身份不得包含仅控制 merge disposition 的运行策略版本。请区分并命名：`decisionPolicyVersion`（v2/v3，控制 auto-merge，不进去重身份）与真正会改变 gray 证据/阈值的 `scoringRuleVersion` 或 `adjudicationSchemaVersion`（是否进入键需明确迁移规则）。同一来源事件在 v2→v3 恢复时必须生成同一键；测试必须显式覆盖“策略换版但 gray 案不重复”。

### 2. “命中 TERMINAL 后按既有裁决语义写图”没有调用契约

当前 `create_direct_case` 的 `_ingress_response` 只返回 `reviewId/status/riskLevel/isolationStrategy/duplicate`，既不返回 `ReviewDecision.result`，也不会把历史 merge/create/reject 决定应用到本次记录。仅规定“终态保护，不重开不新建”会让调用方不知道应过滤、改写 VID、写新点还是跳过；尤其 merge 裁决若无持久 remap，恢复记录和边仍可能使用旧 VID。

请为 dedupe 命中 TERMINAL 明确三态契约及数据来源：

- 已成功应用的 create/reject/merge 如何返回可机器执行的 disposition；
- merge 必须从经批准的持久 remap 读取 canonical VID，不能临时重算或只靠案件状态；
- APPLYING/失败应用等非稳定终态如何失败关闭；
- 调用方如何据此过滤记录、改写端点或安全 no-op，并保证案件裁决已经落图与重放顺序一致。

没有这层契约时，不得写“按既有裁决语义走”。

### 3. `sourceEventVersion` 的普通 SHA-256 与时间列优先级仍不稳妥

整行业务列可能含机构名、邮箱等低熵敏感值；普通 SHA-256 不能因为被用于 dedupe 就豁免此前已接受的低熵枚举风险。同时仅取时间列作为最高优先级，会把同一主键在时间精度内的多次不同更新错误视为同一事件。

请采用明确的 canonicalization，并把业务版本/高精度时间与**带密钥的完整 HMAC-SHA256 行摘要**组合，而不是三选一后退到无盐摘要；说明 keyVersion 和密钥轮换时如何仍命中旧事件（例如稳定 dedupe 专用密钥不随普通轮换直接换键，或双 key 查找/迁移）。这属于安全与密钥审批项，不能标成“无新增审批”。若平台无法提供该稳定能力，应失败关闭而非生成可漂移或可枚举的事件键。

claim-check 的完整性摘要也应保存完整 SHA-256（它承担完整性校验，不需要截成 16 位）；工件本身含原始 VID，启用其写入、保留期、删除策略和读取权限均须明确审批，不只是“读取权限口径”。

### 4. 来源行“自然有界”不成立

方案规定第 33 条以后仍为每个 distinct 来源插入一行，只把 `evidence` 置空；因此表行数随来源数持续增长，并非自然有界。请如实选择：要么承认明细行无硬上限并给出容量、索引与保留策略；要么设置硬上限并为溢出来源设计不会因重试虚增的持久去重/聚合结构。`source_count` 与 `source_truncated_count` 的含义也须固定为“不同来源总数/未保存 evidence 的不同来源数”，不能把数据库行有界与敏感 evidence 有界混为一谈。
