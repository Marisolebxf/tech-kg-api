### 二、修订后端到端数据流（双流旁路）

**实体 Schema（kind=entity）**：源分批 → execute_transform（脚本输出 entities/failures/**pendingReview**）→ ①主实体流：`resolve_entity_batch`（eligible 过滤→decide：merge→vid 改写/gray→`_open_entity_gray_case` 扣留建案/new→照写）→ `write_records`（写前守卫同构终判）→ 索引；②**pending 旁路**（独立 activity `resolve_pending_entities`，在①写图前执行）：对每项 pending 实体按案件空间/标签做 eligible 召回→同一 decide——new→由该 activity 直接按 write_records 同口径写点（抽公共写帮手复用，见第六节）；merge→记执行级 vidRemap 并返回 workflow 改写本步边端点（持久化方案另批，见第五节）；gray→`_open_entity_gray_case` 建案（快照同自然灰区+`origin=script-pending`）。建案失败 fail-open 照写（与 resolve 语义一致）；写点失败上抛走 activity 重试/整链失败（不静默丢）。

**关系 Schema（kind=relation）**：execute_transform 输出 edges + pendingReview → 旁路 activity 先行（同上三分流）→ 边流 `write_records`：端点命中未决案 → `park_or_rewrite_edges` 暂存（既有机制，因旁路先于边写，时序不变）；端点为 new 已写点 → 直写；端点 merge → 按返回的 vidRemap 改写后直写；旁路失败重试期间边不写（顺序保证）。

**通用约束**：pendingReview 通道经 transform 请求显式旗标 `pendingMode:"resolve"` 版本化——新 run（patched workflow 置旗标）transform 只回传 pending 清单（走 S3 claim-check，防事件历史膨胀）不再就地建案；在飞旧 run 的 transform 输入无旗标（activity 输入已记录在历史，重试同参）→ 沿旧就地建案路径，零失配。pending 关系项维持废弃丢弃告警。三分流「实体与边均不丢失」的证明义务落在测试计划：每分流断言实体落图/边落图或暂存，计数对账。
