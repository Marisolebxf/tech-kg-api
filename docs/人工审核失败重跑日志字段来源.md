## 一、弹窗数据链路总览

点「日志」后前端按三条数据源拼出整个弹窗,各有归属:

```
openLog(row)                                    OperationsCenterView.vue:285
  ├─ getProductionReview(row.id)                ① case 详情(含 input 快照)
  │    GET /api/v1/manual-reviews/production/{id}
  │    → service/manual_review_production.py:277 get_case
  │    → 业务库 gkx_element.manual_review_case(tech-kg-mysql,宿主 30306)
  │    快照 input.executionId / input.rerunExecutionId 决定打开哪条执行
  ├─ getExecution(executionId)                  ② 执行行(概要/抽取结果)
  │    GET /api/v1/workflow-system/executions/{id}
  │    → service/workflow_operations.py:283 get_execution
  │    → 共享控制库 techkg_control.workflow_executions(temporal-mysql-dev2 容器,payload 长文本 JSON)
  └─ getTask(execution.taskId)                  ③ 任务行(阶段状态/日志正文)
       GET /api/v1/task-center/tasks/{taskId}
       → service/workflow_repository.get_task
       → 共享控制库 techkg_control.tasks(payload JSON)
```

- ①决定「打开哪条执行」:重跑执行优先(`rerunExecutionId` 存在则默认看它,可切回原执行)。
- ②③都源自 Temporal 工作流的真实下发与 worker 回填,无一处写死或 mock(演示/mock 兜底已在 860d98c 清除)。

## 二、弹窗展示字段来源明细

模板位置:`frontend/src/views/platform/OperationsCenterView.vue:638-686`;取值 computed 在 `:237-261`。

| 执行概要 | 开始时间 | `logExecution.startedAt` | 同上,payload `startedAt`(UTC 字符串) | 下发时写 |
| 执行概要 | 完成时间(空显 `—`) | `logExecution.completedAt` | 同上,payload `completedAt` | 工作流终态时写 |
| 执行概要 | 抽取结果「写入 X · 失败 Y(Z 个来源)」(output 有内容才显示) | `logExtractSummary`(`OperationsCenterView.vue:245-253`)= Σ`output.sources[].written`、`output.failures.count`、`len(sources)` | 同上,payload 的 `output` | `SchemaExtractWorkflow` worker 完成时回填:逐来源批次/读行/写入/失败统计(`temporal_workflows.py`) |
| 阶段状态 | 每步 `step.name`(如 `extract`) | `logTask.steps[].name` | `GET /v1/task-center/tasks/{taskId}`(`taskId` 取自执行 payload,`OperationsCenterView.vue:277`)→ `workflow_repository.get_task` → `techkg_control.tasks` payload JSON | worker 每步真实执行记录写进 `output.steps`(`temporal_workflows.py:957`),读取时 `_sync_task_from_execution` 经 `pipeline_steps` / `normalize_stages`(`stage_normalizer.py:63,107`)回填 `task.steps` |
| 阶段状态 | `step.status`(成功/失败,样式类 `is-<status>`) | `logTask.steps[].status` | 同上 | 同上,该步 Temporal activity 的真实结果 |
| 执行日志 | 日志正文(`<pre>` 逐行拼接) | `logLines`(`OperationsCenterView.vue:256-261`)= `logTask.logs` 数组;无任务记录时兜底 `logExecution.message` 单行 | 同上,tasks payload 的 `logs` 数组 | 见下表(六类日志行) |

## 三、日志正文各行(logs 数组)的产生方式

| 日志行样例 | 写入时机 | 写入代码 | 数据来自 |
|---|---|---|---|
| `工作流已下发` | 任务创建(下发即有) | `workflow_operations.py:208` | 下发时的 `execution.message` |
| `重跑范围:20 条失败记录(1 个来源),原执行 EXEC-…` | 重跑执行创建(下发即有,RERUNNING 阶段即可看) | `_rerun_scope_line`(`:25-40`,由 `:209-211` 追加) | 重跑下发 payload 的 `recordIdsBySource` / `rerunOfExecutionId` |
| `阶段回写:1 个 step(含输入输出),状态=ABNORMAL` | 执行终态后**首次被读取**时(读时惰性回填) | `_sync_task_from_execution`(`:336-407`) | 执行 payload 的终态 status + output.steps 形状 |
| `来源 source:xxx(techkg_e2e_liz.review_widgets):1 批 / 读 20 行 / 写入 0 / 失败 20` | 同上 | `_extract_result_log_lines`(`:43-73`) | worker 回填的 `output.sources[]`(batches/rows/written/failed/watermark),按内容去重幂等追加 |
| `失败汇总:20 条(详见人工审核失败队列)/ (已落审核 case 64 条)` | 同上 | 同上(`:68-72`) | `output.failures.count/recorded`;重跑模式 recorded 恒 0(仍失败记录由 resolve 重建为新案,不重复落 case) |
| `任务重试:reset 到新 run_id=…,原因:…` | 任务中心「重试」按钮触发 | `retry_task`(`:330-332`) | Temporal ResetWorkflowExecution 结果 |

## 四、case 快照(input)关键字段的写入时点

`manual_review_production.py` 中三条路径决定了弹窗能打开哪条执行:

| 快照字段 | 写入时点 | 代码位置 |
|---|---|---|
| `executionId`(初始)= 原执行 | 抽取 worker 逐行失败转案时 | 建案路径(manual_review_service 直调) |
| `rerunExecutionId` = 重跑执行 | 重跑下发时补写进被重跑的旧案(旧案随之 RERUNNING/RESOLVED) | `:677,707`;superseded 标记 `:782,795` |
| `executionId` = 重跑执行 + `rerunOfExecutionId` = 原执行 + `attempt+1` | 重跑仍失败,resolve 重建新案时(去掉旧 `rerunExecutionId` 键) | `:833-839`,reason 前缀「重跑仍失败:」 |

## 五、真实性结论(2026-09-30 dev2 实测)

1. **日志本身是真实数据**:每行数字都对应真实 Temporal 工作流执行的 payload/output,控制库可查证。135 条 T_EXTRACT_FAIL 待处理案分布在 14 个真实执行上(0920:82 / 0930:20 / 0922:19 / 0921:10 / 0928:3 / 0929:1),共享控制库全部健在、弹窗 100% 可开,无死链、无 mock。
2. **但底层业务数据是测试造数**:135 条全部来自 e2e 测试表 `techkg_e2e_liz.review_widgets`(129)/`review_ghosts`(6),schema 是厂商的「审测挂件 ReviewWidget」(f0ecec95-…),失败原因清一色是故意投毒的 `ValueError: POISON 拒绝解析(审测)` 行——这些行永远重跑不成功。
3. 例证:2026-09-30 11:39(本地)一次 20 条重跑(EXEC-267504896EBE43DF,triggerSource=RERUN,跑 20.5 分钟)全部又失败,20 条案 attempt+1 重建;其任务日志如实记录「1 批 / 读 20 行 / 写入 0 / 失败 20」。
4. 已知小瑕疵(不影响日志真实性):2 个 0921 的重跑执行行 message 是通用「工作流执行完成」,与其 output 里 3 条失败数不符(FUNC-00901 状态映射漏网的存量);任务日志行本身如实。
