# 亿级科技知识图谱引擎测试文档（轻量专测库 gkx_lite 版）

场景：**新建一个图空间**，从零走完 建 Schema → 绑来源表 → 传脚本 → 跑抽取 → 验收。样例取 6 个实体 + 3 个关系，全部按页面上鼠标怎么点来写。

本版全部指向**专用轻量测试库 `gkx_lite`**（7 张表、共 64 行），跑完整条链路只要几分钟，且**验收数字是精确值**（见 Step 6），不再依赖大库数据量。库由物料包 `docs/gkx_lite_materials/gkx_lite.sql` 一键重建（含数据），沿用原版脚本 `docs/gkx_local_1_materials/scripts/page_test/` 下 9 个页面直传精简版脚本。2026-10-18 已按本文档在 8093 栈从零页面点击全链路实测通过（9 项计数全部精确命中）。

- 数据实体 3 个：Paper 论文、Journal 期刊、IndustryChain 产业链
- 关系端点实体 3 个（关系要连它们，必须先建）：**IndustryNode 产业链节点**（BELONGS_TO_NODE 终点）、**Organization 机构**（BELONGS_TO_NODE 起点）、**Person 科技专家**（AUTHORED_BY 终点）
- 关系 3 个：PUBLISHED_IN（论文→期刊）、AUTHORED_BY（论文→专家）、BELONGS_TO_NODE（机构→产业链节点）

登录说明：8093 这类本地免登栈（`AUTH_ENABLED=false`）**不需要任何账号密码**，打开即是本地管理员；开了登录的栈用统一认证账号进。

## Step 0 重建轻量库（一次性，可跳过若库已在）

```bash
docker exec -i tech-kg-mysql mysql -uroot -pgkx_element < docs/gkx_lite_materials/gkx_lite.sql
```

7 张表：`dwd_zh_paper`(10 行，P2026L001–010)、`dwd_zh_journal`(5，J001–J005)、`dwd_industry_chain_info`(10，2 条链×5 节点)、`dwd_org_base_info`(6，O2026L001–006)、`dwd_scholar`(6，A2026L001–006)、`dwd_zh_author`(19)、`dwd_org_industry_chain_dtl`(8)。

> 为什么自带一份产业链表：`gkx_dwd_local.dwd_industry_chain_info` 2026-10-14 重建后列名改成了 `industry_code/industry_link_code`，而 9 个脚本读的是旧列 `chain_code/node_id`——在 `gkx_dwd_local` 上照旧绑表会抽出 **0 条**产业链实体。`gkx_lite` 里的副本是**旧结构**，脚本可正常读。

## Step 1 新建图空间（配置管理页）

1. 左侧导航 **「配置管理」** → 左侧分类切到 **「图数据空间」** → 右上 **「＋ 新建图数据空间」**。
2. 弹窗里：图数据空间名称填新空间名（仅字母/数字/下划线，字母或下划线开头，如 `gkx_lite_1`）；说明选填 → **「创建」**。
   - 页面提示属实：真实执行 CREATE SPACE，创建后有**秒级传播延迟**——紧接着建 Schema 若偶发 DDL 失败，等几秒重试即可。
3. 同页分类切 **「MySQL 数据源」**，只需要**一个**：指向 `gkx_lite` 库（如 8093 栈已建好的 `gkx_lite`，地址 `host.docker.internal:30306`、账号 root、默认库 gkx_lite）；缺就「＋ 新建配置」补，填完点测试连通。7 张源表（含 `dwd_org_industry_chain_dtl`）全在这一个库里，**不需要第二个数据源**。
4. 到 **「平台总览」**，右上角**全局图空间选择器**切到新空间——之后 Schema 管理、图谱构建、统计全都跟随这个选择。

## Step 2 建 Schema（Schema 管理页，逐个建）

**实体的点法**：「Schema 管理」→「标准实体」标签页 → 右上 **「＋ 增加」** → 填 实体名 / 中文名 / 说明 → 属性表里带锁图标的公共必选属性已自动带出，点「添加属性」按下方表格逐个补业务属性（属性名 + 类型）→ 底部「nGQL 预览」扫一眼 → **「预览并创建」→「确认创建」** 两步 → 应看到 toast「已创建并执行图 DDL」。

**关系的点法**：切「关系」标签页 →「＋ 增加」→ 填 关系英文名 / 中文名 / **起点实体** / **终点实体**（下拉选）→ 补业务属性 → 同样「预览并创建」→「确认创建」（执行 CREATE EDGE）。

**六个实体要填的东西：**

| 实体名 | 中文名 | 业务属性（属性名＋类型，逐个添加） |
|---|---|---|
| `Paper` | 论文 | title_zh(string)、title_en(string)、doi(string)、publication_year(string)、publication_date(string)、language(string)、document_type(string)、publication_type(string)、volume(string)、issue(string)、start_page(string)、end_page(string)、is_oa(string)、source_url(string)、source(string)、created_time(string)、updated_time(string)、output_awards(string) |
| `Journal` | 期刊 | name_zh(string)、name_en(string)、name_abbr(string)、issn(string)、eissn(string)、country(string)、founding_time(string)、impact_factor(string)、is_sci(string)、jcr_zone(string)、cite_nums(string)、annual_publication(string)、publication_cycle(string)、source(string)、zh_core(string)、sub_quartile(string)、top(string)、scope_zone(string) |
| `IndustryChain` | 产业链 | chain_code(string)、chain_name(string) |
| `IndustryNode` | 产业链节点 | node_id(string)、node_name(string)、node_type(string)、level(string)、node_seq(string)、node_imp_level(string)、node_stage(string)、node_path(string) |
| `Organization` | 机构 | name_cn(string)、name_en(string)、province(string)、city(string)、org_kind(string)、founded_year(int64) |
| `Person` | 科技专家 | name_zh(string)、name_en(string)、scholar_org(string)、paper_nums(int64)、h_index(int64) |

**三个关系要填的东西：**

| 关系英文名 | 中文名 | 起点实体 | 终点实体 | 业务属性 |
|---|---|---|---|---|
| `PUBLISHED_IN` | 论文发表关系 | Paper | Journal | volume(string)、issue(string)、start_page(string)、end_page(string)、publication_year(string) |
| `AUTHORED_BY` | 论文署名关系 | Paper | Person | author_order(string)、is_corresponding(string)、citations(int64) |
| `BELONGS_TO_NODE` | 企业归属产业链节点 | Organization | IndustryNode | chain_score(double) |

说明三点：

- **说明字段别用 `+` 或 `!@#￥%&`**：弹窗校验会拦「说明不能包含异常字符」，多个表名用「与」连接（如「dwd_scholar 与 dwd_zh_author」）。
- 不用手填的：实体公共必选属性 `id/name/create_time/update_time/source_table`（关系是 `create_time/update_time/source_table`）弹窗里自动带出且带锁；溯源列 `vid/source_system/source_record_id/source_url/source_update_time/confidence/match_method/match_evidence/ingest_batch/ingest_time` 建 TAG/EDGE 时平台自动注入。
- **属性不用建全**（上表已是精简集）：写图取「脚本输出 ∩ Schema 属性」交集——Schema 里没建的属性被静默丢弃、不会报错；建了但脚本没输出的列留空/补默认值。
- **先建实体再建关系**，否则关系弹窗的起点/终点下拉里选不到 Person/Organization/IndustryNode。

## Step 3 绑来源表（全绑在 gkx_lite 一个数据源上）

点法：列表找到该 Schema 的行 → 操作列 **「···」→「来源表」** → 弹窗里 **「＋ 绑定来源表」** 逐行加：数据源/库/表按下表选 → **主键列自动带出且正确，直接用**；**时间列要手动选 `updated_time`**（见下）→ **「保存绑定」** → toast「来源表绑定已保存」。注意：**保存绑定不会自动触发抽取**，抽取在 Step 5；保存后弹窗不自动关，点右上 × 即可。

| Schema | 数据源→库 | 表（行数） | 主键列（自动带出，2026-10-18 实存值） | 时间列（手选） |
|---|---|---|---|---|
| Paper | → `gkx_lite` | `dwd_zh_paper`(10) | id | updated_time |
| Journal | → `gkx_lite` | `dwd_zh_journal`(5) | pk_id | updated_time |
| IndustryChain | → `gkx_lite` | `dwd_industry_chain_info`(10) | pk_id | updated_time |
| IndustryNode | → `gkx_lite` | `dwd_industry_chain_info`(10) | pk_id | updated_time |
| Organization | → `gkx_lite` | `dwd_org_base_info`(6) | dwd_id | updated_time |
| Person | → `gkx_lite` | `dwd_scholar`(6) | dwd_id | updated_time |
| Person | → `gkx_lite` | `dwd_zh_author`(19) | pk_id | updated_time |
| PUBLISHED_IN | → `gkx_lite` | `dwd_zh_paper`(10) | id | updated_time |
| AUTHORED_BY | → `gkx_lite` | `dwd_zh_author`(19) | pk_id | updated_time |
| BELONGS_TO_NODE | → `gkx_lite` | `dwd_org_industry_chain_dtl`(8) | chain_code（复合主键取首列） | updated_time |

某行没选完整（数据源/库/表缺一）就点保存会被拦：toast「存在未选择完整的来源表绑定（数据源/库/表均需选择）」。几条说明：

- **时间列要手动点选**（2026-10-18 实测产品缺陷）：选完表后「主键列」会自动纠正成表里真实主键，但「时间列」**自动带出的常是空**，直接保存会存成空串——增量水位列就没了。正确姿势：每行加完后把时间列下拉手动选 `updated_time` 再保存。
- **主键列不参与普通表的读取翻页**（普通表按 LIMIT/OFFSET 读，主键列只是记录；时间列才是增量水位用），带出什么用什么即可。
- **绑定不用绑全**（上表每个 Schema 只绑 1~2 张）：绑几张表就抽几张表的数据，少绑只是数据少，链路照跑。Person 只求跑通可只绑 `dwd_zh_author`（少 scholar_org/paper_nums/h_index 属性）。
- **实体和它的关系绑「同族表」最稳**（上表即按此配）：Paper/PUBLISHED_IN 同绑 `dwd_zh_paper`（边端点 `paper_<pk_id>` 与实体同源）、Person/AUTHORED_BY 同绑 `dwd_zh_author`（端点 `person_<author_id>` 同源）。
- 同一张表绑给多个 Schema 是正常的（`dwd_industry_chain_info` 同时绑 IndustryChain 和 IndustryNode）。

## Step 4 传脚本

点法：该 Schema 行 → 操作列 **「更换脚本」**（从未传过时显示「上传脚本」）→ 弹窗里选文件（仅支持 .py）→ 提交 → 应看到「正在上传并校验...」→「**脚本已通过安全校验并保存**」（通道带语法/入口静态检查 + LLM 审核，被拒会给原因）→ 列表「脚本状态」列从「未上传」变「已上传」（跑抽取前带「未运行」角标）。文件取自物料包 `docs/gkx_local_1_materials/scripts/page_test/`（**页面直传精简版**，文件名与下表一致）：

| Schema | 脚本文件 |
|---|---|
| Paper | paper_entity_step.py |
| Journal | journal_entity_step.py |
| IndustryChain | industry_chain_entity_step.py |
| IndustryNode | industry_node_entity_step.py |
| Organization | organization_entity_step.py |
| Person | person_entity_step.py |
| PUBLISHED_IN | published_in_relation_step.py |
| AUTHORED_BY | authored_by_relation_step.py |
| BELONGS_TO_NODE | belongs_to_node_relation_step.py |

> **LLM 审核的三种被拒，处置不同**（2026-10-18 全链路实测：9 个脚本共传 32 次才全过，被拒 29 次）：
> 1. **「LLM 调用失败，未返回结果」且反复出现** → 先去「配置管理 → 语言模型」看**默认**那条配置：点「管理 → 测试」若报 `429 余额不足或无可用资源包(1113)`，是**账户欠费，重传永远无效**——把默认切到一条测试通过的配置（行内「设为默认」开关；「停用/异常/业务空间私有」的配置行内不可切），再回来传。
> 2. **「LLM 调用失败」偶发** → 多为 `429 访问量过大(1305)` 限流，等 20 秒左右重传即可。
> 3. **「内存溢出 / ReDoS / eval/exec / pickle 反序列化 / 闭包无法审计」等具体风险指控** → 对这套模板脚本是**误判**（脚本里根本没有 eval/pickle，同一样本多次校验结论摇摆：Paper 连续 6 次给出 6 种不同理由后第 7 次通过；Person 用了 9 次、BELONGS_TO_NODE 7 次），点「重新选择」重传，通常几次内过。
>
> 根治修复（证据锚定 + 限流区分 + 静态高危回退）在分支 `fix/script-security-evidence-1017`，合入部署后不再需要重试。

「查看脚本」可随时看已传内容；`scripts/` 目录下另有同名的生成版（供 `rebuild_gkx_local.py` 整栈重建用），两版在本文档绑定的来源表上输出逐字段一致；生成版由 `script/tools/build_portable_steps.py` 产出，**勿手改**。

## Step 5 跑抽取（图谱构建 → 新建任务）

1. 左侧导航 **「图谱构建」**（本页就是任务列表）→ 右上 **「新建任务」**。
2. 弹窗里照这个填：
   - 任务名称：随意（如 `精简样例链`）
   - 任务类型：**「多脚本串行」**
   - 「串联 Schema 队列」搜索框依次添加 9 个：IndustryChain、IndustryNode、Journal、Organization、Person、Paper、PUBLISHED_IN、AUTHORED_BY、BELONGS_TO_NODE；用行内 **「上移」「下移」** 排成**先实体后关系**（边要等端点实体先在图里）；至少 2 个、最多 20 个
   - 批大小（对每个 Schema 生效）：`2000`（默认 500；库总共 64 行，500 也一次读完）
   - MySQL 数据源 / 数据库：默认跟随 Schema 绑定，**不用动**
   - 增量游标 since：留空
   - 执行模式：**「一次性」** → 创建。
3. 点任务卡进 **「任务详情」**：每个 Schema 一个抽屉，抽屉里是脚本转换步；上方执行历史看每次触发的终态。
4. 终态怎么读：`COMPLETED` 全部成功；`FAILED` 整链中止（链上任一环失败即中止，修完从失败环重跑）；`ABNORMAL` **≠失败**——抽取完成但有个别失败行转了人工审核，图已写入。
5. 只想跑一个 Schema：任务类型选「单脚本抽取」，选目标 Schema 即可。
6. 新空间首跑即全量；跑完再触发一次是幂等的（水位已高 → 空读快过，不重复写图）。

## Step 6 验收（精确数字）

1. **任务详情**：执行历史终态 `COMPLETED`（或 `ABNORMAL`，个别失败行在「人工审核」里处理，可一键重跑）。
2. **实体列表 / 图统计**：类型逐个切，数量应**精确等于**下表（64 行源数据全量进图，一行不多一行不少）：

| 实体 | 期望数 | 来源 |
|---|---|---|
| Paper 论文 | **10** | dwd_zh_paper 10 行 |
| Journal 期刊 | **5** | dwd_zh_journal 5 行 |
| Person 科技专家 | **6** | dwd_scholar 6 人（author 表 19 行署名的 author_id 均落在 A2026L001–006） |
| Organization 机构 | **6** | dwd_org_base_info 6 行 |
| IndustryChain 产业链 | **2** | IC0101 集成电路产业链、IC0202 人工智能产业链 |
| IndustryNode 产业链节点 | **10** | 2 链×5 节点 |

| 关系 | 期望数 | 来源 |
|---|---|---|
| PUBLISHED_IN | **10** | 每篇论文 1 条（paper.publication_id → J001–J005） |
| AUTHORED_BY | **19** | dwd_zh_author 19 行署名 |
| BELONGS_TO_NODE | **8** | dwd_org_industry_chain_dtl 8 行 |

边计数在页面上从「图谱可视化」的连线数看个大概，精确对账用图库 `SHOW STATS`（8090 直连，空间头 `gkx_lite_1`）。

3. **点开任意一条实体**：属性有值且与源表一致（如 Paper P2026L001 的 doi/volume；Person 的 paper_nums/h_index 来自 dwd_scholar）；溯源列 source_table 指向 `gkx_lite.dwd_*` 表。实体列表页顶部的关键词搜索框搜《轻量级知识图谱构建综述》应唯一命中 `paper_P2026L001`。
4. **图谱可视化**：进页面即自动挑一个有边的实体出图（如期刊「中国科学:信息科学」带 3 条论文发表关系、专家「张守拙」的署名关系），节点可点、关系可展开。注意：**关键词检索起点需要实体索引**——抽取 worker 配了 `SCHEMA_EXTRACT_BUILD_INDEX=0` 的栈（如 8093/yunfei3）不建索引，检索会报「尚未构建实体索引」，且当前部署的页面上没有「重建索引」按钮，只能用自动出图；开了索引的栈（默认 `1`）关键词检索可用。
5. **幂等复跑**：已完成的一次性任务在任务列表**没有「再触发」按钮**（只有 未运行/失败/异常 状态才有「执行/重新执行」），幂等验证就**再新建一个同配置任务跑一遍**——执行很快结束（实测 24 秒）且上表 9 项计数全部不变。
