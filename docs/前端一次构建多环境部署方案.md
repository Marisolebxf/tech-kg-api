# 前端一次构建多环境部署方案（方案 B：运行时注入）

> 状态：**已实施（2026-09-04）**，验证全绿（单测 147 / 双前缀 docker run / 浏览器冒烟 / dev2 回归）。部署前缀确定为 **`/bkg_zpt`**。
> 关联文档：`docs/k8s-deployment.md`（通用 K8s 部署）、`docs/k8s-bkg/K8s部署文档.md`（交付清单）。

## 1. 背景与目标

前端 `VITE_*` 配置目前是**构建期内联**（Vite 把 `import.meta.env.VITE_*` 编译进静态 JS），镜像内 `nginx.conf` 也硬编码 `/bkg_zpt` 前缀——一个环境就要构建一个镜像，改配置必须重新构建。

目标改为"**构建一次、部署多环境**"（业界标准方案 B）：镜像不含任何环境信息，部署时通过**环境变量**注入配置，与后端 `envFrom` ConfigMap 的模型统一。

现状关键事实（决定设计走向）：

- 路由是 history 模式（`frontend/src/router/index.ts:36` 的 `createWebHistory`）。嵌套路由硬刷新时相对 base（`./`）会让浏览器把 `./assets/...` 解析到错误深度 → **base 必须是绝对路径**，不能靠相对引用规避构建期 bake。
- `index.html` 与文档站（VitePress，`frontend/docsite/.vitepress/config.ts`）的资产引用在构建期由 `VITE_BASE` 推导 bake；docsite base = `${appBase}docs/`。
- 镜像运行时只有 nginx + 静态文件，没有进程读环境变量——所以需要启动期注入机制。

## 2. 设计

### 2.1 四个组成部分

1. **哨兵 base**：镜像构建用 `VITE_BASE=/__BASE__/`（绝对、token 唯一）。启动脚本把产物（index.html + dist/docs 的 html/js/css）里的 `/__BASE__/` 全量 `sed` 成真实前缀。本地 dev / compose 构建继续显式传 `VITE_BASE`（`/` 或 `/bkg_zpt/`），哨兵不出现，脚本空跑无害。
2. **runtime-config.js**：nginx 官方镜像的 `/docker-entrypoint.d/` 机制挂启动脚本，从环境变量生成 `window.__RUNTIME_CONFIG__`；`index.html` 在主 bundle 前以 `<script src="%BASE_URL%runtime-config.js">` 加载（构建后即 `/__BASE__/runtime-config.js`，随哨兵一并修正）。
3. **前端统一读取**：新增 `frontend/src/config.ts`，读取链 `window.__RUNTIME_CONFIG__ ?? import.meta.env.VITE_* ?? 默认值`——无 runtime-config 时行为与现状逐字一致（单测不受影响）。
4. **nginx 模板**：`frontend/nginx.conf` → `frontend/nginx.conf.template`，`/bkg_zpt` 前缀参数化为 `${APP_BASE}`。官方镜像 20-envsubst 只替换环境里已定义的变量，`$uri` / `$host` 等 nginx 变量不受影响（`tech-kg-config` 的 key 均为大写，已核对无冲突）。CSP `frame-ancestors` 保持字面量。

### 2.2 环境变量约定

Dockerfile `ENV APP_BASE=/bkg_zpt` 兜底，k8s / compose 可覆盖：

| 环境变量 | 缺省 | 说明 |
|----------|------|------|
| `APP_BASE` | `/bkg_zpt` | 部署前缀，**不带尾斜杠**（nginx location 需要）；脚本内部归一化 |
| `APP_API_BASE` | `${base}api` | API 前缀，即 `/bkg_zpt/api` |
| `TRS_GRAPH_SPACE` | 空 | 与后端同名同源（同一 ConfigMap） |
| `AUTH_ENABLED` | `false` | 与后端同名同源；前端仅显式 `false` 关闭认证 |
| `PORTAL_EMBEDDED_DEFAULT` / `PORTAL_ALLOWED_ORIGINS` / `PORTAL_TARGET_ORIGIN` / `PORTAL_SOURCE` | 空 | 门户 iframe 相关，空串按未设置处理 |
| `ADMIN_EXAMPLE_FALLBACK` | `true` | 管理页示例数据兜底开关 |

k8s web Pod 直接 `envFrom` **同一份** `tech-kg-config` ConfigMap（`docs/k8s-bkg/02-configmap.yaml`）——`TRS_GRAPH_SPACE` / `AUTH_ENABLED` 与后端单一事实来源，不再需要单独的前端配置对象。

### 3.2 compose

- **`docker-compose.dev2.yml`（web-dev2）**：挂载路径 `/etc/nginx/conf.d/default.conf:ro` → `/etc/nginx/templates/default.conf.template:ro`（否则 envsubst 向只读挂载写入失败，nginx 起不来）。dev2 的 `VITE_BASE: /` 构建参数保持。
- 根 `docker-compose.yml` prod `web` **不动**：构建参数继续生效；nginx 模板用 `ENV APP_BASE=/bkg_zpt` 默认渲染出与今天相同的 conf；runtime-config.js 缺省值与今天 bake 值一致。

### 3.3 k8s 交付清单（docs/k8s-bkg/）

- **`02-configmap.yaml`**：新增 `APP_BASE: "/bkg_zpt"`；**`AUTH_COOKIE_PATH`、`AUTH_FRONTEND_URL`、`USER_CENTER_REDIRECT_URI` 三处遗留的 `/bkg_zp` 修正为 `/bkg_zpt`**（现状 cookie 路径与门户实际路径错位会导致登录态丢失）。
- **`23-web.yaml`**：container 加 `envFrom: configMapRef: tech-kg-config`；头部注释改为 `APP_BASE` 运行时注入说明。
- **`K8s部署文档.md`**：前端构建命令去掉全部 `VITE_*` 参数（仅留 NPM_REGISTRY）；"前端构建参数必须与代理路径一致"改为运行时注入说明。
- **`docs/k8s-deployment.md` §3/§5**：同上，构建命令去 `VITE_*`，ConfigMap 示例加 `APP_BASE`。

## 4. 新的构建与推送命令（实施后的目标态）

```bash
REGISTRY=10.50.62.9:30303; TAG=v0.0.1
# 后端不变（api / temporal-worker / m3e-embedding 共用）
docker build -t $REGISTRY/bkg/baked:$TAG \
  --build-arg PYPI_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/ ./backend
# 前端不再传任何 VITE_*——环境差异全部部署期注入
docker build -t $REGISTRY/bkg/baked-web:$TAG \
  --build-arg NPM_REGISTRY=https://registry.npmmirror.com ./frontend
docker push $REGISTRY/bkg/baked:$TAG && docker push $REGISTRY/bkg/baked-web:$TAG
```

## 5. 验证方案

1. **单测/类型/构建**（容器内，见 CLAUDE.md）：builder 阶段 `pnpm vitest run --exclude "src/__tests__/review-full-integration.spec.ts"`；完整 `docker build ./frontend`（`vue-tsc -b && vite build` 挡类型错误）。
2. **镜像运行时行为**（`docker run` + curl）：
   - `-e APP_BASE=/bkg_zpt`：`/` → 302 `/bkg_zpt/`；`/bkg_zpt/` 的资产引用全部 `/bkg_zpt/...` 且 grep 不到 `__BASE__`；`/bkg_zpt/runtime-config.js` 含 `base:"/bkg_zpt/"`、`apiBase:"/bkg_zpt/api"`；`/bkg_zpt/api/...` → 502（无 upstream，证明代理命中）；`/bkg_zpt/docs/` 资产同样带前缀。
   - `-e APP_BASE=`（根路径）同套检查；再叠 `-e TRS_GRAPH_SPACE=dev -e AUTH_ENABLED=true` 验证 env → config.js 透传。
3. **浏览器冒烟**：容器起后打开 `http://127.0.0.1:18088/bkg_zpt/`，不白屏、路由正常、API 请求带 `/bkg_zpt/api` 前缀。
4. **dev2 栈回归**：`docker compose -f docker-compose.dev2.yml up -d --build web-dev2`，验证模板挂载路径变更后 nginx 正常启动、SPA fallback 生效。
5. k8s 清单 `kubectl apply --dry-run=client` 校验；后端零改动无需 pytest。

## 6. 风险与注意

- envsubst 只替换 env 已定义变量；模板中 `$uri`/`$host`/`$scheme`/`$proxy_add_x_forwarded_for` 均不在 env，不受影响。
- `APP_BASE` 约定不带尾斜杠；脚本内部归一化容错（多斜杠也能纠正）。
- 根路径部署（`APP_BASE=`）实测行为与文档 §5.2 的差异：`/` 返回 200 直接服务 SPA
  （模板 302 在空前缀下会自指成环、`${APP_BASE}/api/` 与独立 `/api/` 块重复），
  由启动脚本按块过滤渲染产物修正，`nginx -t` 校验通过。
- 哨兵 `/__BASE__/` 足够独特，误伤风险为零；本地 `vite dev` 不经过哨兵。
- 兼容性：无 runtime-config.js 时逐字回落旧语义（如 `VITE_AUTH_ENABLED === 'false'`），compose 两套栈与单测行为不变。
- **哨兵裸替换仅限 .html**：VitePress 类名（`___BASE___docs_…`）需要裸 `__BASE__` 替换，但 JS 里业务代码
  可能含哨兵字面量（如 config.ts 防泄漏守卫）——曾被全量裸替换改写成 `includes("/bkg_zpt")` 导致
  base 被误判回 `/`、路由视图空白；修复后裸替换只扫 html，守卫字面量拆分拼写（`'__BASE'+'__'`）双保险。
- **门户是剥前缀转发**：edu.itic-sci.com 把 `/bkg_zpt/*` 剥掉前缀后转发到本机 8089（浏览器 URL 带前缀、
  容器收到根路径）。因此 dev2 的 nginx 用根路径全兜底（nginx.dev2.conf 不含 `${APP_BASE}` location），
  `APP_BASE` 仅驱动 runtime-config.js（base=/bkg_zpt、apiBase=/bkg_zpt/api，浏览器侧带前缀）。
  e2e/本地根路径访问走 web-dev2-root（8091，APP_BASE=""）。
- 交付清单 `/bkg_zp → /bkg_zpt` 修正需与统一门户侧的回调白名单（`USER_CENTER_REDIRECT_URI`）同步登记，否则 OAuth 回调不通（仅影响管理端完整 OAuth 流程，门户 iframe cookie 交换不受影响）。
