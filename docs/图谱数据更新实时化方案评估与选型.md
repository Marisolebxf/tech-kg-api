# 图谱数据更新实时化方案评估与选型

> 状态：已评审，选型结论为**维持 watermark 定时增量轮询，缩短调度周期至分钟级**。本文记录完整评估过程与依据，作为后续同类讨论的决策底稿。

## 背景与问题

当前系统支持用户创建实体、上传抽取脚本，由 Temporal 定时调度，脚本按 watermark（`service/script_watermark.py`，类比 Kafka offset 的增量游标）从 MySQL 要素库增量拉数、写图。数据更新非实时。诉求：**在亿级数据规模下让图谱更新尽量实时**。

核心评估问题：要不要引入 trigger / CDC 等变更驱动机制，替代或补充现有的定时轮询？

## 评估过的方案与结论

| 方案 | 结论 | 一句话依据 |
|---|---|---|
| MySQL trigger 触发 | ❌ 否 | trigger 在写事务内同步执行，触发外部脚本会把 OLTP 写入与 ETL 链路耦合；逐行触发无合并削峰能力；工业标准答案是 binlog CDC |
| NebulaGraph 数据库 trigger | ❌ 不存在 | nGQL 无 `CREATE TRIGGER`，也无存储过程，官方长期 feature request 未实现；图侧变更感知只能应用层自建 |
| 写图路径挂钩触发（Python 客户端层） | ❌ 挂错位置 | 脚本子进程持有明文密码可绕开 `ctx.graph` 直连（见`docs/脚本数据访问溯源设计方案.md` 同样的限制），只能观测经过本层的写；真正的写咽喉是 trs-graph-service；且图写大多是 ETL 链路的产物，在下游感知上游变更效率低，主变更源应在 MySQL 侧 |
| 图侧实体/关系变更级联触发（折衷方案） | ❌ 性价比不足 | 实体写图 → 事件 → 定向触发消费该实体的关系脚本，技术上成立且能覆盖"手动建实体"这一轮询盲区；但用户手动创建关系时已显式指定两端实体，若要维持该关系的实时性需持续监听两端实体变化并重新校验，投入产出比不成立（详见下文）；且引入级联防环、事件合并、outbox 等一整套机制 |
| binlog CDC → Kafka | ⏸ 保留为升级路径 | 技术正确（已有 Kafka 基础设施），但引入 Connector 运维、事件路由、防环等复杂度，当前阶段分钟级新鲜度用轮询即可达成，不值得 |
| **分钟级水位轮询（现机制缩短周期）** | ✅ **选型** | 复用现有 watermark + Temporal 调度，零新增基础设施；增量切片查询走索引时成本 O(log n + 变更行数)，与表总量无关，亿级表可承受 |

## 折衷方案（图侧级联触发）的评估记录

该方案的构想的完整形态：

```
实体脚本(分钟级轮询 MySQL) ──写图 Person{ids}──> outbox 事件 ──> 合并去重 ──> 定向触发关系脚本
平台手动建实体 ────────────────────────────────> 同上（轮询盲区，仅此机制可覆盖）
```

技术上可行且有两个真实收益（关系脚本从扫描式变定向式、覆盖手动建实体场景），但最终放弃，决定性理由：

1. **用户手动创建关系时显式指定两端实体**——关系的内容是用户判断的产物，不是自动派生的。若要求"两端实体任一变化就更新该关系"，等于把用户关系降级为派生数据，需要持续监听 + 重校验 + 冲突处理（用户改过 vs 脚本重算谁赢），机制复杂度远超收益。
2. 级联机制附带一整套必须做对的约束：异步 outbox 不阻塞写路径、按 (脚本, ID) 合并去重防风暴、关联路由必须是单向 DAG 防环、事件只带 ID 不带数据、保留低频兜底轮询保最终完整。任何一条缺失都会引入比"不实时"更严重的问题。
3. 它对核心痛点（MySQL 变更尽快反映到图）零贡献——实体新鲜度仍由轮询周期决定，只加速第二跳（实体→关系）。

若未来"手动建实体的关联自动化"成为真实需求，本节记录的 outbox + 合并 + 定向触发设计可直接复用。

## 选型：分钟级水位轮询 + 现有 watermark 机制

### 依据

代码核查确认脚本天然是增量切片模式，轮询成本可控的前提成立：

- `script/load_scholar_entities.py`：`WHERE status = 1 AND update_time > :since` 按水位增量，且已支持 `scholar_id` 定向模式；
- `script/organization_relation_etl.py` `iter_source_rows`：有 `updated_time/update_time` 列时按水位过滤；
- 水位查询走索引时成本 O(log n + 变更行数)，与表总量无关。

### 落地前必须逐表核对的约束（不做则分钟级会在亿级表上翻车）

1. **水位列必须存在且 update 会刷新**。只有 `created_at` 或 update 不刷新该列的表，更新过的行永远扫不到——轮询最常见的静默丢数据点。源表不在本仓库控制下，需逐表确认。
2. **水位列必须有索引**。本仓库 DDL 中唯一有索引的是工作流自有表（`schemas/ddl/manual_review/`），`dwd_scholar` 等要素库源表由上游建表，`update_time` 是否有索引未知。无索引的亿级表每分钟 `WHERE update_time > :since` = 每分钟一次全表扫描。**建议产出审计脚本，遍历所有脚本源表，输出（源表 / 水位列存在 / 有索引）三列清单。**
3. **水位查询加 lookback 重叠窗口**（如 `> watermark - 5min`）+ 幂等 merge 兜底乱序。扫描条件不是裸 `> watermark`。`organization_relation_etl.py` 无水位列时**静默退化全量**（`iter_source_rows`），分钟级调度前必须将此路径改为显式报错/告警并维持低频。
4. **调度错峰 + 禁止自身重叠**：脚本按序号错开相位（避免整点尖峰），Temporal schedule 配置 overlap policy 禁止上轮未完开下轮。有效新鲜度 = 调度间隔 + 脚本耗时，慢脚本间隔放宽，不一刀切。
5. **实体层调度相位先于关系层**（依赖见 `docs/九个业务服务图谱实体关系依赖分析.md`：关系脚本依赖两端实体已存在），配 lookback 窗口兜底匹配竞争。
6. **明确放弃的能力**：轮询感知不到删除（源表删除的行图里永留，需低频全量对账任务或在删除语义重要时升级 CDC）；多表变更无时点一致性（各脚本各自扫描，业务读图需容忍分钟内不同步）。

## 升级触发条件（何时重新考虑 CDC）

出现以下任一情况时，重启 CDC（binlog → Canal/Debezium → Kafka → 事件路由）评估：

- 源表缺 `update_time` 列且上游不配合改造；
- 删除/状态回退语义成为业务硬需求；
- 新鲜度要求进入秒级；
- 轮询的空转扫描在多个亿级表上被证实为 MySQL 显著负载。

届时现有 watermark 机制不废弃：CDC 只替换"何时拉"（时钟 → 事件），脚本仍按水位/ID 集合增量拉数。

## 明确不做（本轮）

- MySQL trigger、图侧任何形式的同步触发；
- 图侧级联触发 / outbox 事件机制（理由见折衷方案评估记录）；
- CDC 及配套的事件路由器、防环 DAG；
- 源表索引改造（仅在审计清单产出后，对确认无索引的表逐个与上游协调）。
