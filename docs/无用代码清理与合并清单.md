## 五、基于目标架构的清理合并（2026-09-14 设计确认）

**设计口径**（用户确认）：用户脚本只从 Schema 管理上传 → 存 S3；执行只经 `kg.schema.extract`——平台按 Schema 创建时绑定的来源表自动分批、按水位增量读取（**读源是 activity**）→ 送入用户实现的 `transform`（**activity step**）→ 平台统一入库：写图/消歧/索引（**入库也是 activity**）。

### 5.0 现状与设计的差距

核心链路**已经实现**：`read_source_batch`（读源）、`execute_transform`（用户函数）、`write_records` + `detect_extract_collisions` + `build_entity_index`（入库）全部是 `SchemaExtractWorkflow` 内的 activity，水位由 `advance_schema_extract_watermark` activity 推进。差距不在主链，而在**还有四条平行的"用户代码进图库"旁路**与之共存：

| 旁路 | 入口 | 问题 |
|---|---|---|
| ① Schema 脚本的 kg.custom.python 化身 | 上传时自动注册（`_register_workflow`） | 同一脚本两份存储两套定义，制造"可单独跑"的假象 |
| ② 工作流系统独立脚本上传 | `POST /definitions/python` / `steps` / `chains` | 与 schema 抽取重复的脚本通道，存共享卷而非 S3 |
| ③ builtin 域工作流 stub 族 | seed 的 9 个 `kg.entity.*`/`kg.relation.*` + `kg.graph.build` | `execute_kg_step` 空壳记账，不做真实 ETL |
| ④ 算子注册表 | `/operators` 上传 + invoke | 进程内执行无隔离无超时，且与图谱构建无关 |
| ⑤ 旧按域大批 ETL | `script/load_*` 手工执行 | 与平台喰抽取双轨维护 |

按下述顺序逐条关闭，最终收敛到单一通道。

### 5.2 D2：下线工作流系统独立脚本上传通道（依赖 D1）
