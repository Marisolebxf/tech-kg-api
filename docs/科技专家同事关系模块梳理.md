# 科技专家同事关系模块梳理

**定位**:判定两位专家是否曾在**同一机构任职**(时间有交集),并给出共同部门、团队、期间成果。核心依据 `AFFILIATED_WITH` 任职边,同事关系按新边(VID 字典序从小到大)生成,判定全程无 LLM/Milvus。

**数据链路**:MySQL `gkx_element`(dwd 层数据)→ ETL 入 trs-graph → 在线查询(`service/expert_colleague_relation.py`,经 graph-search 网关)→ 前端 `/expert-colleague`。

## 一、实体(节点)

| 实体(Tag) | VID 规则 | 关键属性 | 来源表 | 写入脚本 | 作用 |
|---|---|---|---|---|---|
| Person(学者) | `person_{scholar_id}` | name_zh、work_experience_date/department/position | `dwd_scholar`(status=1) | `load_scholar_entities.py` | 查询主体与同事候选 |
| Organization(任职机构) | `org_{org_id}` | name_cn/name_en | 机构域 dwd 表 | `organization_entity_etl.py` | 共同任职点(判定前提) |
| Team/Laboratory/Department/Project | — | name | 已在图中 | 各域脚本 | 共享团队标注 |
| Paper/Patent/Project/Report/Award | `paper_{id}` 等 | title、year | 各域表 | `load_paper_journal_graph.py` 等 | 期间成果展示 |

## 二、直接/间接关系分析

| # | 关系 | 节点及方向 | 直接/间接 | 数据源及关联方式 | 判定理由 |
|---|---|---|---|---|---|
| 1 | 任职 AFFILIATED_WITH | Person → Organization(任职机构) | **直接** | dwd_scholar 任职机构 ID/名称,关联机构表 | 源行明确记录任职事实,按 ID 或规范化名称关联即可,无需 LLM/Milvus |
| 2 | 同事 COLLEAGUE | Person → Person;新边按 VID 字典序从小到大 | **直接** | 任职数据按同一机构自 JOIN,筛选双方任职时间重叠 | 同机构、任职时间交集均可从已有字段计算;经过机构两跳或业务计算不等于间接关系 |
| 3 | 合著 COAUTHOR_WITH | Person(专家)→ Person(合著专家) | **直接** | dwd_scholar_coauthor:scholar_id、co_scholar_id | 同一行明确记录双方专家 ID,可直接生成关系 |
| 4 | 署名 AUTHORED_BY | Paper → Person(作者) | **直接** | dwd_zh_author / dwd_en_author;或 dwd_scholar_paper_relation | 源记录明确关联论文 ID 与作者/学者 ID,无需模型推断 |
| 5 | 发明人 INVENTED_BY | Patent → Person(发明人) | **直接**(当前自动建边路径) | dwd_patent.inventors,关联人才及机构数据 | 发明人姓名已记录;姓名与任职机构精确一致且候选唯一时建边,可用 JOIN 和过滤复现;歧义进入待复核。该分支不使用 Milvus |
| 6 | 项目负责人 LEADS | Project → Person(负责人) | **直接** | dwd_zh_project / dwd_en_project.project_host | 负责人角色由字段明确记录,规范化姓名匹配唯一人员即可 |
| 7 | 项目参与者 HAS_PARTICIPANT | Project → Person(参与者) | **直接** | dwd_zh_project / dwd_en_project.participants | 展开参与人员名单后关联唯一人员即可,歧义不自动建边 |
| 8 | 共同论文 | Person ↔ Person(业务聚合) | **直接** | 作者/学者论文关联记录按同一 paper_id 自 JOIN | 双方共同署名事实可由源表关联得到;两端需使用同一套专家 ID |
| 9 | 共同专利 | Person ↔ Person(业务聚合) | **直接**(已核实的精确关联路径) | 同一专利关联两位已确认发明人 | 在发明人身份已确认的前提下,按专利 ID 关联即可;未确认候选不算已成立关系 |
| 10 | 共同项目 | Person ↔ Person(业务聚合) | **直接** | 同一项目的负责人、参与者记录 | 展开名单,按项目 ID 自 JOIN 即可得到专家对 |
| 11 | 同部门 | Person ↔ Person(业务聚合) | **直接** | 同机构任职记录比较 work_experience_department_zh 等部门字段 | 在同事成立基础上,比较已有部门字段即可得到 |
| 12 | 共同报告、奖项、团队、实验室、部门节点 | 双方 Person 的共享邻居;基础边方向未统一定义 | **直接** | 双方专家与已有 Report/Award/Team/Laboratory/Department 节点的关联记录,按同一节点 ID 关联并取交集 | 按本次业务口径定义为直接关系;基于已有节点关联记录,通过 JOIN 或共享邻居交集即可得到共同关系,无需 LLM 或 Milvus 分析 |

> 小结:同事模块 12 类关系**全部为直接关系**——均可由一行源数据或多表 JOIN + 确定性过滤计算得到,整条链路不使用 LLM,也不使用 Milvus 做关系判定。
>
> **展示口径**:前端关系页签按边动态判定——命中上表直接关系映射的边,关系类别标"直接关系";未命中映射的其他边,关系类别默认标"间接关系"。

## 三、抽取脚本执行顺序

均在 `backend/` 下执行,先 `export PYTHONPATH=. TRS_GRAPH_SPACE=<空间>`:

| 序 | 命令 | 作用 |
|---|---|---|
| 1 | `script/init_paper_journal_schema.py` | Person 基础 tag DDL |
| 2 | `-m script.organization_entity_etl init-schema` | Organization 全字段 DDL |
| 3 | `-m script.init_graph_schema` | Scholar / EMPLOYED_BY |
| 4 | `-m script.init_scholar_schema` | **AFFILIATED_WITH / COAUTHOR_WITH 边 DDL + Person 索引** |
| 5 | `-m script.organization_entity_etl load --full --write` | 机构顶点(**前置**:后续按机构名 join) |
| 6 | `-m script.load_scholar_entities` | 学者 Person 顶点(支持 `--mode incremental`) |
| 7 | `-m script.load_scholar_relations --skip-studied-at` | **写 AFFILIATED_WITH + COAUTHOR_WITH**(`--dry-run` 可干跑) |
| 8 | `-m script.load_paper_journal_graph` | Paper + AUTHORED_BY(共同论文/署名) |
| 9 | `-m script.load_patent_graph` / `-m script.load_patent_relations` | Patent + INVENTED_BY(共同专利/发明人) |
| 10 | `-m script.init_project_schema` + `-m script.load_project_graph` | Project + LEADS / HAS_PARTICIPANT(共同项目) |

## 四、业务伪码

```text
【ETL 离线】load_scholar_relations.load_affiliations / load_coauthors
FOR 学者 s IN dwd_scholar WHERE status=1:
    org ← s.scholar_org_id 定位,否则 scholar_org_name_zh 按名匹配已入图 Organization
    IF org 未命中: 跳过,不建桩        # 置信度: 有ID=source_primary_key / 仅名匹配=placeholder
    写边 person_{s.id} -[AFFILIATED_WITH {任职时间,部门,职位,置信度,血缘}]-> org
FOR 合作记录 IN dwd_scholar_coauthor:
    写边 person_a -[COAUTHOR_WITH {co_paper_count, 血缘}]-> person_b

【在线查询】POST /api/v1/kg-service/expert-colleague-relation
输入: expert_a_id, expert_b_id [, start_time/end_time]

expertA/expertB ← resolve_person(两个ID)                  # 并行解析并校验非同一人
affiliations ← expertA 出向 AFFILIATED_WITH 边(机构+时间区间+部门)
coauthor     ← expertA 的 COAUTHOR_WITH 边                  # 仅统计
context      ← expertA 一跳邻域(成果/团队节点)

FOR 每个任职点 aff IN affiliations:                       # 只认直接同机构,不展开上下级机构
    同批人 ← 机构 aff 入向 AFFILIATED_WITH 边对端
    FOR 候选 c IN 同批人 WHERE c ≠ expertA(双人模式则 c == expertB):
        overlap ← 月序号区间交集(expertA任职期, c任职期)   # "至今"→当前年月;缺时间→计入待复核
        IF 无交集: continue                               # 请求时间只筛选不截断生效时段
        同部门 ← 双方 work_experience_department_zh 归一化相等
        团队   ← 双方共同邻接 Team/Laboratory/Department/Project 节点(共享邻居交集)
        成果   ← 双方共同邻接 Paper/Patent/Project 且年份 ∈ overlap
        置信度 ← 0.42(同机构)+≤0.22(重叠时长)+0.12(同部门)
               +≤0.12(合著)+0.05(共享团队)+≤0.05(成果)   # 上限0.98
    同一候选多个共同任职点 → 合并(任职史去重拼接,取最高置信度)

输出: { expert, targetExpert, colleagues[], summary, graph{nodes,edges}, rules }
      图谱 = 专家—同事"同事关系"边 + 双方→共同机构 AFFILIATED_WITH 边 + 期间成果节点
```

## 五、使用方式

- **脚本**:按表三顺序执行;重跑幂等(rank@0);部署后自检 `AFFILIATED_WITH` 边数 > 100。
- **API**:`POST /api/v1/kg-service/expert-colleague-relation`(参数 `expert_a_id`/`expert_b_id`);模块描述 `GET /api/v1/kg-construction/expert-colleague-relations`。
- **前端**:路由 `/expert-colleague`;测试参数下拉来自 `GET /kg-construction/options`。
