# 科技专家校友关系模块梳理

**定位**:判定两位专家是否**毕业于同一院校**,细分"同校/同学历/同期"维度并汇总后续互动。核心依据 `STUDIED_AT` 就读边 + Person 教育属性,**仅查询返回,不写 ALUMNI 边**,判定全程无 LLM/Milvus。

**数据链路**:MySQL `gkx_element`(教育字段)→ ETL 入 trs-graph → 在线查询(`service/expert_alumni_relation.py`,直连 TRSGraphClient)→ 前端 `/expert-alumni`。

## 一、实体(节点)

| 实体(Tag) | VID 规则 | 关键属性 | 来源表 | 写入脚本 | 作用 |
|---|---|---|---|---|---|
| Person(学者) | `person_{scholar_id}` | education_background_institution_zh/en、degree_zh/en、date、education_background_zh/en(blob) | `dwd_scholar`(status=1) | `load_scholar_entities.py` | 查询主体与校友候选 |
| Organization(院校) | `org_{org_id}` | name_cn/name_en | 机构域 dwd 表 | `organization_entity_etl.py` | 共享院校(同校判定) |
| Paper/Patent/Project | `paper_{id}` 等 | title、publication_date/year | 各域表 | `load_paper_journal_graph.py` 等 | pair 模式展示共同成果 |

## 二、直接/间接关系分析

| # | 关系 | 节点及方向 | 直接/间接 | 数据源及关联方式 | 判定理由 |
|---|---|---|---|---|---|
| 1 | 就读 STUDIED_AT | Person → Organization(院校) | **直接** | dwd_scholar.education_background_institution_zh/_en 等结构化教育字段,关联院校名称 | 就读事实由源字段明确记录,当前使用名称精确/小写匹配,无需向量分析 |
| 2 | 校友(不写 ALUMNI 边) | Person ↔ Person,仅展示 | **直接** | 双方教育院校字段自 JOIN,规范化后比较相等或包含 | 当前同校规则可表达为确定性查询条件,无需 LLM/Milvus;名称包含可能误匹配属于数据质量问题 |
| 3 | 合著 COAUTHOR_WITH | Person(专家)→ Person(合著专家) | **直接** | dwd_scholar_coauthor:scholar_id、co_scholar_id | 同一行明确记录双方专家 ID,可直接生成关系 |
| 4 | 署名 AUTHORED_BY | Paper → Person(作者) | **直接** | dwd_zh_author / dwd_en_author;或 dwd_scholar_paper_relation | 源记录明确关联论文 ID 与作者/学者 ID,无需模型推断 |
| 5 | 发明人 INVENTED_BY | Patent → Person(发明人) | **直接**(当前自动建边路径) | dwd_patent.inventors,关联人才及机构数据 | 发明人姓名已记录;姓名与任职机构精确一致且候选唯一时建边,可用 JOIN 和过滤复现;歧义进入待复核。该分支不使用 Milvus |
| 6 | 项目负责人 LEADS | Project → Person(负责人) | **直接** | dwd_zh_project / dwd_en_project.project_host | 负责人角色由字段明确记录,规范化姓名匹配唯一人员即可 |
| 7 | 项目参与者 HAS_PARTICIPANT | Project → Person(参与者) | **直接** | dwd_zh_project / dwd_en_project.participants | 展开参与人员名单后关联唯一人员即可,歧义不自动建边 |
| 8 | 共同论文 | Person ↔ Person(业务聚合) | **直接** | 作者/学者论文关联记录按同一 paper_id 自 JOIN | 双方共同署名事实可由源表关联得到;两端需使用同一套专家 ID |
| 9 | 共同专利 | Person ↔ Person(业务聚合) | **直接**(已核实的精确关联路径) | 同一专利关联两位已确认发明人 | 在发明人身份已确认的前提下,按专利 ID 关联即可;未确认候选不算已成立关系 |
| 10 | 共同项目 | Person ↔ Person(业务聚合) | **直接** | 同一项目的负责人、参与者记录 | 展开名单,按项目 ID 自 JOIN 即可得到专家对 |
| 11 | 同学历校友 | Person ↔ Person(业务维度) | **直接** | 同校教育经历中的学位字段归一化后比较 | 同校前提下,非空学位文本相等即可得到,不做学位语义推断 |
| 12 | 同期校友 | Person ↔ Person(业务维度) | **直接** | 同校教育经历的年份区间求交集 | 年份相交可通过条件计算得到;缺失时间不能认定同期 |

> 小结:校友模块 12 类关系**全部为直接关系**——同校判定与维度细分均为确定性字符串/年份计算,互动统计为图上共享邻居交集;整条链路不使用 LLM,也不使用 Milvus 做关系判定。
>
> **展示口径**:前端关系页签按边动态判定——命中上表直接关系映射的边,关系类别标"直接关系";未命中映射的其他边,关系类别默认标"间接关系"。

## 三、抽取脚本执行顺序

均在 `backend/` 下执行,先 `export PYTHONPATH=. TRS_GRAPH_SPACE=<空间>`:

| 序 | 命令 | 作用 |
|---|---|---|
| 1 | `script/init_paper_journal_schema.py` | Person 基础 tag DDL |
| 2 | `-m script.organization_entity_etl init-schema` | Organization 全字段 DDL |
| 3 | `-m script.init_graph_schema` | Scholar / EMPLOYED_BY |
| 4 | `-m script.init_scholar_schema` | **STUDIED_AT 边 DDL + Person tag 索引** |
| 5 | `-m script.organization_entity_etl load --full --write` | 机构/院校顶点(**前置**:院校名 join 依赖) |
| 6 | `-m script.load_scholar_entities` | 学者 Person 顶点(教育属性随节点入图) |
| 7 | `-m script.load_scholar_relations` | **默认边集含 STUDIED_AT**(同时写 AFFILIATED_WITH/COAUTHOR_WITH;`--dry-run` 干跑) |
| 8 | `-m script.load_paper_journal_graph` | Paper + AUTHORED_BY(共同论文/署名) |
| 9 | `-m script.load_patent_graph` / `-m script.load_patent_relations` | Patent + INVENTED_BY(共同专利/发明人) |
| 10 | `-m script.init_project_schema` + `-m script.load_project_graph` | Project + LEADS / HAS_PARTICIPANT(共同项目) |

## 四、业务伪码

```text
【ETL 离线】load_scholar_relations.load_studied_at
FOR 学者教育记录 IN dwd_scholar.education_background_*:
    org ← 院校名(institution_zh/en)按名匹配已入图 Organization
    IF 未命中: 跳过,不建桩                    # 置信度 = placeholder_org_name_match
    写边 person_{id} -[STUDIED_AT {degree, education_date, institution, 血缘}]-> org

【在线查询】POST /api/v1/kg-service/expert-alumni-relation
输入: expert_id [, target_expert_id 双人模式] [, school, education_stage, limit]

source_edus ← 解析 expert 教育属性
              (结构化字段 + education_background_zh/en blob → JSON/分号切分
               → {institution, degree, date},按(院校,学位,时间)去重)

候选获取:
  双人模式: candidates ← [target]
  列表模式: org_vids ← expert 出向 STUDIED_AT 指向的院校(可按 school 参数过滤)
                     ∪ (无边时: 教育院校名 → Organization 名索引匹配)
           candidates ← 院校入向 STUDIED_AT 边对端 Person    # 禁止全量 Person 扫描
           仍为空 → LOOKUP ON Person(education_background_institution 索引)兜底

FOR 候选 c IN candidates:
    cand_edus ← 解析 c 教育属性
    同校 ← 双方任一教育记录 institution NFKC 归一化后相等/互含
    IF 非同校: continue                                     # 同校是必要条件,不编造院系/导师
    维度 ← [同校] + (学位非空且归一相等→同学历) + (教育年份区间相交→同期)
    互动 ← 双方 COAUTHOR_WITH 边 + 共同邻接 Paper/专利/项目计数
           (经 AUTHORED_BY / INVENTED_BY / LEADS / HAS_PARTICIPANT 边)
    置信度 ← 0.70(同校)+0.08(同学历)+0.12(同期)
           +0.04/0.02/0.02(论文/专利/项目互动)+0.02(字段完整度)   # 上限0.98

输出: { expert, targetExpert, mode: pair|list, total, items[{校友, sharedInstitutions,
        dimensions, educations, interactions{summary, sharedAchievements}, confidence, provenance}],
        dimensionsCatalog, sourceMeta, summaryRows, graph{nodes,edges} }
      图谱 = 专家—校友"校友关系"边 + pair 模式共同成果节点;不回写 ALUMNI 边
```

## 五、使用方式

- **脚本**:按表三顺序执行;重跑幂等;院校未入图会整体跳过(覆盖率取决于机构域灌入的院校数量)。
- **API**:`POST /api/v1/kg-service/expert-alumni-relation`(参数 `expert_id`,兼容 `POST /api/v1/kg-construction/expert-alumni-relations/query`);模块描述 `GET /api/v1/kg-construction/expert-alumni-relations`。
- **前端**:路由 `/expert-alumni`;结果含"摘要/结果/规则/溯源/图谱"多 Tab,溯源按 graphVid 逐节点给出证据。
