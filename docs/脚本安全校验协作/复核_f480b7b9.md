## P2 SEC-LIFETIME 取消标志也被延后到守护线程

位置：[script_security.py:381](https://github.com/Marisolebxf/tech-kg-api/blob/f480b7b9/backend/service/script_security.py#L381)、[llm.py:110](https://github.com/Marisolebxf/tech-kg-api/blob/f480b7b9/backend/infra/llm.py#L110)。

超时分支调用 `Thread(target=aborts.cancel, daemon=True).start()`；`_cancelled=True`在cancel方法内部才设置。因此调用者只是启动清理线程，没有在返回前完成逻辑取消。操作系统若尚未调度清理线程，晚完成初始化的工作线程仍可register成功并调用SDK create。锁只保证cancel和register已经执行时互斥，不能保证cancel先于返回发生。

Codex使用f480b7b9原始模块，模拟SDK及传输构造器，以事件控制两个工作线程的交错，没有访问真实端点，也没有执行危险源码：

1. 将专属传输构造暂停在register之前，阶段预算临时设为0.06秒。
2. 控制名为llm-review-abort的清理线程在实际调用cancel之前等待事件，模拟它尚未获得调度；其他线程正常运行。
3. 调用约0.062秒返回unavailable_stage_deadline，此时构造已进入，模拟请求计数为0，cancel尚未执行。
4. 在继续暂停清理线程的同时释放传输初始化；register返回成功，模拟SDK create被调用，请求计数变为1。
5. 再释放取消线程完成清理，线程收尾及槽位恢复。

这是确定性交错测试，不是线上已发生该调度的记录。它复现的仍是上轮提出的“调用者放弃后迟登记并发起请求”，不是新增无关需求。GLM已有“handle预先cancel后再register”测试和当前容器探针没有固定这次交错，不能证明该窗口不存在。

最小修正方向：将**设置取消标志/取出待关闭传输**与**可能阻塞的连接关闭**分离。超时分支应先在调用线程里用短锁同步完成逻辑取消，再将待关闭传输交给守护线程；不要把close搬回同步返回路径。迟登记返回False后仍由工作线程关闭其自有传输且不发请求，槽位继续以future真终态为准释放。

新增验证应先暂停清理线程，再让调用者返回，最后释放初始化，并断言请求分派计数为0；在同一设计下保留慢close不阻塞返回、close失败、幂等取消、4槽真终态后恢复等测试。后续还应检查register已成功但SDK构造尚未完成时的取消，以及真正分派前的取消/剩余预算复核，不能仅用预先cancel的句柄测试覆盖全部交错。
