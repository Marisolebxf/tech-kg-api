# 脚本数据访问溯源（access report）+ 前端移除"选择数据表"设计方案

> 状态：已评审通过的设计方案，未实施。

## 背景与动机

用户上传的抽取脚本通过 `kg_sdk.Context` 拿到 mysql/graph/milvus/llm/embedding 客户端，可以访问任意数据库表。当前存在两个问题：

1. **Schema 创建表单里的"来源表"勾选（`mappings`）只是静态声明**，不驱动任何执行逻辑——没有任何 ETL/抽取脚本读它来决定查哪张表；且来源表清单查的是 workflow 库的 `information_schema`，与脚本实际连接的库（触发时 `mysql_datasource_id` 选择的 MySQL 数据源）完全脱节。
2. **平台无法回答"脚本实际访问了哪些表"**——数据溯源只能靠人读脚本代码。

目标：

1. **观测式溯源**：在 SDK 构造客户端处无侵入挂钩，记录脚本实际访问的 MySQL 表 / graph tag·edge / Milvus collection / LLM·embedding 调用，随 step 结果回传持久化，前端展示。crash-safe：脚本超时/失败也要留账。
2. **前端移除"选择数据表"交互**；后端保留 `mappings` 字段（可选、默认空），系统预置 schema 的血缘展示不受影响。
3. 覆盖范围：**全部五类资源**（mysql / graph / milvus / llm / embedding）。

已确认的设计取舍：

- SQL 解析用 **sqlglot**（新增依赖），能准确处理 JOIN / 子查询 / CTE / INSERT INTO / 别名；解析失败降级记原文，绝不让脚本报错。
- 这是**观测，不是管控**：脚本进程持有明文密码与完整环境变量，可绕开 `ctx.mysql` 直连。表级 ACL 需网络层方案（子进程只允许访问代理端口），另行立项。

## 实施步骤

### 1. 依赖

`backend/pyproject.toml` 加 `sqlglot>=26`，`uv sync`。

### 2. SDK 采集层（backend/sdk/kg_sdk.py 或拆 sdk/access.py）

新增访问采集器：

- 模块级 `_ACCESS` 汇总结构：

```python
{
  "mysql":     {db: {table: {"ops": set, "statements": int}}},
  "graph":     {kind(tag/edge): {name: {"ops": set, "count": int}}},
  "milvus":    {collection: {"ops": set, "count": int}},
  "llm":       {model: {"calls": int, "failures": int}},
  "embedding": {model: {"calls": int, "failures": int}},
}
```

- **sidecar JSONL**：路径读 `KG_ACCESS_LOG` env（activity 传临时文件路径）；每条事件 append（open→write→close，保证 crash-safe）。这是超时/崩溃路径留账的关键——**超时被 kill 的脚本恰恰最需要溯源**。
- `record_mysql_statement(sql)`：sqlglot `parse_one` 提取表（含 JOIN/子查询/CTE/INSERT INTO/UPDATE），失败降级记 `_unparsed` 计数 + 最近一条原文片段；操作类型按 expression 类型映射（SELECT/INSERT/UPDATE/DELETE/DDL）。
- `Context.mysql`：构造 `MySQLClient` 后主动 touch `client.engine` 并挂 `sqlalchemy.event.listen(engine, "before_cursor_execute", ...)`——不管脚本用 ORM、`text()` 还是裸 SQL 字符串，最终都走 cursor execute，`statement` 参数就是原始 SQL。回调整体 try/except 包死，绝不影响脚本。
- `Context.graph`：返回轻量代理 `ObservedGraphClient`：
  - `__getattr__` 转发原客户端；
  - 方法名→读写方向表：`get_*`/`find_*`/`list_*`/`node_count`/`edge_count`/`labels`/`edge_types` = read，`create_*`/`merge_*`/`update_*`/`delete_*`/`batch_*` = write；
  - 从 kwargs/args 取 `labels`/`label`/`edge_type` 记录访问对象；
  - `execute_query/read/write` 裸 nGQL：记 op + query 片段到 `_ngql` 桶。
- `Context.milvus`：`ObservedMilvusClient` 代理，从 `collection_name` 参数记 collection，读写按方法名（query/search/get/list = 读，insert/upsert/delete = 写）。
- `Context.llm`/`embedding`：代理记录模型名 / 调用次数 / 成败（`synthesize` 失败也计）。
- `access_report() -> dict`（汇总，ops set 转 sorted list）+ `reset_access_report()`（测试用，与现有 `reset_current_context` 对称）。

### 3. Runner 回传（service/temporal_workflows.py 两处内联 runner）

runner 在 `fn()` 外包 try/finally：

- 正常路径：`print(json.dumps({"result": result, "_access": access_report()}))`；
- 异常路径：stderr 输出前先落 sidecar（finally 保证）。

activity 侧：

- `tempfile.NamedTemporaryFile` 路径经 `KG_ACCESS_LOG` env 传给子进程；
- stdout 解析后 `output.pop("_access")`（镜像 `_strip_watermark_meta`）；
- 进程结束后（含 `TimeoutError` kill、非零退出码分支）读 sidecar，与 stdout 报告合并去重（sidecar 为准）；
- step 返回值加 `"access"`：`{"step","status","output","attempt","access"}`；
- access 处理全程 fire-and-forget（仿 `pendingReview`：任何异常仅 `logger.warning`，绝不阻塞 step）。

### 4. Workflow 层

`StepPipelineWorkflow._steps[step_id]` 增存 `"access"`（L629-633）；`get_steps` query 自动带出。`execute_python_script` 返回值同样加 `access`。

### 5. 持久化与 API（零 schema 变更）

- `execution["output"]` 已随 workflow 结果整体落库（payload JSON），steps 里含 access，无需改 repository / 不新建表。
- 前端类型 `WorkflowExecution`/`PipelineStepInfo` 加 `access?` 字段即可。

### 6. 前端 — 移除"选择数据表"

- `SchemaBrowserView.vue`：删 checkbox 块、`toggleSourceTable`、`CreateForm.sourceTables`、`.source-table-*` CSS；`loadSourceTablesAndLlmConfigs` 改名只拉 LLM 配置；payload 里 `mappings` 改发 `[]`。**保留**列表列对服务端 `mappings`/`attributeSource` 的展示（系统预置 schema 的血缘仍可见）。
- `api/schemaManagement.ts`：`EntitySchemaCreatePayload.mappings` 改可选；删 `SourceTable` 类型与 `listSourceTables`。
- `JobLaunchDialog.vue`：删"来源表"hint。
- 后端清理：删 `GET /schema-management/source-tables` 接口（handler + service + application 转发三层）。

### 7. 前端 — 溯源展示

- `api/workflowOperations.ts`：新增 `AccessReport` 类型（mysql/graph/milvus/llm/embedding 各桶）；`PipelineStepInfo` 加 `access?`。
- `ProcessInstanceDetailView.vue` io tab：step 选中后在 input/output JSON 下方加"实际访问资源"chips 区——MySQL 表 `db.table` + ops 徽标（R 蓝 / W 橙）+ 次数；graph tag/edge；milvus collection；llm 模型 `calls/failures`。无 access（旧执行记录）不显示。
- `GraphBuildView.vue` 详情面板：execution 级聚合（客户端从 `output.steps` 各 step access 合并去重）同款 chips。
- `TaskCenterView.vue` 脚本执行 dialog 的 raw JSON 保持不动（access 已含其中）。

### 8. 测试

- `tests/unit/test_kg_sdk.py` 扩展（复用 fake 注入模式）：
  - `record_mysql_statement`：SELECT/JOIN/子查询/INSERT 解析 + unparsed 降级；
  - `Context.mysql` 挂钩后用 SQLite engine 执行语句断言记录（`before_cursor_execute` 对 SQLite 同样触发，无需真 MySQL）；
  - graph/milvus 代理转发 + 记录；
  - `access_report()` 汇总 + sidecar 写入（`tmp_path` + `KG_ACCESS_LOG` env）。
- 新增 `tests/unit/test_step_access.py`：把 activity 的"sidecar 合并 + pop `_access`"抽成小函数（如 `_merge_access(stdout_output, sidecar_path)`）直接单测，超时路径用伪造 sidecar 验证。
- 前端 `pnpm build`（vue-tsc 类型检查）。

## 明确不做（本轮）

- **表级 ACL / 网络管控**——观测不是管控；脚本可绕开 `ctx.*` 直连（持有明文密码），真管控需网络层代理 + ACL，另立项。
- **声明 vs 实际对账**——`mappings` 已保留为可选字段，后续可做"声明了哪些表 vs 实际访问了哪些表"的差集警示展示（类似 app 权限清单）。
- **独立 access 明细表**——随 execution payload JSON 走，够用。
