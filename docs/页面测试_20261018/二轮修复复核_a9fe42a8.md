## [P1] 取消协程会提前释放仍在运行的写线程所需的锁

位置：backend/service/temporal_workflows.py:2372–2373；backend/service/entity_write_guard.py:309–316。

`asyncio.to_thread(_write_all)` 的等待者被取消时，同步线程不会随之停止。当前上下文管理器随即取消续期心跳并释放 VID 锁，但线程仍可能持有取消前 FETCH 的旧快照继续 INSERT。

独立探针 test_cancelled_activity_must_not_unlock_running_write_thread：

1. A 读取旧属性后在线程内暂停。
2. 取消 A 的异步活动，确认锁已释放。
3. B 获取相同 VID 锁并成功写入 h_index=5。
4. 恢复 A 的线程，A 用旧快照写入 scholar_org。
5. 最终 h_index 消失，断言实际得到 None 而不是 5。

建议：让工作线程生命周期与持锁生命周期绑定。取消时先阻止继续派发写入，并等待已启动的线程/请求安全收尾，再释放锁和关闭图客户端；收尾期间仍须正确维护租期。仅给 to_thread 加 shield、但不等待工作线程结束就释放锁，并不能修复。

## [P1] 已观察到租期丢失，当前 chunk 的重试仍会再次派发 INSERT

位置：backend/service/temporal_workflows.py:2250–2299、2332；_with_watermark_retry 位于 1770 起。

丢失标记只在 chunk 外层检查。`_with_watermark_retry(lambda: client.execute_write(stmt))` 的内部重试，以及未知列自愈和逐条回退，没有在每次实际发送前检查失锁状态。

独立探针 test_lease_loss_must_stop_current_chunk_retry：第一次 INSERT 抛 high watermark，重试等待期间心跳返回续期失败；等待结束后仍发生第二次 INSERT。最终退出才抛“租期丢失”，不能撤销这次写入。探针期望仅一次尝试且零成功写入，实际为两次尝试、一次成功写入。

建议：把租期/取消检查放到每次实际发送前，覆盖重试、未知列自愈、批量回退逐条路径。失锁后退出旧快照重试；重新获取锁必须重新 FETCH 合并。已发出但未完成的请求还需结合上一项处理，不能把退出抛错或整批重试当作此前写入已回滚，也不能仅凭幂等性证明并发属性不丢失。
