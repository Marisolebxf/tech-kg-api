# 【人工处理】界面设计思路技术方案

## 1. 定位与目标

**人工处理不是独立业务系统，而是图谱构建 Pipeline 的异常治理出口。**

Pipeline 在质量校验、对齐消歧、Schema 映射等节点失败或低置信时，将数据**隔离**并生成「处理实例」；人工在本平台完成裁决后，按约定**回写结果并从阻断节点重跑**，而不是另起一套审核流程。

| 角色 | 诉求 |
|------|------|
| 审核/治理人员 | 快速看懂「卡在哪、为什么、怎么判、判完会怎样」 |
| 建图/运维 | 批次级阻断可恢复公共流程；任务级隔离不拖垮整批 |
| 产品/研发 | 异常类型可扩展：队列统一，详情按模板分支 |

**一句话目标**：让人在一屏证据内做完裁决，并明确后果（回写目标 / 重跑锚点 / 影响范围）。

---

## 2. 设计原则

1. **Pipeline 从属，不另起炉灶**  
   入口可来自任务中心、处理实例详情、顶栏异常铃；列表展示的是「阻断节点」，不是抽象工单类型。

2. **证据 → 裁决 → 后果** 三段式  
   详情页固定三步，避免「先点通过再发现影响整批」。

3. **按裁决形态分模板，不按业务域堆页面**  
   7 种决策形状覆盖多数异常（见 §3）；队列壳统一，详情按 `templateId` 分支。

4. **影响范围优先于异常类型**  
   待处理队列：**批次级阻断**排在任务级隔离之前，视觉上强提示「已阻断」。

5. **裁决可沉淀为规则（可选）**  
   映射/别名/去重策略可勾选「写入字典或规则」，同类异常后续自动处理；不强制。

6. **可审计、可回看**  
   待处理可编辑；已完成/已撤销只读展示决策与备注；支持撤销与重试。

---

## 3. 模板收敛为 7 种决策形状

异常类型可以很多，但人工真正要做的**决策形状**只有 7 种。界面按模式渲染，不按业务域复制页面。分类 / 阻断节点由 `pipelineStep` 推导，与模式解耦（实现：`manual-review-data.ts` 的 `getReviewTemplateId` / `resolvePipelineStep`）。

### 3.1 七种模式一览

| 模式 | 决策形状 | 说明 |
|------|----------|------|
| `T_MAP` | 选目标值 | 字段/字典映射与实体类型修正（同一模式，数据驱动） |
| `T_DQ_FILL` | 补全 | 必填缺失 |
| `T_DQ_MERGE` | 定主合并 | 唯一性冲突 |
| `T_LINK` | 是否同一实体 | 对齐消歧 |
| `T_EVIDENCE` | 证据够不够 | 关系入图 |
| `T_ATTR` | 选权威来源 | 属性冲突 |
| `T_RUNTIME` | 运行处置 | 超时 / LLM / 兜底 |

未识别类型一律兜底 `T_RUNTIME`，保证队列永远可进。

### 3.2 与【图谱构建】流水线节点的对应

【图谱构建】主链节点（工作台 / 处理实例口径）为：

```text
读取结构化数据
  → 字段映射入 Schema（Schema 映射）
  → 大模型抽取（实体关系抽取）
  → 实体对齐消歧
  → 规则验证与证据回链（质量校验）
  → 结果入库与异常分流（图谱入库）
```

规范 stepId：`schema` / `extract` / `align` / `validate` / `persist`（阶段均为「图谱构建」）。  
上游「数据处理」还有 `source`（数据接入）、`normalize`（清洗标准化），部分模板会在入图前就阻断。

| 模式 | 决策形状 | 主要阻断 / 重跑节点 | 所属阶段 | 图谱构建节点说明 |
|------|----------|---------------------|----------|------------------|
| `T_MAP` | 选目标值 | **Schema 映射**（`schema`）；字典/枚举类也可落在**清洗标准化**（`normalize`） | 图谱构建为主；字典子形态偏数据处理 | 对应工作台「字段映射入 Schema」：源字段对 Schema 属性失败、实体类型判错 → 选目标值后从本节点重跑 |
| `T_DQ_FILL` | 补全 | **清洗标准化**（`normalize`） | 数据处理 | **不在图谱构建主链**；必填缺失在入图前拦截。补全后重跑标准化，再进入 Schema / 抽取 |
| `T_DQ_MERGE` | 定主合并 | **清洗标准化**（`normalize`） | 数据处理 | **不在图谱构建主链**；唯一性冲突在标准化阶段定主合并后再入图 |
| `T_LINK` | 是否同一实体 | **实体对齐消歧**（`align`） | 图谱构建 | 对应工作台「实体对齐消歧」：候选与存量歧义 / 低置信 / 对齐超时 → 合并、新建或驳回后从对齐节点重跑 |
| `T_EVIDENCE` | 证据够不够 | **质量校验**（`validate`） | 图谱构建 | 对应工作台「规则验证与证据回链」：关系证据不足、关系类型置信度不足 → 确认入图 / 保持隔离 / 驳回抽取 |
| `T_ATTR` | 选权威来源 | **质量校验**（`validate`） | 图谱构建 | 同属「规则验证与证据回链」：属性多源冲突 → 择优或手工改写后从校验节点重跑 |
| `T_RUNTIME` | 运行处置 | 默认 **实体关系抽取 / 大模型抽取**（`extract`）；亦可挂任意失败节点 | 图谱构建（常见） | 对应工作台「大模型抽取」：输出格式错误、抽取超时、配置异常 → 换 Prompt/模型重跑、跳过或升级；未知工单也走本模式 |

### 3.3 按图谱构建节点反查模板

| 图谱构建节点（工作台名） | stepId | 常见转入的人工模式 |
|--------------------------|--------|--------------------|
| 字段映射入 Schema | `schema` | `T_MAP`（字段映射、实体类型修正） |
| 大模型抽取 | `extract` | `T_RUNTIME`（格式错误、超时、配置）；证据不足驳回上游时也会回到本节点重跑 |
| 实体对齐消歧 | `align` | `T_LINK` |
| 规则验证与证据回链 | `validate` | `T_EVIDENCE`、`T_ATTR` |
| 结果入库与异常分流 | `persist` | 一般不直接开模板；高置信入库，低置信/冲突已在上游分流到人工队列。若入库写失败，可兜底 `T_RUNTIME` |

```text
【图谱构建】节点 → 人工模式

字段映射入 Schema ──────────────► T_MAP（选目标值）
大模型抽取 ─────────────────────► T_RUNTIME（运行处置）
实体对齐消歧 ───────────────────► T_LINK（是否同一实体）
规则验证与证据回链 ─┬───────────► T_EVIDENCE（证据够不够）
                   └───────────► T_ATTR（选权威来源）
结果入库与异常分流 ─────────────► （分流入口；写失败兜底 T_RUNTIME）

【数据处理·清洗标准化】（入图前）
  ├─ 必填缺失 ──────────────────► T_DQ_FILL（补全）
  ├─ 唯一性冲突 ────────────────► T_DQ_MERGE（定主合并）
  └─ 字典/枚举映射失败 ─────────► T_MAP（选目标值，重跑锚点可为 normalize）
```

### 3.4 各模式主交互（详情裁决区）

| 模式 | 一句话问题 | 主交互 |
|------|------------|--------|
| `T_MAP` | 源字段/源值对到哪？或类型如何改？ | 映射表 / 类型 radio |
| `T_DQ_FILL` | 如何补全缺失的必填字段？ | 源快照 + 参考建议 + 补录表单 |
| `T_DQ_MERGE` | 哪条是主记录、如何合并字段？ | 主记录 radio + 字段 checkbox |
| `T_LINK` | 候选与存量是否为同一实体？ | 双卡对照 + 合并 / 新建 / 驳回 |
| `T_EVIDENCE` | 现有证据是否足以让该关系入图？ | 证据勾选 + 确认 / 隔离 / 驳回 |
| `T_ATTR` | 冲突属性以哪份来源为准？ | A / B / 手工 / 时间切分 |
| `T_RUNTIME` | 重试、换配置重跑，还是跳过 / 升级？ | 失败摘要 + Prompt/配置选择 |

## 4. 信息架构与路由

```text
侧栏「人工处理」 /manual-review
        │
        ▼
┌───────────────────────────────┐
│ 队列页 OperationsCenterView   │  mode=review
│  指标 · Tab · 分类 chips · 表 │
└───────────────┬───────────────┘
                │ /manual-review/task/:instanceId
                ▼
┌───────────────────────────────┐
│ 详情工作台                     │
│ ManualReviewWorkspaceView     │
│  1 证据 → 2 裁决 → 3 后果     │
└───────────────────────────────┘
```

| 路由 | 组件 | 职责 |
|------|------|------|
| `/manual-review` | `OperationsCenterView` (`mode: review`) | 处理队列：筛选、排序、进入详情 |
| `/manual-review/task/:instanceId` | `ManualReviewWorkspaceView` | 单实例裁决工作台 |

与周边关系：

- **任务中心 / 处理实例**：看流水线步骤；需人工时跳转本平台。
- **异常铃 / 工作台风险条**：深链到 `?batch=` 或详情。
- **Pipeline 算子「人工处理」**：定义分流策略；本界面是运行时落地。

相关实现：

- 路由：`frontend/src/router/index.ts`
- 队列：`frontend/src/views/platform/OperationsCenterView.vue`
- 详情：`frontend/src/views/platform/ManualReviewWorkspaceView.vue`
- 模板与分类：`frontend/src/views/platform/manual-review-data.ts`
- API 封装：`frontend/src/api/workflowOperations.ts`
- 后端：`backend/biz/handler/manual_review.py`

## 5. 队列页设计思路

### 5.1 顶部指标（3 卡）

| 指标 | 含义 | 设计意图 |
|------|------|----------|
| 待处理 | `status === 待处理` | 工作量 |
| 批次级阻断 | 待处理且 P0 / 批次级 | **优先处理池** |
| 历史记录 | 已完成 + 已撤销 | 审计入口 |

不做过多 KPI，避免与「异常治理」告警页混淆（告警偏监控，人工处理偏裁决）。

### 5.2 Tab + 分类 + 筛选

```text
[待处理 N] [历史记录 M]
[全部] [清洗标准化] [Schema 映射] [抽取配置] [实体对齐] [质量校验]
关键词 | 更新批次 | 清空
```

- **Tab**：待办 / 历史分列，切换时重置状态筛选，避免「待处理里混已完成」。
- **处理分类 chips**：短名对齐 Pipeline 阶段（由阻断节点推导，不是模板 ID）；列表「阻断节点」仍展示具体节点名。
- **排序（待处理）**：批次级 → 任务级，再按更新时间倒序。

### 5.3 列表列（一眼能决策）

| 列 | 作用 |
|----|------|
| 处理实例 ID | 主键，直达详情 |
| 待处理对象 | 对象名 + 类型 + 异常子类型 |
| 阻断节点 | 流水线节点名 + 阶段 + 影响范围徽章 |
| 来源记录 | 源表 / 源 ID，便于对照库表 |
| 更新批次 | 与任务中心批次对齐 |
| 处理人 / 状态 / 时间 | 责任与 SLA |
| 操作 | 「进入处理」或「查看记录」 |

深链：`/manual-review?batch=UPD-xxx`、`?tab=history`、`?keyword=`。

## 6. 详情工作台设计思路（核心）

纵向一屏完成，**禁止**把关键裁决塞进侧滑抽屉（早期抽屉方案已弃用）。

```text
┌────────────────────────────────────────────┐
│ 返回 · 标题 · ID / 处理人 / 节点·类型·规则  │
│ [分类] [批次级·已阻断] [状态]               │
├────────────────────────────────────────────┤
│ ① 证据                                      │
│    对象 · 来源 · 系统结论 · 置信度 · 摘要   │
├────────────────────────────────────────────┤
│ ② 裁决 · {模板标题}                         │
│    一句话问题 + 建议                        │
│    【按 §3 七种模式渲染控件区】             │
├────────────────────────────────────────────┤
│ ③ 后果                                      │
│    回写目标 | 重跑锚点 | 影响范围           │
│    [可选] 沉淀为规则                        │
├────────────────────────────────────────────┤
│ 次要动作 · 备注 · [主按钮：确认并重跑…]     │
└────────────────────────────────────────────┘
```

### 6.1 证据区（只读）

原则：**本屏信息应足够做出决定**，少跳转。

必显：对象标识、来源表/记录、系统结论、证据摘要；有置信度则展示。

### 6.2 裁决区（模板驱动）

由 `getReviewTemplateId(record)` 映射到 §3 七种模式之一，界面只答一个决策问题；控件见 §3.4。重跑锚点必须与 §3.2 阻断节点一致。

### 6.3 后果区（提交前强制可见）

| 字段 | 含义 |
|------|------|
| 回写目标 | 字典 / 映射表 / 对齐结果 / 隔离区 / 源表… |
| 重跑锚点 | 流水线节点名与 stepId（如「实体对齐消歧 · align」） |
| 影响范围 | 批次级恢复公共流程 / 任务级仅本对象 |

主按钮文案应体现后果，例如「确认映射并重跑」「确认合并并从对齐节点重跑」，避免笼统「提交」。

### 6.4 状态与动作

| 状态 | 行为 |
|------|------|
| 待处理 | 可编辑；主/次动作；可选撤销、重试 |
| 已完成 / 已撤销 | 只读展示 `decision` / `decisionNote` / 完成时间 |

主路径：`POST /manual-reviews/{id}/actions`（`rerun` 控制是否从阻断节点重跑）。

## 7. 影响范围与优先级模型

```text
P0（批次级）  公共流程异常（如 LLM 批量输出格式错误 → T_RUNTIME @ 大模型抽取）
              → 当前节点及下游阻断 → 队列置顶、红色徽章

P1（任务级）  单对象冲突/证据不足/必填缺失等（T_LINK / T_EVIDENCE / T_DQ_* …）
              → 隔离当前任务，同批其他任务继续
              → 修正后从当前节点重跑
```

界面承诺：

- 队列排序与徽章与该模型一致；
- 详情 banner / 后果区明示「已阻断」或「仅本对象」；
- 批次级修正后强调「恢复公共流程」。

## 8. 与 Pipeline 的衔接

```text
【图谱构建】抽取 / 对齐 / 校验 …
        │
        ├─ 通过 ──────────────► 写入图谱（结果入库）
        │
        └─ 失败/低置信 ───────► 隔离区 + 人工处理实例（§3 七种模式）
                                      │
                                      ▼
                               人工裁决（本界面）
                                      │
                          ┌───────────┼───────────┐
                          ▼           ▼           ▼
                       回写结果    从失败节点重跑   （可选）规则沉淀
```

`resolvePipelineStep` 保证：

- 列表「阻断节点」与流水线语言一致；
- 后果区重跑锚点可执行；
- 处理分类 chips 与阶段对齐。

质量校验建议演进为明确双分支（与《图谱构建流水线设计说明》一致）：

```text
                    ┌→ 校验通过 → 写入图谱
抽取 → 质量校验 ───┤
                    └→ 校验失败 → 人工处理（T_EVIDENCE / T_ATTR）→ 修正后重跑
```

## 9. 前后端契约（界面依赖）

统一前缀 `/api/v1`，响应 `{ code, success, data, msg }`。

| 方法 | 路径 | 界面用途 |
|------|------|----------|
| GET | `/manual-reviews` | 队列列表与筛选 |
| GET | `/manual-reviews/{id}` | 详情对象、证据、关联任务 |
| GET | `/manual-reviews/{id}/flow` | 处理流程时间线（可扩展） |
| POST | `/manual-reviews/{id}/actions` | 提交裁决；`rerun=true` 从阻断节点重跑 |
| PUT | `/manual-reviews/{id}/result` | 改结果但不结束审核（少用） |
| POST | `/manual-reviews/{id}/retry` | 重新下发任务 |
| POST | `/manual-reviews/{id}/revoke` | 撤销人工任务 |

前端封装：`frontend/src/api/workflowOperations.ts`。  
模板与分类推导：`manual-review-data.ts`（可逐步下沉后端，但**交互形态仍由模板 ID 驱动**）。

建议详情载荷逐步结构化（减少前端写死样例）：

```json
{
  "id": "PI-…",
  "status": "待处理",
  "templateId": "T_LINK",
  "impactScope": "任务级",
  "pipelineStep": { "id": "align", "name": "实体对齐消歧", "phase": "图谱构建" },
  "evidence": { "summary": "…", "items": [] },
  "candidates": [],
  "consequence": { "writeTarget": "…", "rerunAnchor": "…" }
}
```

更完整的 API 说明见：`backend/docs/workflow_operations_api.md`。

## 10. 关键路径（端到端）

```text
顶栏铃 / 工作台「进入人工处理」
  → 队列（可带 batch）
  → 优先点开「批次级 · 已阻断」
  → 详情：读证据 → 按 §3 模板填裁决 → 核对后果（含图谱构建重跑锚点）
  → 主按钮提交（通常 rerun=true）
  → 状态变已完成；可回任务中心看重跑进度
```

失败路径：重试保持待处理；撤销进历史；证据不足可选「保持隔离」不重跑。

## 11. 视觉与交互约束

对齐现有平台规范（主色 `#165DFF`、工作区白底、表头 sticky；详见 `frontend/DESIGN_SPEC.md`）：

- 批次级：红系强调；任务级：蓝系说明。
- 分类 chips：按类型着色，与列表节点标签一致。
- 主按钮唯一、文案动作化；危险操作用次要/danger。
- 历史只读，避免误改已入图决策。

## 13. 验收要点

1. 从任务/异常铃能否一跳进对应批次队列或详情。  
2. 待处理是否批次级优先，且徽章与后果一致。  
3. 七种决策形状（§3）是否都能在「证据足够」前提下完成裁决。  
4. 各模式重跑锚点是否与【图谱构建】对应节点一致（§3.2 / §3.3）。  
5. 历史是否只读可审计；撤销/重试语义是否清晰。  
6. 新异常类型能否只加模板映射而不改队列壳。

---

## 14. 设计结论

人工处理界面 = **Pipeline 异常治理工作台**：队列按「阻断节点 + 影响范围」组织，详情强制 **证据 → 裁决 → 后果**，用 **7 种决策形状**覆盖多样异常，并与【图谱构建】**Schema 映射 / 大模型抽取 / 实体对齐消歧 / 规则验证与证据回链 / 结果入库** 等节点一一可追溯，保证「判得快、后果清、能重跑」。
