# 实体表补充 SQL 执行说明

文件：`gkx_kg_entity_completion_20261027.sql`。只准备文件，由你在开发机执行；本次没有修改开发库。

**仅补实体表、缺失字段和来源数据，不创建或写入七张关系表。**原 13 张实体表继续使用，缺少的报告、来源目录各补一张表。

| 实体表 | 补充内容 | 来源 |
|---|---|---|
| `kg_organization` | 缺失机构、名称及基础信息 | 七类机构 DWD 主表 |
| `kg_person` | 缺失学者、姓名、当前及任职机构 | `dwd_scholar` |
| `kg_paper` | 缺失论文、题名、DOI、年份 | 中英文论文表 |
| `kg_patent` | 缺失专利、发明人/申请人/权利人数组、源行 ID、题名及同族号 | 专利主表和对应子表 |
| `kg_project` | 缺失项目、参与人/主持人/机构及五类产出数组 | 中英文项目及产出表 |
| `kg_industry_chain`、`kg_industry_node` | 缺失链和节点、可唯一确认的链编码、溯源字段 | `dwd_industry_chain_info` |
| `kg_news` | 从已保存原始快照恢复明确机构 ID | 本表 `extra_json`；须命中已有机构 |

| `kg_data_source`（新表） | 实际存在来源表的目录元数据 | 开发机实际来源表及代码目录 |

人物、机构等各实体类型仍只有一张主表。新系统可据业务主键生成新的图 ID；本 SQL 不生成旧图 VID/EID。

## 执行

1. 先备份开发机现有 `gkx_kg`。该库的原 13 张实体表须已存在。
2. 检查 SQL 开头的 `USE gkx_kg`；将 `SET @source_db = 'gkx';` 改成真实 DWD 来源库名。来源库须与目标库在同一个 MySQL 实例。
3. 用 MySQL 8.0.21+ 客户端执行，账号需有来源读取、目标表修改和存储过程/函数创建权限：

```bash
mysql -h 127.0.0.1 -P 3306 -u YOUR_USER -p --default-character-set=utf8mb4 --show-warnings < gkx_kg_entity_completion_20261027.sql > completion.log 2>&1
```

4. 查看退出码、`ERROR`、逐步统计和末尾缺项清单。缺源表会记录跳过，不造数据。不要用 `--force` 忽略错误。

## 处理规则

- 按明确来源键查找现有实体；能唯一定位时沿用其业务主键，只补空字段。
- 有真实来源但确无现有实体时才新增；不从人名、关键词或统计数捏造实体。
- 同来源键存在冲突时不任意选值；超长值不截断匹配，缺失或歧义会记录。
- 明确测试标记及混有可疑来源的聚合记录跳过。原库已有测试记录不会自动删除；来源无标记也不代表已完成真实性认证。
- 同节点多链不能塞成一个链编码；单值列仅唯一时补，原始多链事实仍在来源表。
- 这是增量补充，保留已有非空值，不做全库清洗或删除同步；DDL 会隐式提交，不是整文件原子事务。
- 投资和特殊事件的参与明细是关系事实，不会因本文件执行而新增关系表或写图；关系规则见配套 MD。
